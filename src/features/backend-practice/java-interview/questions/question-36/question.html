Question: How would you handle distributed transactions when payment succeeds but inventory reservation fails, using Saga, compensation transactions, eventual consistency, and the Transactional Outbox pattern?

Short answer

A local Spring transaction cannot atomically commit payment and inventory databases in different services. Model the order as a saga: each service performs a local transaction and emits a durable result event. If inventory fails after payment succeeds, initiate a compensating refund/void, not a fictional database rollback of the completed payment. The order is temporarily inconsistent while the saga runs; explicit states and reconciliation make that eventual consistency visible and recoverable.

Flow, step by step

  1. Create order PENDING with a unique request ID. Reserve inventory first when possible, then authorize payment; sequence depends on the business's failure cost.
  2. Each local transaction writes its business row and an outbox event together. A relay publishes the event to Kafka; if it crashes after publish, it may publish again.
  3. Consumers insert the event ID in a processed-events table within their local transaction, making duplicate delivery harmless.
  4. If payment succeeds but reservation fails, record COMPENSATING, issue an idempotent void/refund command, and transition to CANCELLED only after confirmation.
  5. Track timeouts, stuck states, retry budgets, and a manual reconciliation path. Compensation can itself fail and must be retried safely.

Runnable Java 17 state-machine example

Save as SagaStateDemo.java. This is a deterministic in-process model; the production implementation persists each transition and command.

public class SagaStateDemo {
    enum State { PENDING, PAID, COMPENSATING, CANCELLED, COMPLETED }

    static State onPaymentSuccess(State state) {
        if (state != State.PENDING) throw new IllegalStateException();
        return State.PAID;
    }
    static State onInventoryFailure(State state) {
        if (state != State.PAID) throw new IllegalStateException();
        return State.COMPENSATING;
    }
    static State onRefundConfirmed(State state) {
        if (state != State.COMPENSATING) throw new IllegalStateException();
        return State.CANCELLED;
    }

    public static void main(String[] args) {
        State state = onPaymentSuccess(State.PENDING);
        state = onInventoryFailure(state);
        System.out.println("before refund=" + state);
        state = onRefundConfirmed(state);
        System.out.println("final=" + state);
    }
}

Expected output:

before refund=COMPENSATING
final=CANCELLED

Real-world edge cases

A compensation is a new business action, not time travel: a refund may take time or incur fees. Outbox removes the local DB + broker dual-write gap, but it does not guarantee exactly-once delivery to a consumer. Publish and consume events with stable IDs; use unique constraints and idempotent state transitions. Orchestration centralizes saga decisions; choreography lets services react to events but can become difficult to trace. Define what a customer sees while an order is pending or refunding.

Common follow-up interview questions and answers

  • Why not one @Transactional annotation? It controls a local transaction manager, not separate databases and payment providers.
  • What if the outbox relay publishes twice? Consumers deduplicate by event ID in their own transaction.
  • What if refund fails? Keep the order in a compensating state, retry idempotently, alert, and reconcile.
  • What is eventual consistency? Services may temporarily disagree, but a defined process converges them to a valid outcome.

Interview-ready answer

I would use a saga with explicit states and local transactions. If payment succeeds and inventory fails, I record a compensation command and perform an idempotent void/refund, leaving the order pending until confirmed. A transactional outbox reliably publishes local state changes, and consumers deduplicate repeated events. I monitor stuck sagas and reconcile failures because compensation can fail too.
