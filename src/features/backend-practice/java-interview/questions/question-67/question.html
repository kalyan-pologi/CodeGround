Question: What is the difference between @RestController and @Controller internally, and what happens when a request reaches a REST endpoint?

Short answer

@RestController is effectively @Controller plus @ResponseBody for handler methods, so return values are written through HTTP message converters. A normal controller usually resolves a view unless a method uses @ResponseBody.

Request flow

  1. Filters and security process the request.
  2. DispatcherServlet selects a handler through mappings.
  3. Argument resolvers bind path, query, headers, and JSON body.
  4. Validation and controller logic run.
  5. Return-value handlers serialize the response and exception resolvers map failures.

Measure each stage with tracing when an endpoint is slow; controller execution time is not the whole request time.

I distinguish handler selection, argument conversion, business work, serialization, and filters because each can be the bottleneck.

Failure and performance points

A malformed JSON body fails during message conversion before the controller runs. Validation errors are different from authorization failures and domain conflicts, so map them to stable response types. Large JSON serialization, filters, security checks, and lazy entity traversal can dominate time after the service method itself is fast.

Minimal controller example

@RestController
@RequestMapping("/orders")
class OrderController {
  @GetMapping("/{id}") OrderView get(@PathVariable long id) { return service.find(id); }
}

Production code should add authorization, validation, a stable error contract, and a service boundary rather than placing database work in the controller.

Interview-ready answer

@RestController combines controller registration with response-body serialization. A request passes filters and security, handler mapping, argument conversion, validation, business logic, serialization, and exception resolution, so I measure each stage when latency is high.
