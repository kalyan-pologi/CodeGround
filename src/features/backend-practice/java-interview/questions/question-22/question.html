Question: What happens internally when a Spring Boot application starts, including @SpringBootApplication, auto-configuration, component scanning, ApplicationContext, and bean lifecycle?

Short answer

SpringApplication.run() creates and refreshes an ApplicationContext. @SpringBootApplication combines configuration, component scanning, and auto-configuration. Scanning discovers application components; auto-configuration contributes beans when classpath, properties, and missing-bean conditions match. Spring resolves dependencies, constructs beans, applies post-processors/proxies, runs initialization callbacks, starts the web server when relevant, then runs application runners.

Startup, step by step

  1. Boot builds an Environment from command-line arguments, environment variables, configuration files, and other property sources; profile selection affects which configuration applies.
  2. It creates the appropriate context type (for example, a servlet web context) and registers the application's configuration class.
  3. @ComponentScan scans from the main class's package downward for @Component, @Service, @Repository, and @Controller. Explicit @Bean methods register more definitions.
  4. Auto-configuration imports conditional configuration. Conditions such as “class exists,” “property enabled,” and “no user bean exists” determine which beans are added. User-defined beans can cause defaults to back off.
  5. During context refresh, Spring resolves dependencies and instantiates non-lazy singletons, applies BeanPostProcessors, initialization callbacks such as @PostConstruct, and AOP proxies. It starts embedded server infrastructure, then runners execute.

The exact order of every internal callback depends on configuration and framework version. A bean should not rely on arbitrary peer-bean creation order. Use explicit dependencies or lifecycle interfaces when ordering matters.

Runnable Spring Boot example

In a Spring Boot project with the core starter, save as src/main/java/demo/StartupDemo.java and run the application. Boot's own log lines vary; the application line below is stable.

package demo;

import org.springframework.boot.CommandLineRunner;
import org.springframework.boot.SpringApplication;
import org.springframework.boot.autoconfigure.SpringBootApplication;
import org.springframework.context.annotation.Bean;
import org.springframework.stereotype.Service;

@SpringBootApplication
public class StartupDemo {
    public static void main(String[] args) {
        SpringApplication.run(StartupDemo.class, args);
    }

    @Bean
    CommandLineRunner runner(GreetingService greeting) {
        return args -> System.out.println(greeting.message());
    }
}

@Service
class GreetingService {
    String message() { return "context-ready"; }
}

Expected application output: context-ready. Spring first creates GreetingService and injects it into the runner.

Real-world issues and edge cases

A main class placed too deep in the package tree may not scan sibling packages. A missing database driver can alter auto-configuration; a failing constructor or circular dependency can stop refresh. Use Boot's condition evaluation report or --debug to see why an auto-configuration matched or backed off. Keep expensive migrations and remote calls out of constructors and @PostConstruct; control startup/readiness separately. Secure Actuator endpoints and do not expose internal configuration publicly.

Common follow-up interview questions and answers

  • What does @SpringBootApplication combine? @SpringBootConfiguration, @EnableAutoConfiguration, and @ComponentScan.
  • Does auto-configuration always override my bean? Usually conditional defaults back off when an appropriate user bean exists; inspect the specific condition.
  • When are singleton beans created? Normally during context refresh, unless lazy initialization or another rule delays them.
  • Why might @Transactional not work inside @PostConstruct? Proxy initialization and transaction advice may not yet be available as expected.

Interview-ready answer

SpringApplication.run builds the environment and application context, scans application packages, applies conditional auto-configuration, and refreshes the bean factory. During refresh, Spring injects dependencies and runs bean post-processors and initialization callbacks; for web apps it also starts the embedded server, then runners execute. I use the condition report to diagnose missing or unexpected beans and avoid heavy work in constructors.
