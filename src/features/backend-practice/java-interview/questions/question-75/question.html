Question: What are the most common Spring Boot performance mistakes, and how would you identify them with metrics, traces, and profiling?

Short answer

Common mistakes include unbounded thread pools, oversized request concurrency, N+1 queries, holding database connections during remote calls, missing timeouts, excessive retries, synchronous work on event-loop threads, large payloads, and exposing expensive debug logging.

Investigation order

  1. Start with throughput, error rate, p50/p95/p99 latency, saturation, and dependency timings.
  2. Use distributed traces to locate the slow segment.
  3. Use thread dumps, pool metrics, SQL plans, allocation profiles, and GC data to confirm the cause.
  4. Apply one bounded change and compare production-like load results.

Do not treat CPU as the only capacity signal: low CPU can mean threads are waiting on I/O, locks, pools, or rate limits.

I optimize from observed wait time and saturation, not from a generic list of framework settings.

Concrete diagnostic examples

  • Low CPU plus high latency: inspect thread dumps, pool wait, locks, and remote I/O.
  • Fast SQL plus slow API: inspect N+1 queries, mapping, serialization, filters, and network time.
  • Peak-only failures: inspect queueing, rate limits, connection caps, GC pauses, and p99 latency.
  • Memory growth: compare allocation profiles, heap occupancy after GC, caches, and retained references.

Follow-up questions

  • Why can adding threads reduce throughput?
  • How do you choose a useful load-test workload?
  • Which metric proves that a fix improved the system?

Minimal measurement checklist

http_server_requests_seconds{quantile="0.99"}
hikaricp_connections_pending
jvm_gc_pause_seconds
process_cpu_usage

Pair aggregate metrics with traces and thread or heap profiles. A successful change reduces tail latency or saturation without shifting the bottleneck to a dependency.

Interview-ready answer

I begin with p95/p99 latency, throughput, errors, and saturation, then trace the slow segment and confirm it with thread, pool, SQL, allocation, or GC data. I apply one bounded change and verify it under production-like load rather than tuning blindly.
