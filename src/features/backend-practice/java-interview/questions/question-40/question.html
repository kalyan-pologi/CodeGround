Question: How does Apache Kafka work internally, including brokers, topics, partitions, offsets, consumer groups, rebalancing, and message ordering?

Short answer

Kafka stores records in ordered partition logs spread across brokers. A topic is a named collection of partitions; each record has an offset within its partition. A consumer group divides partitions among its members so each partition is processed by one group member at a time under normal assignment. Adding/removing members triggers rebalancing. Ordering is guaranteed within a partition, not across an entire multi-partition topic.

Internal working, step by step

  1. A producer selects a topic partition, commonly from a stable record key such as orderId, and sends a batch to the partition leader broker.
  2. The leader appends records and replicates them to follower brokers according to topic replication and producer acknowledgment settings.
  3. Each partition's offsets increase monotonically. An offset is a position, not a global ID or timestamp.
  4. A consumer polls assigned partitions, processes records, and commits the next offset to resume from. Different consumer groups track their own positions independently.
  5. On rebalance, partitions move between consumers; uncommitted work may be read again. Make side effects idempotent.

Runnable Java 17 partition-key illustration

Save as PartitionKeyDemo.java. This is an illustration of stable key-to-partition mapping, not Kafka's exact partitioner algorithm.

public class PartitionKeyDemo {
    static int partition(String key, int count) {
        return Math.floorMod(key.hashCode(), count);
    }

    public static void main(String[] args) {
        int first = partition("order-7", 3);
        int second = partition("order-7", 3);
        System.out.println("sameKeySamePartition=" + (first == second));
        System.out.println("partitions=" + 3);
    }
}

Expected output:

sameKeySamePartition=true
partitions=3

The same key is routed consistently while partition count and partitioner configuration stay stable. Changing the partition count can change routing for future records, so ordering across that change needs care.

Real-world edge cases

More consumers than partitions in one group leave some consumers idle. A hot key sends disproportionate load to one partition. Slow processing can exceed poll/rebalance constraints and cause repeat delivery. Retention is time/size based unless compaction is configured; committing an offset does not delete the record. Use schemas and compatibility rules for evolving event payloads. Replication improves availability but does not make an external database update exactly-once.

Common follow-up interview questions and answers

  • Does Kafka order a whole topic? No; only records within one partition have a total order.
  • What is consumer lag? Difference between a partition's latest available offset and the group's committed/processed position, interpreted carefully.
  • What happens during rebalance? Partition assignments change, and unfinished records can be reprocessed.
  • Can two groups both read one record? Yes. Each group has independent offsets.

Interview-ready answer

Kafka is a replicated, partitioned append log. Producers append to partition leaders; offsets identify positions per partition. A consumer group assigns each partition to one member and stores its own progress. Rebalances move assignments and can cause replay, so consumers must be idempotent. I choose a stable aggregate key to preserve order for related events and scale by partitions, not by adding unlimited consumers.
