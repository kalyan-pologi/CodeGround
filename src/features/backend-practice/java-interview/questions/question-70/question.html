Question: How does Spring exception translation work from JDBC or Hibernate exceptions to Spring DataAccessException types?

Short answer

Repository infrastructure and exception-translation post-processors convert vendor-specific persistence exceptions into a consistent unchecked DataAccessException hierarchy. The translated type communicates categories such as integrity violations, connection failures, timeouts, and concurrency conflicts.

How to use it

  • Log the root cause and constraint or SQL state.
  • Map expected conflicts to a stable API response such as 409.
  • Retry only transient, safe-to-repeat operations.
  • Do not catch every data-access exception and return success.
Translation gives service code a portable abstraction, but diagnosis still requires the vendor error and the operation's transaction context.

Concurrency and API mapping

A unique-key conflict may be an expected idempotency race, while a foreign-key violation may be a client or data-integrity error. A deadlock or transient connection failure may be retryable only when the operation is safe and the transaction is restarted from a clean boundary. Do not retry a transaction by continuing to use a rollback-only persistence context.

Follow-up questions

Minimal mapping example

@ExceptionHandler(DataIntegrityViolationException.class)
ResponseEntity<ApiError> conflict() { return ResponseEntity.status(409).body(ApiError.conflict()); }

Keep the vendor SQL state and constraint name in protected logs, while returning a stable and safe client response.

Interview-ready answer

Spring translates vendor persistence failures into a portable unchecked hierarchy. I use the translated category for service behavior, retain the root cause for diagnosis, and retry only transient operations from a clean transaction.
