Question: How would you protect REST APIs against SQL injection, XSS, CSRF, IDOR/BOLA, unauthorized access, and sensitive data exposure?

Short answer

Layer defenses at the boundary and the business object. Parameterize SQL, validate input, encode data in its output context, enforce authentication plus per-object authorization, choose CSRF protection based on browser credential handling, and minimize/redact sensitive data. A gateway or frontend check cannot replace authorization inside the service.

Threat-by-threat design

  • SQL injection: use prepared statements/ORM bind parameters. Never concatenate user data into SQL. Whitelist dynamic table/column names because identifiers cannot be bound as values.
  • XSS: encode untrusted data for HTML/attribute/URL/JavaScript context at rendering time; avoid unsafe HTML injection and use a Content Security Policy. A JSON API can still feed an unsafe browser UI.
  • CSRF: matters for browser requests where credentials such as cookies are sent automatically. Use CSRF tokens and suitable SameSite cookies; a stateless bearer-token API with no ambient cookie authentication has a different threat model.
  • IDOR/BOLA: query or authorize each object under the caller's tenant/owner; changing /orders/7 to /orders/8 must not reveal another user's order.
  • Exposure: return DTOs with only required fields, restrict logs/traces, encrypt sensitive data appropriately, rotate secrets, and rate-limit abusive calls.

Runnable Java 17 authorization illustration

Save as ObjectAccessDemo.java. A real service would load the order from the database with tenant scoping, not trust client-supplied ownership.

public class ObjectAccessDemo {
    record Order(long id, String owner) {}

    static int readStatus(String caller, Order order) {
        return caller.equals(order.owner()) ? 200 : 403;
    }

    public static void main(String[] args) {
        Order order = new Order(7, "alice");
        System.out.println("alice=" + readStatus("alice", order));
        System.out.println("bob=" + readStatus("bob", order));
    }
}

Expected output:

alice=200
bob=403

A safe JDBC query similarly uses PreparedStatement("select ... where id=? and owner_id=?") and binds both values; no row means the caller cannot access that object.

Real-world edge cases

Validation is not a replacement for output encoding. Escaping HTML is not a fix for SQL injection. CORS does not authorize requests; it is a browser cross-origin policy. Avoid mass assignment by mapping allowed DTO fields explicitly. Do not expose stack traces, JWTs, passwords, or payment details in errors and logs. Test cross-tenant access for every read, update, and delete endpoint, including bulk/export paths.

Common follow-up interview questions and answers

  • Is an authenticated user allowed any resource ID? No; authorization must be checked on each object.
  • Does a prepared statement prevent all injection? It protects bound values; dynamic SQL identifiers and unsafe string fragments still need whitelisting.
  • Is CSRF relevant to JWT? It depends on transport. Automatically sent cookies can be CSRF targets; a bearer token added explicitly in a header differs.
  • Does CORS stop malicious clients? No; non-browser clients are not constrained by CORS.

Interview-ready answer

I use parameterized SQL, DTO-level input validation, context-aware output encoding, and explicit object-level authorization for every request. I apply CSRF defenses for cookie-authenticated browser flows, minimize sensitive data in responses and logs, and test cross-user/tenant access. I treat CORS and gateway authentication as supporting controls, not substitutes for service-side authorization.
