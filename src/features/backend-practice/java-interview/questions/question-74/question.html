Question: How do you make a scheduled Spring job safe when multiple application instances run, and how do you avoid duplicate execution?

Short answer

@Scheduled runs independently in every instance unless coordination is added. Make the job idempotent, then use a shared lock or scheduler such as a database lock, ShedLock, Quartz, or a queue with one consumer when only one execution should run.

Design checklist

  1. Use a stable job key and an execution record or lease.
  2. Set a lock duration shorter than the job's worst-case time or renew the lease.
  3. Make retries safe and record success, failure, and ownership.
  4. Decide whether missed schedules should be skipped, replayed, or coalesced.
Distributed scheduling is a coordination problem. A local JVM flag cannot prevent duplicate work after horizontal scaling or a restart.

Failure cases

A lock holder can crash midway, a clock can drift, or a job can run longer than its schedule interval. Use a lease with expiry, renew it for long work, and make each item operation idempotent. Store a job execution ID so operators can distinguish a retry from a duplicate schedule.

Follow-up questions

  • What happens if the lock expires while work is still running?
  • When is a queue better than a scheduled task?
  • How do you test duplicate execution and crash recovery?

Minimal lock example

@Scheduled(cron = "0 */5 * * * *")
void run() {
  if (lockProvider.tryLock("invoice-reconciliation", Duration.ofMinutes(4))) {
    try { reconcileIdempotently(); } finally { lockProvider.release(); }
  }
}

The lock provider must be shared across instances. The business operation still needs an idempotency key or execution record because a crash can happen after the side effect and before lock release.

Interview-ready answer

@Scheduled runs in every instance. I combine a shared lease or scheduler with idempotent work, execution records, bounded lock duration, and a clear policy for missed or overlapping runs.
