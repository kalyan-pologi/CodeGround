Question: A Spring Boot application works locally but fails or performs poorly in production. How would you troubleshoot profiles, configuration, Actuator, logging, startup, connection pools, and resource limitations?

Short answer

Compare the production environment with local assumptions before changing code. Confirm the active profile and resolved non-secret configuration, startup failure cause, dependency reachability, health/readiness, database pool state, thread/memory/CPU limits, and latency by dependency. Use structured logs, metrics, and traces to narrow the difference; reproduce with production-like limits and configuration.

Investigation, step by step

  1. Check the exact image/commit, JDK, Spring Boot version, startup arguments, active profiles, and environment-variable names. Configuration precedence can make a production setting override a local file.
  2. Read startup logs from the first exception, not just the final “application failed” line. Inspect missing beans, port binding, migrations, credentials, TLS, DNS, and database connectivity.
  3. Use protected Actuator health, readiness, metrics, and condition reports. A live JVM is not necessarily ready to serve requests.
  4. For slowness, correlate request traces with JDBC pool active/pending/acquisition time, slow SQL, HTTP client timeouts, thread states, GC, and container throttling or memory pressure.
  5. Reproduce using the same profile, resource limits, and downstream behavior. Roll back if customer impact is high, then fix the verified cause.

Runnable Spring Boot diagnostic example

In a Spring Boot project, place this in src/main/java/demo/ConfigDemo.java. Run with --spring.profiles.active=prod --app.name=orders. It prints only non-secret settings.

package demo;

import java.util.Arrays;
import org.springframework.boot.ApplicationRunner;
import org.springframework.boot.SpringApplication;
import org.springframework.boot.autoconfigure.SpringBootApplication;
import org.springframework.context.annotation.Bean;
import org.springframework.core.env.Environment;

@SpringBootApplication
public class ConfigDemo {
    public static void main(String[] args) { SpringApplication.run(ConfigDemo.class, args); }

    @Bean
    ApplicationRunner showConfig(Environment env) {
        return args -> {
            System.out.println("profiles=" + Arrays.toString(env.getActiveProfiles()));
            System.out.println("app=" + env.getProperty("app.name", "unset"));
        };
    }
}

Expected application output with those arguments:

profiles=[prod]
app=orders

Do not print passwords, tokens, connection strings, or full environment dumps in production logs.

Real-world edge cases

A pool of ten DB connections can saturate even with 200 request workers and low CPU. Kubernetes liveness failures can cause restart loops while readiness should only remove traffic. JVM heap below its max does not rule out container OOM. A local database may hide production query-plan/index differences. Actuator endpoints should expose only needed information and be secured; centralized logs need correlation IDs and redaction.

Common follow-up interview questions and answers

  • What is the first thing to compare? Deployed commit/image, active profiles, resolved config, and the first failure log.
  • Does “health UP” prove the app is fast? No. It is a coarse availability signal; use latency and dependency metrics.
  • Why can CPU be low while requests time out? Threads can be waiting for DB connections, locks, or remote IO.
  • How do you protect secrets during debugging? Log configuration keys and safe values only; use redaction and least-privilege access.

Interview-ready answer

I would compare the deployed artifact, JDK, profile, and effective configuration with local behavior, then follow the earliest startup or request failure. I would use secured Actuator metrics, logs with correlation IDs, traces, thread dumps, and pool/GC/container metrics to locate the bottleneck. I would reproduce under production-like limits, fix the confirmed difference, and roll back promptly if users are affected.
