Question: How does the Java Memory Model work, and what are the differences between volatile, synchronized, atomicity, visibility, and happens-before relationships?

Short answer

The Java Memory Model (JMM) defines which values one thread may observe from another and which operations may be reordered. A happens-before relationship gives a visibility and ordering guarantee. volatile establishes that guarantee for reads and writes of one field, while synchronized also provides mutual exclusion. Atomic classes combine indivisible updates with specified memory effects. Visibility alone does not make a compound operation atomic.

Start with the basics

Threads share heap objects but can execute using registers, caches, compiler optimizations, and CPU reordering. Without coordination, reading a shared field in one thread is a data race: another thread's latest write is not guaranteed to be observed. Visibility means seeing a published value; atomicity means an operation cannot be observed halfway through. An increment is conceptually read → add → write, so two increments can lose an update even when the field is volatile.

Internal working: happens-before rules

  1. Within one thread, earlier actions happen-before later actions in program order.
  2. An unlock of a monitor happens-before a later lock of that same monitor. This is why both sides must synchronize on the same object.
  3. A write to a volatile field happens-before a later read of that field. Writes before publishing a volatile “ready” flag become visible to a reader that observes it.
  4. Calling Thread.start() happens-before actions in that thread; all actions in a thread happen-before another thread successfully returns from join().
  5. These rules are transitive. Correctly synchronized, data-race-free code can be reasoned about as if its operations were sequentially consistent.

final fields have special safe-publication guarantees when an object is properly constructed and does not escape its constructor. An atomic class such as AtomicInteger gives an atomic read-modify-write operation; a volatile field does not. A lock also protects multi-field invariants such as “balance plus reserved amount equals total.”

Runnable Java 17 example

Save as MemoryModelDemo.java and run with javac MemoryModelDemo.java and java MemoryModelDemo.

import java.util.concurrent.atomic.AtomicInteger;

public class MemoryModelDemo {
    static volatile boolean ready;
    static int message; // Published by the volatile ready flag.

    public static void main(String[] args) throws InterruptedException {
        Thread writer = new Thread(() -> {
            message = 42;
            ready = true;
        });
        writer.start();
        while (!ready) Thread.onSpinWait();
        System.out.println("message=" + message);
        writer.join();

        AtomicInteger count = new AtomicInteger();
        Runnable increment = () -> {
            for (int i = 0; i < 1_000; i++) count.incrementAndGet();
        };
        Thread a = new Thread(increment);
        Thread b = new Thread(increment);
        a.start();
        b.start();
        a.join();
        b.join();
        System.out.println("count=" + count.get());
    }
}

Expected output:

message=42
count=2000

The volatile write publishes message=42; incrementAndGet() prevents lost increments. A busy spin is only for this small demonstration—production code normally uses a latch, future, queue, or blocking synchronization.

Real-world use and edge cases

  • Use a volatile cancellation flag for one-way visibility, not for compound balance updates.
  • Use a lock when a decision and several fields must change together. Hold it only as long as needed; do not perform slow network calls while holding it.
  • Use atomics for independent counters and single-value state transitions. An atomic reference to a mutable object does not automatically protect that object's fields.
  • Publishing a reference without synchronization can expose stale fields. Use final fields, thread-safe containers, locks, volatile publication, or another documented safe-publication mechanism.

Common follow-up interview questions and answers

  • Does volatile make count++ atomic? No; two threads can read the same old count.
  • Does synchronized guarantee visibility? Yes, when writes occur before unlocking and reads occur after locking the same monitor.
  • Is join() just a wait? It also establishes happens-before from the completed thread's actions to the joining thread.
  • Does happens-before mean an action ran earlier in wall-clock time? It is a formal ordering/visibility relationship, not simply a timestamp comparison.

Interview-ready answer

The JMM tells us when writes by one thread become visible to another and which reorderings are legal. I look for a happens-before edge: volatile write/read, unlock/lock on the same monitor, thread start/join, or a concurrent utility. Volatile gives visibility and ordering for a field but not atomic read-modify-write; synchronized adds mutual exclusion, and atomic classes provide indivisible single-value operations. For multi-field invariants I use a lock or a transactional store.
