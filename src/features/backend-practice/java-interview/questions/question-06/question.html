Question: How would you choose between HashMap, ConcurrentHashMap, Hashtable, CopyOnWriteArrayList, and TreeMap for different real-world applications?

Short answer

Choose based on ordering, concurrency, read/write ratio, null policy, and required operations. Use HashMap for ordinary single-threaded or externally synchronized key-value access, ConcurrentHashMap for concurrent map operations, TreeMap for sorted keys and range queries, and CopyOnWriteArrayList for many reads with very rare writes. Avoid new uses of legacy Hashtable unless compatibility requires it.

Runnable selection example

import java.util.*;
import java.util.concurrent.*;

public class CollectionChoiceDemo {
    public static void main(String[] args) {
        Map<String, Integer> fastLookup = new HashMap<>();
        Map<String, Integer> sharedCounts = new ConcurrentHashMap<>();
        Map<Integer, String> sorted = new TreeMap<>();
        List<String> listeners = new CopyOnWriteArrayList<>();

        fastLookup.put("order-1", 100);
        sharedCounts.merge("success", 1, Integer::sum);
        sorted.put(2, "medium");
        sorted.put(1, "low");
        listeners.add("audit-listener");

        System.out.println(fastLookup.get("order-1"));
        System.out.println(sharedCounts.get("success"));
        System.out.println(sorted.firstKey());
        System.out.println(listeners);
    }
}

1

Concurrency details

ConcurrentHashMap makes individual operations and methods such as putIfAbsent, compute, and merge safe for concurrent use. A sequence such as “check then put” is not automatically atomic; use one of those compound operations. Its iterators are weakly consistent rather than fail-fast.

Hashtable synchronizes individual methods, but a sequence of calls still needs external coordination. CopyOnWriteArrayList gives readers a stable snapshot-like array and is useful for listener registries, configuration observers, or routing tables with rare changes.

Real-world decision examples

  • Per-request local lookup: HashMap.
  • Application-wide counters or a token registry: ConcurrentHashMap with merge or compute.
  • Time windows, sorted IDs, or range queries: TreeMap.
  • Event listeners read on every request but changed only during startup: CopyOnWriteArrayList.
  • Old library contract requiring a synchronized map: Hashtable, preferably behind a compatibility boundary.

Edge cases and common mistakes

  • Do not use CopyOnWriteArrayList for a high-volume queue or frequently updated collection.
  • Do not assume ConcurrentHashMap makes the values themselves thread-safe.
  • Do not use TreeMap when you only need lookup and do not need ordering.
  • Do not use a synchronized wrapper as a replacement for understanding iteration and compound-operation locking.
  • Do not select a collection only by benchmark numbers; measure the actual workload, memory pressure, and contention.

Follow-up questions

  • Why does ConcurrentHashMap reject null? A null result can clearly mean “no mapping” during concurrent operations, so allowing null would make APIs such as get ambiguous.
  • When is LinkedHashMap a better choice? When insertion or access order matters, such as a simple LRU-style structure.
  • What if I need a thread-safe sorted map? Consider ConcurrentSkipListMap, external synchronization, or a design that avoids shared mutation.

Interview-ready answer

I choose HashMap for ordinary unsynchronized lookup, ConcurrentHashMap for shared concurrent map updates, TreeMap for sorted keys and ranges, and CopyOnWriteArrayList for read-heavy lists with very rare writes. Hashtable is mainly a legacy compatibility choice. I also check whether compound operations need atomic methods such as compute or merge.

Selection by workload

Start with the operation the application needs rather than the collection name. If the key is arbitrary and lookup dominates, a hash map is usually appropriate. If users ask for “all records between these two keys,” a sorted map is a better fit. If readers greatly outnumber writes and readers must not block while a small list changes, copy-on-write can be ideal.

import java.util.*;
import java.util.concurrent.*;

public class CollectionWorkloadDemo {
    public static void main(String[] args) {
        Map<String, String> cache = new HashMap<>();
        NavigableMap<Integer, String> byPriority = new TreeMap<>();
        ConcurrentMap<String, Long> counters = new ConcurrentHashMap<>();
        List<Runnable> listeners = new CopyOnWriteArrayList<>();

        cache.put("token", "abc");
        byPriority.put(10, "normal");
        byPriority.put(1, "urgent");
        counters.merge("requests", 1L, Long::sum);
        listeners.add(() -> { });

        System.out.println(byPriority.firstEntry().getValue());
        System.out.println(counters.get("requests"));
    }
}

Expected output: urgent and 1.

Concurrency and atomicity

Thread safety of a collection does not automatically make a multi-step business operation atomic. This is unsafe even with a concurrent map:

if (!map.containsKey(key)) {
    map.put(key, value); // another thread can win between the two calls
}

Use putIfAbsent, computeIfAbsent, compute, or merge when the operation matches their semantics. Keep mapping functions short and do not recursively modify the same map from inside them.

Ordering and comparator correctness

TreeMap uses natural ordering or a comparator for placement and equality. The comparator must be transitive and consistent with the domain. A comparator that returns zero for distinct keys causes one value to replace or hide another. Null keys are generally not accepted by natural ordering, though a comparator can explicitly define a null policy.

CopyOnWriteArrayList iterators observe a snapshot of the backing array. A write copies the array, so reads are cheap and stable while writes are O(n) and allocate. It is excellent for listener lists and poor for queues, counters, or frequently changing collections.

Memory and performance trade-offs

  • HashMap uses extra bucket and node memory and has good average lookup, but iteration cost depends on capacity as well as size.
  • ConcurrentHashMap supports concurrent access without one global lock for normal operations, but contention can still occur on hot keys.
  • Hashtable synchronizes methods with a legacy coarse-grained model and rejects nulls; it is rarely the best new design.
  • TreeMap provides O(log n) operations and range views such as subMap, headMap, and tailMap.
  • CopyOnWriteArrayList can consume substantial memory during writes because old and new arrays coexist briefly.

Real-world decision examples

  • Per-request variables: local HashMap.
  • Feature flags read on every request and changed only by refresh events: immutable snapshot or CopyOnWriteArrayList for listeners.
  • Rate-limit counters shared by request threads: ConcurrentHashMap with atomic updates, or a distributed store for multiple instances.
  • Time-based scheduling and range lookup: TreeMap or a specialized queue.
  • Cross-process session state: none of these alone; use a database, Redis, or another shared system.

Additional follow-up answers

  • Why not use Hashtable for all thread-safe maps? Its coarse synchronization and legacy API are usually less suitable than ConcurrentHashMap.
  • When use a synchronized wrapper? When a simple legacy map needs synchronized individual operations and the caller can synchronize during iteration and compound actions.
  • What if sorted concurrent access is required? Consider ConcurrentSkipListMap, which provides sorted concurrent operations with different performance characteristics.
  • Why is a cache not just a HashMap? A production cache needs expiration, size bounds, concurrency behavior, eviction, metrics, and often cross-instance consistency.
