Question: What are deadlock, livelock, and starvation, and how would you detect, troubleshoot, and prevent them in production?

Short answer

In a deadlock, threads wait forever for resources held by each other. In a livelock, threads keep reacting and changing state but make no useful progress. In starvation, one task waits indefinitely while others repeatedly get service. Diagnose with thread dumps, lock ownership, queue/latency metrics, and workload traces; prevent with consistent lock ordering, short lock holds, bounded retries, and fair scheduling where necessary.

How a deadlock forms

Imagine transfer A → B locking A then B, while transfer B → A locks B then A. Each thread holds one lock and waits for the other. The classic necessary conditions are mutual exclusion, hold-and-wait, no forced preemption, and circular wait. Eliminating circular wait by always acquiring account locks in a stable order is often the simplest fix.

Runnable Java 17 example: ordered locks

Save as OrderedTransferDemo.java. Both transfers acquire account 1 before account 2, regardless of direction.

public class OrderedTransferDemo {
    static final class Account {
        final int id;
        int balance = 100;
        Account(int id) { this.id = id; }
    }

    static void transfer(Account from, Account to, int amount) {
        Account first = from.id < to.id ? from : to;
        Account second = from.id < to.id ? to : from;
        synchronized (first) {
            synchronized (second) {
                if (from.balance < amount) throw new IllegalStateException();
                from.balance -= amount;
                to.balance += amount;
            }
        }
    }

    public static void main(String[] args) throws InterruptedException {
        Account a = new Account(1);
        Account b = new Account(2);
        Thread one = new Thread(() -> transfer(a, b, 10));
        Thread two = new Thread(() -> transfer(b, a, 20));
        one.start();
        two.start();
        one.join();
        two.join();
        System.out.println("A=" + a.balance + ", B=" + b.balance);
    }
}

Expected output: A=110, B=90. The same lock-order rule must apply to every code path. Real transfers spanning processes need a database transaction, not JVM monitors.

Detection and prevention in production

  • Deadlock: capture repeated jstack/jcmd Thread.print dumps, inspect BLOCKED threads and “waiting to lock”/“locked” lines, or use ThreadMXBean.findDeadlockedThreads(). Database deadlocks require database lock-wait and deadlock reports.
  • Livelock: CPU or retry activity continues, but completed work stops. Add jittered backoff and a retry budget; inspect repeated state transitions.
  • Starvation: long-tail queue wait increases for some tasks even while others finish. Avoid holding locks during IO, monopolizing a shared executor, or scheduling all work at one priority. Fair locks can help but may reduce throughput.
  • Lock timeouts: ReentrantLock.tryLock(timeout) enables recovery, but both acquired locks must be released in finally. A timeout diagnoses contention; it does not replace a consistent design.

Common follow-up interview questions and answers

  • Can synchronized deadlock? Yes, when threads acquire multiple monitors in inconsistent orders.
  • Is high CPU typical of deadlock? Usually blocked threads consume little CPU; high CPU with no progress may indicate livelock or spinning.
  • Does a fair lock guarantee no starvation? It improves acquisition fairness for that lock, but scheduling, queues, and other resources can still starve work.
  • What if two accounts have the same order key? Use a unique immutable ID or a global tie-break lock so the ordering remains total.

Interview-ready answer

Deadlock is circular waiting, livelock is activity without progress, and starvation is unfair indefinite waiting. I would inspect thread dumps and lock owners, correlate them with queue and completion metrics, then fix the resource-ordering or scheduling cause. For multi-lock operations I impose one global acquisition order; I also keep critical sections short, bound retries, and use timeouts where recovery is possible.
