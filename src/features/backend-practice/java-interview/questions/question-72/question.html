Question: How does Spring Boot configure logging by default, and how do you change logging safely in production?

Short answer

Boot provides a logging facade and a default backend through its starters, with console output and level defaults suitable for development. Production logging should be structured, centralized, configurable at runtime where safe, and free of secrets or unbounded payloads.

Operational approach

  • Set package-specific levels instead of enabling global debug.
  • Include correlation or trace IDs.
  • Sample noisy logs and rotate or ship them centrally.
  • Change levels through controlled configuration and revert after diagnosis.
Logging is part of the diagnostic path; I change the smallest package scope, preserve request correlation, and avoid turning an incident into a logging outage.

Production example

For a slow request, temporarily enable debug logging for the affected package or dependency, include a trace ID, and sample repeated messages. Avoid logging full authorization headers, payment payloads, or large response bodies. Restore normal levels after collecting evidence and alert on logging volume.

Minimal configuration

logging:
  level:
    com.example.orders: INFO
  pattern:
    console: '%d %-5level [%X{traceId}] %logger - %msg%n'

Prefer the deployment's structured logging format when the platform parses JSON, and protect trace identifiers and user data from accidental disclosure.

Interview-ready answer

Boot supplies a default logging facade and backend through its starters. In production I use structured, correlated, centrally collected logs, change the smallest package scope during diagnosis, and prevent secrets or unbounded payloads from entering the stream.
