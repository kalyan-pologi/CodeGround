Question: How do @Async, CompletableFuture, RestTemplate, WebClient, and FeignClient differ, and when would you use each for asynchronous and inter-service communication?

Short answer

@Async schedules a Spring method on an executor; CompletableFuture composes asynchronous Java results. RestTemplate is a synchronous HTTP client common in older Spring code; modern Spring also offers synchronous RestClient. WebClient supports non-blocking HTTP pipelines. Feign-style clients generate an HTTP client from an annotated interface, usually with blocking calls unless configured otherwise. These are different layers: scheduling work does not turn a blocking network call into non-blocking IO.

Internal working and choice

ToolWhat it doesKey caution
@AsyncProxy submits method execution to an executorSelf-invocation bypasses proxy; size executor
CompletableFutureCompose completion, error, timeout, and combination stagesChoose an executor; never lose failures
RestTemplate/RestClientSynchronous request/responseCalling thread waits; configure timeouts
WebClientNon-blocking reactive HTTPA terminal block() makes that call blocking
Feign clientDeclarative interface-to-HTTP proxyVerify timeout, retry, and client behavior

For a normal synchronous MVC service, a bounded executor plus blocking clients can be simple and effective. For many concurrent remote waits, a non-blocking WebClient pipeline or appropriately bounded virtual threads may scale better. Never assume “async” automatically means faster; parallel calls still consume downstream capacity and may amplify failures.

Runnable Java 17 example: combine two calls

Save as AsyncCallsDemo.java. The suppliers stand in for two independent API calls so the result is deterministic; replace them with timeout-configured clients in a service.

import java.util.concurrent.*;

public class AsyncCallsDemo {
    public static void main(String[] args) {
        ExecutorService pool = Executors.newFixedThreadPool(2);
        try {
            CompletableFuture<String> user =
                CompletableFuture.supplyAsync(() -> "Maya", pool);
            CompletableFuture<Integer> orders =
                CompletableFuture.supplyAsync(() -> 3, pool);
            String result = user.thenCombine(orders,
                (name, count) -> name + " has " + count + " orders")
                .orTimeout(2, TimeUnit.SECONDS)
                .exceptionally(error -> "profile unavailable")
                .join();
            System.out.println(result);
        } finally {
            pool.shutdown();
        }
    }
}

Expected output: Maya has 3 orders. Completion order may vary; thenCombine runs only when both results are available. In a real API, define whether partial success is acceptable and cancel/ignore late work after a deadline.

Real-world edge cases

@Async needs async support, a named bounded executor, and calls through a Spring proxy. Its thread does not automatically inherit a caller's transaction or thread-local security context. CompletableFuture.get()/join() block the caller. A non-blocking WebClient call loses much of its scaling benefit if repeatedly block()ed in an event-loop path. Configure connection pooling, connect/read/overall timeouts, idempotent retries with jitter, and tracing for every client. Feign is convenient for stable service contracts, but generated clients still need operational tuning.

Common follow-up interview questions and answers

  • Does @Async work on this.method()? No, the internal call bypasses proxy advice.
  • Does CompletableFuture start a new thread by itself? Only methods such as supplyAsync schedule work; ordinary stages may run in a completing thread.
  • When choose WebClient? When a non-blocking pipeline and high concurrency justify its reactive programming model.
  • Can remote calls share a Spring transaction? A local transaction does not make a remote call atomic.

Interview-ready answer

I separate execution from transport: @Async moves a Spring method onto an executor, CompletableFuture composes results, and RestTemplate/RestClient, WebClient, or Feign perform HTTP calls with different programming styles. I choose based on blocking needs and team complexity, then set bounded concurrency, timeouts, retries, and observability. An async wrapper around a blocking call is still blocking on its worker thread.
