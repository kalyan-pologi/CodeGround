Question: Write a Java program using two threads to print odd and even numbers from 1 to 100 in sequence.

Short answer

Share one counter and one monitor. The odd thread waits while the next number is even; the even thread waits while it is odd. Always test the condition in a while loop under the same lock, print/increment while holding it, and call notifyAll() so the other thread can proceed. When the counter passes 100, wake the peer so neither remains waiting forever.

Runnable Java 17 program

Save as OddEvenDemo.java.

public class OddEvenDemo {
    private static final Object lock = new Object();
    private static int next = 1;
    private static final int MAX = 100;

    static void printParity(int parity) {
        while (true) {
            synchronized (lock) {
                while (next <= MAX && next % 2 != parity) {
                    try { lock.wait(); }
                    catch (InterruptedException e) {
                        Thread.currentThread().interrupt();
                        lock.notifyAll();
                        return;
                    }
                }
                if (next > MAX) {
                    lock.notifyAll();
                    return;
                }
                System.out.print(next == MAX ? next + "\n" : next + " ");
                next++;
                lock.notifyAll();
            }
        }
    }

    public static void main(String[] args) throws InterruptedException {
        Thread odd = new Thread(() -> printParity(1), "odd");
        Thread even = new Thread(() -> printParity(0), "even");
        odd.start();
        even.start();
        odd.join();
        even.join();
    }
}

Internal working and edge cases

wait() atomically releases the monitor and suspends that thread. After notification it must reacquire the monitor and recheck the condition; wakeups can be spurious, and another thread might run first. Printing while holding the lock ensures that output order matches counter order. Both threads stop after 100, and notifyAll() wakes a peer that may still be waiting. If an interruption occurs, this demo restores the interrupt flag and exits; a production protocol should define how to cancel the other worker as well.

Common follow-up interview questions and answers

  • Why while instead of if around wait()? Because a wakeup does not guarantee that the condition is now true.
  • Why must wait() be inside synchronized? The caller must own that object's monitor.
  • Could notify() work here? With exactly one waiter of the opposite role it may, but notifyAll() is safer when wait conditions or thread counts change.
  • What happens if we forget the final notification? The peer could remain blocked after the last number.

Interview-ready answer

I share a counter under one monitor. Each thread waits in a loop until the counter has its parity, then prints and increments while holding the lock and notifies all waiters. The loop checks termination before waiting and after wakeup, so spurious wakeups and the final number do not cause out-of-order output or a hang.
