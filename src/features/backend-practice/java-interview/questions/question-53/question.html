Question: Write a Java program demonstrating a race condition and fix it using synchronized and AtomicInteger. Explain the expected output and internal working.

Short answer

count++ is a read, increment, and write. Two threads can read the same old value and overwrite one another, so a plain counter can lose updates. A synchronized method makes the entire increment a critical section and publishes updates when the monitor is released. AtomicInteger.incrementAndGet() performs an atomic read-modify-write operation, typically using compare-and-set machinery.

Runnable Java 17 program

Save as RaceFixDemo.java. The latches force both unsafe threads to read zero before either writes, making the lost update deterministic.

import java.util.concurrent.CountDownLatch;
import java.util.concurrent.atomic.AtomicInteger;

public class RaceFixDemo {
    static int unsafe;
    static int guarded;
    static final AtomicInteger atomic = new AtomicInteger();

    static synchronized void incrementGuarded() { guarded++; }

    static void await(CountDownLatch latch) {
        try { latch.await(); }
        catch (InterruptedException e) {
            Thread.currentThread().interrupt();
            throw new IllegalStateException(e);
        }
    }

    public static void main(String[] args) throws InterruptedException {
        CountDownLatch bothRead = new CountDownLatch(2);
        CountDownLatch release = new CountDownLatch(1);
        Runnable unsafeIncrement = () -> {
            int old = unsafe;
            bothRead.countDown();
            await(release);
            unsafe = old + 1;
        };
        Thread a = new Thread(unsafeIncrement);
        Thread b = new Thread(unsafeIncrement);
        a.start();
        b.start();
        bothRead.await();
        release.countDown();
        a.join();
        b.join();

        Runnable safeIncrement = () -> {
            incrementGuarded();
            atomic.incrementAndGet();
        };
        Thread c = new Thread(safeIncrement);
        Thread d = new Thread(safeIncrement);
        c.start();
        d.start();
        c.join();
        d.join();
        System.out.println("unsafe=" + unsafe);
        System.out.println("synchronized=" + guarded);
        System.out.println("atomic=" + atomic.get());
    }
}

Expected output:

unsafe=1
synchronized=2
atomic=2

Internal working and real-world meaning

The unsafe threads each read 0 and write 1. The monitor on the class serializes calls to the static synchronized method, so the guarded counter reaches 2. AtomicInteger retries a conflicting update so both increments count. A normal race may sometimes appear correct; forcing an interleaving is why this demonstration is reliable. Use the same lock for every guarded read and write. An atomic counter is good for metrics, while a multi-field invariant such as debit plus ledger entry needs a larger critical section or database transaction.

Edge cases and follow-up questions

  • Would volatile int unsafe fix it? No; visibility does not make ++ indivisible.
  • Does synchronization require the same monitor? Yes. Different lock objects do not coordinate access to the same state.
  • Can AtomicInteger overflow? Yes; it uses 32-bit integer arithmetic. Use a wider type/checks if required.
  • Which is faster? Depends on contention and workload; measure. Correctness comes first.

Interview-ready answer

A race happens because count++ is read–modify–write, so two threads can read the same value and lose an increment. I use synchronized to serialize the whole critical section or AtomicInteger.incrementAndGet() for a single independent counter. volatile alone does not solve it. For several related fields or cross-instance state, I use a lock or database transaction protecting the full invariant.
