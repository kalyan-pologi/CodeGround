Question: How does @Configuration differ from a normal class, and what is the complete Spring bean lifecycle?

Short answer

@Configuration marks a class as a source of bean definitions and lets Spring preserve container semantics when one @Bean method calls another. A bean is instantiated, dependencies are injected, post-processors run, initialization callbacks execute, and later destruction callbacks run for managed scopes.

Important details

  • Constructor injection happens before initialization callbacks.
  • Post-processors may wrap the bean in an AOP proxy.
  • Prototype destruction is not managed like singleton destruction.
  • Do not perform slow remote calls in constructors or initialization callbacks.
The lifecycle is a framework-managed sequence; application correctness should rely on explicit dependencies and lifecycle contracts, not incidental creation order.

Lifecycle traps

Calling a proxied method from a constructor or initialization callback can bypass advice because the proxy is not ready or the call stays inside the target object. Circular constructor dependencies fail early, while field or setter injection may defer the symptom but usually reduces clarity. Use constructor injection and explicit lifecycle events for startup work.

Follow-up questions

  • What does a BeanPostProcessor do?

Minimal lifecycle example

@Bean(initMethod = "connect", destroyMethod = "close")
Client client() { return new Client(); }

Keep initialization bounded and local. Remote migrations and long calls belong in explicit startup workflows or readiness-controlled jobs.

Interview-ready answer

A configuration class defines managed beans with container semantics. Spring creates the bean, injects dependencies, runs post-processors and initialization callbacks, may create a proxy, and later invokes destruction callbacks for managed scopes.
