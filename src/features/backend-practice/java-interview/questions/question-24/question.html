Question: How does @Transactional work internally in Spring, and why might transactions fail because of self-invocation, private methods, exception handling, propagation, or isolation?

Short answer

In Spring's default proxy mode, an external call enters a transactional proxy. The proxy asks a transaction manager to begin or join a transaction, invokes the target method, then commits or rolls back according to the outcome. A call from one method to another on this bypasses the proxy. Private methods cannot be intercepted by the usual proxy call path. The default rollback rule is for unchecked exceptions and Error, not every checked exception.

Internal working, step by step

  1. @EnableTransactionManagement/Boot infrastructure registers transaction advice and a transaction manager.
  2. The proxy intercepts a call from another bean. With REQUIRED propagation, it joins an existing transaction or begins one using a connection/entity manager bound to the current thread.
  3. The target executes database operations. On normal return, the manager commits; on a qualifying exception, it rolls back. Caught exceptions do not reach the proxy, so they do not automatically trigger rollback.
  4. Isolation controls what concurrent transactions can observe; the database actually enforces it. A Spring transaction does not automatically span a remote HTTP call or another service's database.

Runnable Spring Boot example

Use a Spring Boot project with spring-boot-starter-jdbc and H2. Place this in src/main/java/demo/TransactionDemo.java. The service is a separate bean so the call crosses the proxy.

package demo;

import org.springframework.boot.ApplicationRunner;
import org.springframework.boot.SpringApplication;
import org.springframework.boot.autoconfigure.SpringBootApplication;
import org.springframework.context.annotation.Bean;
import org.springframework.jdbc.core.JdbcTemplate;
import org.springframework.stereotype.Service;
import org.springframework.transaction.annotation.Transactional;

@SpringBootApplication
public class TransactionDemo {
    public static void main(String[] args) {
        SpringApplication.run(TransactionDemo.class, args);
    }

    @Bean
    ApplicationRunner demo(JdbcTemplate jdbc, PaymentService service) {
        return args -> {
            jdbc.execute("create table payments (id int primary key)");
            try { service.insertThenFail(); }
            catch (IllegalStateException expected) { /* inspect rollback */ }
            System.out.println("rows=" +
                jdbc.queryForObject("select count(*) from payments", Integer.class));
        };
    }
}

@Service
class PaymentService {
    private final JdbcTemplate jdbc;
    PaymentService(JdbcTemplate jdbc) { this.jdbc = jdbc; }

    @Transactional
    public void insertThenFail() {
        jdbc.update("insert into payments(id) values (1)");
        throw new IllegalStateException("simulate failure");
    }
}

Expected application output: rows=0. The unchecked exception leaves the proxy, so the insert rolls back. Run the demo against a fresh in-memory H2 database.

Propagation, isolation, and failure traps

  • REQUIRED: join or create a transaction. REQUIRES_NEW suspends the outer one and uses another transaction; it may need another pool connection. NESTED uses savepoints when supported.
  • Self-invocation/private methods: move the transactional operation to another bean or use TransactionTemplate; do not assume an internal call is advised.
  • Exceptions: unchecked exceptions roll back by default; checked exceptions normally need rollbackFor unless the application changed the default. Swallowing an exception can cause commit.
  • Isolation: database default varies. Higher isolation may prevent anomalies but adds locks/retries. Test behavior with the actual database.
  • Async calls: thread-bound transactions do not automatically follow @Async work. Keep the transaction short and avoid network calls inside it.

Common follow-up interview questions and answers

  • Why does this.save() not start a transaction? It calls the target directly, bypassing the proxy.
  • Will a checked exception roll back? Not by the usual default; configure the rollback rule if required.
  • Can an inner REQUIRES_NEW commit while the outer rolls back? Yes; it is an independent transaction.
  • Does @Transactional make a distributed transaction? No. Use an explicit distributed consistency pattern such as outbox or saga.

Interview-ready answer

@Transactional is usually implemented by a Spring proxy around an externally invoked bean method. The proxy obtains a transaction, calls the method, and commits or rolls back according to rollback rules. I watch for self-invocation, non-intercepted methods, caught or checked exceptions, propagation choices, and the database's actual isolation. I keep transactions short and verify rollback with an integration test.
