Question: How do you design an immutable Java class, and why does immutability help with thread safety?

Short answer

An immutable object cannot change after construction. Make the class difficult or impossible to extend, keep fields private and final, initialize them in the constructor, provide no setters, validate inputs, and make defensive copies of mutable objects. Immutability removes shared state changes, so multiple threads can safely read the same object without locks.

Rules for an immutable class

  1. Declare the class final, or carefully control subclassing.
  2. Make state private final.
  3. Set every field during construction.
  4. Do not expose setters or mutable internal state.
  5. Defensively copy mutable input and output such as Date, arrays, and collections.
  6. Validate invariants before publishing the object.

Runnable example

import java.util.*;

public final class UserProfile {
    private final String name;
    private final List<String> roles;

    public UserProfile(String name, List<String> roles) {
        this.name = Objects.requireNonNull(name);
        this.roles = List.copyOf(roles);
    }

    public String name() { return name; }
    public List<String> roles() { return roles; }
}

class ImmutableDemo {
    public static void main(String[] args) {
        List<String> input = new ArrayList<>(List.of("USER"));
        UserProfile profile = new UserProfile("Maya", input);
        input.add("ADMIN");

        System.out.println(profile.name());
        System.out.println(profile.roles());
        try {
            profile.roles().add("ADMIN");
        } catch (UnsupportedOperationException ex) {
            System.out.println("roles cannot be changed");
        }
    }
}

Expected output:

Maya
[USER]
roles cannot be changed

Internal working and thread safety

Threads can safely share an immutable object because its fields never change after construction. A properly constructed object also benefits from the Java Memory Model's final-field guarantees: other threads can reliably observe final fields after safe publication. Immutability does not automatically make referenced objects safe; the whole object graph must be immutable or safely wrapped.

Edge cases

  • Collections.unmodifiableList prevents mutation through that view but does not copy the original list. Changes to the original list may still be visible.
  • A final reference cannot be reassigned, but the referenced object can still be mutable.
  • Returning an internal array directly breaks immutability. Return a copy.
  • Lazy caching inside an immutable object needs safe publication or synchronization.
  • Serialization, reflection, and deserialization can bypass normal constructors, so sensitive classes may need extra protection.

Real-world examples

Value objects such as money, coordinates, configuration snapshots, request objects, cache keys, and Java records are good candidates. Immutable configuration can be shared by request threads without defensive locking.

Follow-up questions

  • Are records always immutable? No. A record's fields are final, but a field may refer to a mutable list or object. Use defensive copies.
  • Why use a builder? A builder helps create complex immutable objects while keeping the final object itself unchangeable.
  • Is immutability faster? It can reduce locking and simplify caching, but defensive copying may add allocation cost.

Interview-ready answer

An immutable class is fully initialized in its constructor and never changes afterward. I use private final fields, no setters, validation, defensive copies, and controlled inheritance. Since threads only read stable state, immutable objects can be shared without locks, are safe as map keys, and are easier to reason about.

Deep immutability and defensive copying

Immutability is a property of the reachable state, not just the top-level reference. A final List<String> prevents replacing the list reference, but it does not prevent callers from adding to the list. Copy mutable inputs on the way in and return an immutable copy or a copy on the way out.

import java.util.*;

public final class Schedule {
    private final Date start;
    private final List<String> attendees;

    public Schedule(Date start, List<String> attendees) {
        this.start = new Date(start.getTime());
        this.attendees = List.copyOf(attendees);
    }

    public Date start() { return new Date(start.getTime()); }
    public List<String> attendees() { return attendees; }
}

List.copyOf also rejects null elements and returns an unmodifiable list. If elements themselves are mutable, copy or make those elements immutable too.

Safe publication and the Java Memory Model

Final fields receive special initialization guarantees when the constructor completes normally and the object is not allowed to escape during construction. For shared mutable objects, use a safe publication mechanism such as a final field of another safely published object, a volatile reference, a lock, a concurrent collection, or a static initialization boundary. Immutability reduces the number of visibility and race problems, but it does not fix unsafe publication of a partially constructed object.

Builder and validation example

public final class ConnectionConfig {
    private final String host;
    private final int port;

    private ConnectionConfig(Builder builder) {
        if (builder.port < 1 || builder.port > 65535) {
            throw new IllegalArgumentException("invalid port");
        }
        host = java.util.Objects.requireNonNull(builder.host);
        port = builder.port;
    }

    public static class Builder {
        private String host;
        private int port = 443;
        public Builder host(String value) { host = value; return this; }
        public Builder port(int value) { port = value; return this; }
        public ConnectionConfig build() { return new ConnectionConfig(this); }
    }
}

The builder is mutable while constructing the value; the resulting configuration is immutable after build. This is useful when there are many optional fields or cross-field validation rules.

Common advanced pitfalls

  • Do not let this escape from a constructor through a listener, thread, callback, or overridable method.
  • Do not assume Collections.unmodifiableList is a snapshot; it can still reflect changes to the original list.
  • Do not use mutable objects as keys in a hash map unless their equality state is stable for the key's lifetime.
  • Lazy memoization changes internal state. Use a safe holder, volatile field, or synchronization if multiple threads can initialize it.
  • Serialization frameworks and reflection may bypass normal invariants; validate at deserialization boundaries.

Additional follow-up answers

  • Why does immutability help caching? A stable object can be safely reused and its hash code can remain stable for the lifetime of a map key.
  • Is StringBuilder immutable? No; it is intentionally mutable and is not a thread-safe value object.
  • Can an immutable object contain a cache? Yes, but the cache is internal mutable state and must be safely synchronized or made safely visible.
