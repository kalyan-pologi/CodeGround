Question: How would you handle database schema migrations, versioning, backward compatibility, and data consistency during zero-downtime deployments?

Short answer

Use versioned migrations and an expand → migrate → contract rollout. First make an additive schema change that both old and new application versions can tolerate. Deploy code that can read old/new representations and write consistently, backfill data safely, switch reads, and only later remove the old column/constraint. Keep migration history in source control and test upgrades against production-like data.

Rollout, step by step

  1. Expand: add a nullable/new column or table and indexes with online/concurrent techniques supported by the database. Do not rename/drop a column while old pods still use it.
  2. Bridge: deploy code that reads the new value when present and falls back to old data; dual-write or use a controlled database mechanism while both versions run.
  3. Backfill: process rows in small resumable batches, record progress, and throttle against database load. Make each batch idempotent.
  4. Switch: verify counts and business invariants, move reads to the new shape, stop old writes, and monitor error/lag metrics.
  5. Contract: after all old versions and rollback windows are gone, enforce NOT NULL or uniqueness and drop old schema in a later migration.

Runnable Java 17 compatibility example

Save as SchemaBridgeDemo.java. It illustrates how a reader can handle rows before and after a backfill.

public class SchemaBridgeDemo {
    record Row(String oldName, String newName) {}

    static String displayName(Row row) {
        return row.newName() != null ? row.newName() : row.oldName();
    }

    public static void main(String[] args) {
        System.out.println(displayName(new Row("Maya", null)));
        System.out.println(displayName(new Row("Maya", "Maya P.")));
    }
}

Expected output:

Maya
Maya P.

In practice, put numbered Flyway/Liquibase migrations in source control and test each application version against the transitional schema. A sample additive SQL migration is ALTER TABLE users ADD COLUMN display_name text;; a later version can backfill and eventually enforce a constraint.

Real-world edge cases

DDL locking and transaction behavior vary by database; a seemingly small ALTER TABLE can block writes. Build large indexes with the database's online option where supported. Dual-write can fail halfway, so define reconciliation and monitoring. Rollback of code after a destructive migration may be impossible, which is why contract happens later. Unique constraints should be introduced only after duplicates are resolved. Do not run expensive backfills synchronously in every pod's startup path.

Common follow-up interview questions and answers

  • Why not rename a column in one deploy? Old and new pods may run simultaneously and expect different names.
  • What makes a backfill safe? Small, restartable, idempotent batches with progress and load limits.
  • Can every schema migration be rolled back? No; data loss or a long backfill can make reversal impractical. Design forward fixes.
  • When add NOT NULL? After every row is populated and all writers guarantee the new field.

Interview-ready answer

I use versioned migrations and an expand–migrate–contract sequence. I add compatible schema first, deploy code that tolerates both shapes, backfill in resumable batches, verify invariants, switch reads, and drop old schema only after older application versions are gone. I test mixed-version deployment and rollback behavior, because zero downtime is mainly a compatibility problem.
