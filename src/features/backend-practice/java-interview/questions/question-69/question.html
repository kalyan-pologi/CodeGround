Question: How does Spring Boot auto-configure a DataSource, and how would you diagnose connection-pool exhaustion?

Short answer

Boot detects a JDBC driver and datasource properties, then creates a pooled DataSource when no user datasource is present. Pool exhaustion means requests are waiting for connections, often because transactions are slow, connections leak, the pool is undersized, or the database is saturated.

First checks

  1. Active, idle, pending, acquisition-time, and timeout metrics.
  2. Transaction duration and code paths that hold connections while calling remote services.
  3. Slow queries, database locks, server connection limits, and leak detection.
  4. Pool size versus database capacity; increasing it blindly can worsen overload.
I would identify whether connections are unavailable, held too long, or rejected by the database before changing pool size.

Safe tuning

Set acquisition and query timeouts so waiting is bounded. Size the pool from database capacity and measured transaction time, not from request-thread count. Keep transactions short and never hold a database connection while waiting on a remote HTTP call. Monitor leak detection warnings and close resources through framework-managed templates.

Follow-up questions

  • Why can increasing the pool make the database slower?
  • Which metric separates pool wait from SQL time?
  • How do read and write pools change the design?

Minimal pool configuration

spring.datasource.hikari.maximum-pool-size=20
spring.datasource.hikari.connection-timeout=2000
spring.datasource.hikari.leak-detection-threshold=5000

Choose values from database capacity and measured transaction time. Treat leak detection as a diagnostic aid, not a substitute for closing resources.

Interview-ready answer

Boot creates a pooled DataSource when a driver and properties are present and no user datasource replaces it. For exhaustion I inspect active, idle, pending, acquisition, transaction, query, lock, and database-capacity metrics before tuning the pool.
