Question: How would you design production-ready REST APIs using Spring Boot, including request validation, exception handling, DTOs, pagination, API versioning, and response standardization?

Short answer

Define a clear resource contract first: URLs, methods, request/response DTOs, status codes, and error shape. Validate at the boundary, keep persistence entities out of public responses, centralize exception mapping, bound pagination, version only when compatibility requires it, and document the API with examples and tests. Security, idempotency, timeouts, and observability are part of “production-ready,” not optional extras.

Design, step by step

  1. Use resource-oriented paths such as /api/v1/users; POST creates, GET reads, PUT replaces, PATCH partially changes, and DELETE removes.
  2. Use DTOs to keep API shape independent of database entities. Apply Bean Validation (@Valid, @NotBlank, etc.) and domain validation in the service.
  3. Return meaningful HTTP statuses and a consistent error body, for example Spring ProblemDetail with a stable application error code. Do not return stack traces or secrets.
  4. Require bounded size, deterministic ordering, and a stable cursor or page number. Offset pagination can degrade for large pages and shift under concurrent inserts.
  5. Use additive backward-compatible changes when possible; version breaking contracts deliberately and publish a deprecation plan.

Runnable Spring Boot example

In a Spring Boot project with spring-boot-starter-web and spring-boot-starter-validation, place this in src/main/java/demo/UserApi.java. It uses in-memory data only to demonstrate the HTTP contract.

package demo;

import java.net.URI;
import java.util.List;
import java.util.concurrent.CopyOnWriteArrayList;
import java.util.concurrent.atomic.AtomicLong;
import jakarta.validation.Valid;
import jakarta.validation.constraints.NotBlank;
import org.springframework.boot.SpringApplication;
import org.springframework.boot.autoconfigure.SpringBootApplication;
import org.springframework.http.ResponseEntity;
import org.springframework.web.bind.annotation.*;

@SpringBootApplication
public class UserApi {
    public static void main(String[] args) { SpringApplication.run(UserApi.class, args); }
}

record CreateUser(@NotBlank String name) {}
record UserDto(long id, String name) {}

@RestController
@RequestMapping("/api/v1/users")
class UserController {
    private final AtomicLong ids = new AtomicLong();
    private final List<UserDto> users = new CopyOnWriteArrayList<>();

    @PostMapping
    ResponseEntity<UserDto> create(@Valid @RequestBody CreateUser request) {
        UserDto created = new UserDto(ids.incrementAndGet(), request.name());
        users.add(created);
        return ResponseEntity.created(URI.create("/api/v1/users/" + created.id()))
            .body(created);
    }

    @GetMapping
    List<UserDto> list(@RequestParam(defaultValue = "0") int page,
                        @RequestParam(defaultValue = "20") int size) {
        if (page < 0 || size < 1 || size > 100)
            throw new IllegalArgumentException("invalid page or size");
        long start = (long) page * size;
        if (start >= users.size()) return List.of();
        return users.subList((int) start, (int) Math.min(start + size, users.size()));
    }
}

Expected response: POST /api/v1/users with {"name":"Maya"} returns HTTP 201, Location: /api/v1/users/1, and {"id":1,"name":"Maya"}; GET /api/v1/users?page=0&size=20 returns a one-item JSON array. Framework log lines vary.

For production, move state to a service/database, add @RestControllerAdvice for validation and domain errors, and use a stable sortable field or cursor. A real GET /{id} should return 404 when absent.

Edge cases and real-world concerns

Do not trust client-supplied IDs or authorization claims. Validate maximum string length and pagination size to prevent resource abuse. Use idempotency keys for non-repeatable payment-like POSTs. Avoid exposing ORM entities because lazy fields, cycles, and internal columns can leak. Add request IDs, metrics, tracing, rate limits, OpenAPI documentation, and integration tests for error responses. Choose versioning via path/header/media type consistently, and avoid breaking old clients without a migration window.

Common follow-up interview questions and answers

  • Why DTOs? They stabilize the public contract and prevent persistence/internal fields from leaking.
  • Which status for a created resource? Usually 201 with a Location header.
  • Offset versus cursor pagination? Offset is simple; cursor/keyset is often better for large changing datasets when backed by a suitable index.
  • Where does validation live? Boundary validation checks shape; the service enforces business rules and authorization.

Interview-ready answer

I design the API contract before coding: resource paths, method semantics, DTOs, validation, statuses, and a consistent error format. In Spring Boot I validate requests at the controller, keep business rules and authorization in services, centralize exceptions, cap pagination, and version breaking changes deliberately. I test success and error cases, document the contract, and add observability and idempotency where retries matter.
