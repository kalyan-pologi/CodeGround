Question: How does Spring Boot manage dependency versions with its BOM, and what are the differences between a normal JAR and an executable fat JAR?

Short answer

Spring Boot's dependency-management BOM aligns versions tested together, so applications normally declare dependencies without repeating versions. A normal JAR contains application classes; an executable Boot JAR contains application classes, nested dependencies, and a launcher that builds the runtime classpath.

Production checks

  • Inspect the resolved dependency tree for conflicts and overrides.
  • Use reproducible builds and scan the packaged artifact.
  • Do not assume a dependency version override is compatible with the Boot release.
  • Keep build metadata and runtime Java version aligned.
The BOM reduces version drift; the executable JAR changes packaging and launch behavior but does not remove the need for dependency and vulnerability management.

Build and runtime diagnosis

When a method exists at compile time but not at runtime, inspect the resolved tree and packaged JAR for version skew. Compare the Java runtime used by the build and deployment. Reproducible dependency locking, SBOM generation, and vulnerability scanning should run before the artifact is promoted.

Minimal verification commands

Use the equivalent Gradle dependency report when applicable, then scan the exact packaged artifact that will be deployed.

Interview-ready answer

The Boot BOM aligns tested dependency versions, while an executable JAR packages application classes, dependencies, and a launcher. I inspect the resolved tree and artifact for version skew, runtime mismatch, and vulnerabilities before release.
