Question: Implement a bounded ThreadPoolExecutor with custom thread-pool configuration, queue capacity, rejection handling, and graceful shutdown.

Short answer

Configure a finite number of workers and a finite queue, then make overload visible through a rejection policy. A custom thread factory names workers for debugging. On shutdown, reject new submissions, let queued work finish, wait for a deadline, and interrupt as a last resort. Handle task failures and interrupted work explicitly; do not silently discard important tasks.

Runnable Java 17 program

Save as BoundedExecutorDemo.java. The first task occupies the worker, the second is queued, and the third is rejected.

import java.util.concurrent.*;
import java.util.concurrent.atomic.AtomicInteger;

public class BoundedExecutorDemo {
    public static void main(String[] args) throws InterruptedException {
        AtomicInteger threadIds = new AtomicInteger();
        AtomicInteger completed = new AtomicInteger();
        AtomicInteger rejected = new AtomicInteger();
        CountDownLatch started = new CountDownLatch(1);
        CountDownLatch release = new CountDownLatch(1);

        ThreadFactory namedThreads = task -> {
            Thread thread = new Thread(task,
                "orders-worker-" + threadIds.incrementAndGet());
            thread.setDaemon(false);
            return thread;
        };
        RejectedExecutionHandler reject = (task, executor) -> {
            rejected.incrementAndGet();
            throw new RejectedExecutionException("queue full");
        };
        ThreadPoolExecutor pool = new ThreadPoolExecutor(
            1, 1, 0, TimeUnit.SECONDS,
            new ArrayBlockingQueue<>(1), namedThreads, reject);

        pool.execute(() -> {
            started.countDown();
            try {
                release.await();
                completed.incrementAndGet();
            } catch (InterruptedException e) {
                Thread.currentThread().interrupt();
            }
        });
        started.await();
        pool.execute(completed::incrementAndGet);
        try { pool.execute(completed::incrementAndGet); }
        catch (RejectedExecutionException expected) { /* overload is visible */ }

        release.countDown();
        pool.shutdown();
        if (!pool.awaitTermination(5, TimeUnit.SECONDS)) {
            pool.shutdownNow();
            if (!pool.awaitTermination(5, TimeUnit.SECONDS))
                throw new IllegalStateException("workers did not stop");
        }
        System.out.println("completed=" + completed.get());
        System.out.println("rejected=" + rejected.get());
        System.out.println("terminated=" + pool.isTerminated());
    }
}

Expected output:

completed=2
rejected=1
terminated=true

Internal working and production choices

The executor grows to core size, then queues; when the queue is full it can grow toward max; when both are full it invokes the rejection handler. An unbounded queue usually prevents growth beyond core size and can exhaust memory. AbortPolicy or a custom rejection can return 429/503; CallerRunsPolicy creates backpressure by making the submitter do the work but can block a request thread. Size workers against CPU, blocking time, and downstream capacity; a 100-thread pool cannot increase a 10-connection database's throughput.

Real-world edge cases and follow-ups

shutdown() drains accepted work; shutdownNow() interrupts workers and returns tasks that never started. A task ignoring interrupts may never stop. execute() can report an uncaught exception through the worker; submit() captures it in a Future that must be checked. Monitor queue length, active workers, queue wait, rejection count, and shutdown time.

  • Why bound the queue? To cap memory and make overload explicit.
  • What if a task hangs? Add task/downstream timeouts and cancellation; pool shutdown alone cannot fix uninterruptible IO.
  • Why name threads? Thread dumps and logs become much easier to interpret.
  • Does rejecting mean data loss? It can; durable work should be accepted only after persistence or sent to a reliable queue.

Interview-ready answer

I create a ThreadPoolExecutor with explicit core/max workers, a bounded queue, named threads, and a rejection policy mapped to overload handling. I measure queue wait, active threads, and rejections against downstream limits. On shutdown I stop accepting tasks, wait for accepted work, then interrupt if needed and report unfinished tasks. I never use an unbounded queue for critical burst traffic.
