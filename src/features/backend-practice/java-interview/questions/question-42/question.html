Question: Kafka consumer lag keeps increasing even though all consumers are running. How would you diagnose partition limitations, processing bottlenecks, database latency, and consumer configurations?

Short answer

Lag grows when records arrive faster than the group can finish and commit them. “Running” does not mean productive: consumers may be idle because there are too few partitions, blocked on a database, retrying poison messages, rebalancing repeatedly, or committing slowly. Compare per-partition incoming rate, processing rate, lag, and dependency latency before adding consumers.

Diagnosis, step by step

  1. Inspect lag by partition, not only a topic total. One hot partition/key can dominate while others are idle.
  2. Compare partitions to active consumers in the group. More consumers than partitions do not increase parallelism for that topic/group.
  3. Measure handler time, batch size, DB pool wait, query latency, downstream API latency, and retries. A slow dependency often explains low CPU and rising lag.
  4. Inspect poll cadence, max.poll.interval.ms, heartbeat/rebalance events, commit failures, and consumer errors. Long processing between polls can trigger reassignment and duplicate work.
  5. Optimize the bottleneck, use bounded worker concurrency with correct per-partition ordering, add partitions if key/order requirements allow, then retest under production-like input.

Runnable Java 17 capacity illustration

Save as LagBudgetDemo.java. This models one interval of arrival and processing; it is not a Kafka metrics client.

public class LagBudgetDemo {
    public static void main(String[] args) {
        int oldLag = 100;
        int produced = 500;
        int processed = 300;
        int newLag = Math.max(0, oldLag + produced - processed);
        System.out.println("newLag=" + newLag);
        System.out.println("growing=" + (produced > processed));
    }
}

Expected output:

newLag=300
growing=true

For real Kafka metrics, be precise about whether you compare log-end offset with committed offset or actual completed processing; async workers can make committed position misleading.

Real-world edge cases

Increasing partitions can change key-to-partition routing for future records and affect per-key ordering assumptions. Increasing max.poll.records may improve batch efficiency but can make processing exceed poll intervals. Moving work to a thread pool requires a safe offset-commit strategy: do not commit past unfinished records. If the database can process only 200 writes/s, more consumers may just exhaust its connections. A retry loop on one bad record can block a partition; use bounded retries and a DLT policy.

Common follow-up interview questions and answers

  • Why are consumers idle? A group cannot assign one partition to more than one active member at a time.
  • Why does lag rise with low CPU? Consumers may be waiting on database connections or remote IO.
  • What does a rebalance do to lag? It pauses/reassigns consumption and can repeat uncommitted work.
  • Should we add partitions first? Only after confirming partition count is the bottleneck and understanding ordering/routing effects.

Interview-ready answer

I break lag down by partition and compare arrival rate with completed processing rate. Then I check active assignments, hot keys, handler timing, database pool/queries, retry loops, and rebalances or poll-timeout settings. I fix the limiting resource before increasing consumers; if partition count is truly limiting, I plan a partition increase with ordering implications and load-test the result.
