Question: What is SpringFactoriesLoader, how did auto-configuration imports evolve, and how does Spring Boot discover configuration classes?

Short answer

Spring's factory loading mechanism reads provider metadata from dependencies and instantiates declared implementations. Older Boot versions used META-INF/spring.factories for auto-configuration; modern Boot uses an auto-configuration imports metadata file while retaining factory loading for other extension points.

Why it matters

Auto-configuration is discovered from dependency metadata, then filtered by conditions such as class presence, properties, bean absence, and web application type. Inspect the condition evaluation report when a configuration unexpectedly matches or backs off.

Common mistakes

  • Treating every class on the classpath as an active bean.
  • Debugging only the final exception instead of the condition report.
  • Using internal metadata mechanisms as application APIs.
The key idea is metadata-driven discovery followed by conditional evaluation; classpath presence alone does not guarantee that a bean is created.

How to debug auto-configuration

  1. Run with the condition evaluation report enabled.
  2. Find the positive and negative matches for the configuration.
  3. Check missing classes, properties, bean definitions, and application type.
  4. Prefer a documented customization or replacement bean over copying internal auto-configuration.

Production example

A database auto-configuration can back off because an application-defined DataSource exists, while a missing driver can prevent it from matching at all. The report tells you which condition changed instead of requiring guesswork from the final bean error.
