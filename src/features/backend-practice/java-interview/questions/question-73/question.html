Question: How does Actuator work internally, which endpoints should be exposed, and why is Spring Boot suitable for cloud-native applications?

Short answer

Actuator contributes management endpoints through auto-configuration and exposes health, metrics, mappings, and other operational views according to configuration and security rules. Spring Boot suits cloud-native systems through externalized configuration, stateless services, health probes, metrics, fast packaging, and embedded servers.

Safe exposure

  • Expose only health and required metrics publicly.
  • Protect environment, beans, mappings, and shutdown-capable endpoints.
  • Separate liveness from readiness so dependency failures do not cause restart loops.
  • Export metrics and traces to the platform's observability system.
Actuator is an operational interface, not a public debugging API. Its endpoints must be deliberately exposed and secured.

Readiness versus liveness

Liveness answers whether the process should be restarted; readiness answers whether it should receive traffic. A temporary database outage should usually remove an instance from readiness rather than create a restart loop. Metrics should include request latency, error rate, pool saturation, JVM memory, and dependency health.

Minimal Actuator configuration

management.endpoints.web.exposure.include=health,info,prometheus
management.endpoint.health.probes.enabled=true

Put sensitive management endpoints on a protected network or security boundary and avoid exposing environment or bean details to the public internet.

Interview-ready answer

Actuator contributes secured operational endpoints through auto-configuration. I expose only what the platform needs, separate liveness from readiness, export metrics and traces, and use externalized configuration and stateless processes to support cloud-native deployment.
