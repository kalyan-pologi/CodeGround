Question: Design a Kafka-based order processing workflow with retries, dead-letter topics, idempotent consumers, and database consistency.

Short answer

Publish order events from a transactional outbox so a committed order change is not lost between the database and Kafka. Key records by order ID for per-order partition ordering. A consumer records each event ID under a unique constraint and applies a legal order-state transition in the same local database transaction. Commit the Kafka offset after that transaction succeeds; bounded transient retries and a monitored dead-letter topic handle failures. Replay must remain idempotent.

Workflow, step by step

  1. The API stores Order(PENDING) and an OrderCreated outbox row in one transaction. A relay publishes to the orders topic with orderId as key.
  2. An inventory consumer reads the event, inserts (consumer_name,event_id) under a unique constraint, and reserves stock/updates order state in the same DB transaction. A duplicate ID becomes a no-op.
  3. On success, the consumer commits the DB transaction, then acknowledges the Kafka record. A crash before acknowledgment can replay it, but the dedupe row prevents a second business update.
  4. Temporary DB/API failures use bounded retries with backoff. Invalid or exhausted records go to a DLT with original topic, partition, offset, event ID, schema version, and error metadata.
  5. Operators fix the cause and replay DLT events at a controlled rate. Track stuck orders, lag, retry count, DLT volume, and reconciliation state.

Runnable Java 17 state-transition model

Save as OrderEventDemo.java. It demonstrates duplicate-event handling; the Spring/Kafka version below moves both operations into a database transaction.

import java.util.HashSet;
import java.util.Set;

public class OrderEventDemo {
    static final Set<String> processed = new HashSet<>();
    static String status = "PENDING";

    static void handle(String eventId) {
        if (!processed.add(eventId)) return;
        if (!status.equals("PENDING")) throw new IllegalStateException();
        status = "RESERVED";
    }

    public static void main(String[] args) {
        handle("event-1");
        handle("event-1");
        System.out.println("status=" + status);
        System.out.println("processedIds=" + processed.size());
    }
}

Expected output:

status=RESERVED
processedIds=1

Project-ready Spring Kafka + PostgreSQL processing core

In a Spring Boot project with Spring Kafka, JDBC, and PostgreSQL, create tables with PRIMARY KEY (consumer_name, event_id) for processed_events, an orders(id,status) table, and an order_outbox table. Configure JSON deserialization, manual acknowledgment, and auto-commit disabled for the listener container:

record OrderEvent(String eventId, String orderId) {}

@Component
class OrderListener {
    private final OrderHandler handler;
    OrderListener(OrderHandler handler) { this.handler = handler; }

    @KafkaListener(topics = "orders", groupId = "inventory")
    void receive(OrderEvent event, Acknowledgment ack) {
        handler.reserve(event); // Separate bean: transaction commits on return.
        ack.acknowledge();       // Only after DB commit.
    }
}

@Service
class OrderHandler {
    private final JdbcTemplate jdbc;
    OrderHandler(JdbcTemplate jdbc) { this.jdbc = jdbc; }

    @Transactional
    public void reserve(OrderEvent event) {
        int claimed = jdbc.update(
            "insert into processed_events(consumer_name,event_id) values(?,?) "
          + "on conflict(consumer_name,event_id) do nothing",
            "inventory", event.eventId());
        if (claimed == 0) return; // Replay of a committed event.
        int changed = jdbc.update(
            "update orders set status='RESERVED' where id=? and status='PENDING'",
            event.orderId());
        if (changed != 1) throw new IllegalStateException("invalid order state");
        jdbc.update(
            "insert into order_outbox(event_id,order_id,event_type) values(?,?,?)",
            java.util.UUID.randomUUID().toString(), event.orderId(),
            "INVENTORY_RESERVED");
    }
}

Expected behavior: the first valid event changes one order from PENDING to RESERVED and writes one outbox event; replay leaves both unchanged. If state validation fails, the transaction rolls back the processed-event claim too, allowing retry. Configure DefaultErrorHandler with bounded backoff and a DeadLetterPublishingRecoverer; acknowledge a recovered record only after confirmed DLT publication according to container mode. The actual topic names and schemas must match the application.

Real-world edge cases and follow-up questions

Retries on another topic can break per-order ordering when newer original-topic events overtake an older failed event. Validate event schema versions and preserve original bytes for deserialization errors. A DB transaction plus offset acknowledgment is at-least-once at the Kafka boundary, so deduplication is essential. Kafka producer transactions do not automatically include PostgreSQL; an outbox addresses that gap. DLT records need ownership, alerts, and a safe replay procedure.

  • Why key by order ID? Related events go to one partition and retain per-order order while routing remains stable.
  • When commit the offset? After the local DB transaction succeeds or after a confirmed durable recovery handoff.
  • What if the consumer crashes after DB commit? Kafka replays; the unique event ID makes the second attempt a no-op.
  • What if DLT publish fails? Do not silently advance the source offset; retry or stop according to the recovery policy.

Interview-ready answer

I use a transactional outbox to publish order changes, key Kafka records by order ID, and process each event in a local DB transaction that inserts a unique processed-event ID and performs a conditional state change. I acknowledge only after commit, so replay is harmless. I use bounded retries for transient failures, a monitored DLT for poison messages, and controlled idempotent replay; I do not claim Kafka offsets alone make the database exactly-once.
