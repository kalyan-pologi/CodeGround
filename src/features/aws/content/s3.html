S3

Store report PDFs safely, retrieve them predictably, and separate file bytes from relational metadata.

01 · What & Why

Amazon Simple Storage Service stores objects in buckets. Each object has a key, bytes, and metadata. It is a durable object store for reports and images, not a relational database or a normal shared filesystem. A database can keep the object key and business status while S3 holds the large file.

02 · How it works

The application signs a request to a bucket and key. S3 checks IAM and bucket policies, writes the object, and returns success or an error. Reads use GetObject or a presigned URL. S3 provides strong read after write consistency for object operations, but an application still has to coordinate S3 writes with its own database transaction.

03 · Reidy.AI usage

Example deployment pattern: The Appraisal Service generates appraisals/{reportId}.pdf in a private reports bucket. The Report Service reads it later. RDS stores the report ID, object key, and status. Prefixes can separate appraisals from unrelated files and make IAM policies narrower.

Upload and download flows

  1. React requests an appraisal and Spring Boot generates the PDF.
  2. The ECS task uploads it to private S3 using its task role.
  3. After S3 succeeds, the service stores the object key and marks the RDS record ready.
  4. For download, Spring Boot authorizes the user and returns a five-minute presigned URL.
  5. The browser downloads directly from S3, avoiding API server bandwidth.

04 · Implementation

Grant the ECS task role s3:PutObject only on arn:aws:s3:::reidy-reports/appraisals/*. Set the region and bucket through configuration. Block public access on the bucket and choose server side encryption. Add the AWS SDK v2 S3 module through your Maven BOM.

<dependency> <groupId>software.amazon.awssdk</groupId> <artifactId>s3</artifactId> </dependency>
@Service
class ReportObjectStore {
    private final S3Client s3;
    private final String bucket;

    ReportObjectStore(S3Client s3,
            @Value("${app.reports.bucket}") String bucket) {
        this.s3 = s3;
        this.bucket = bucket;
    }

    String upload(String reportId, Path pdf) {
        String key = "appraisals/" + reportId + ".pdf";
        s3.putObject(PutObjectRequest.builder()
            .bucket(bucket).key(key)
            .contentType("application/pdf").build(),
            RequestBody.fromFile(pdf));
        return key;
    }
}

For browser downloads, issue a short lived presigned GetObject URL after checking that the user may access that report. Do not store a presigned URL as the permanent database value. Configure S3Presigner with the same region and role-based provider, and keep the duration short because the URL is a bearer capability.

GetObjectPresignRequest.builder()
    .signatureDuration(Duration.ofMinutes(5))
    .getObjectRequest(getRequest)
    .build();

07 · Follow-up questions

  • Bucket versus key? The bucket is a container; the key identifies an object within it.
  • What is a presigned URL? A time limited signed request for one object operation.
  • Can S3 join a database transaction? No; design compensation or reconciliation.
  • Why use lifecycle rules? To transition or expire objects according to retention needs.
  • What if the object uses KMS? The caller may need the relevant KMS permissions in addition to S3 access.

08 · Top 5 interview questions

  1. What is S3?

    It is object storage. I use it for PDFs and other files, while keeping business records and object keys in RDS.

  2. How do you secure a report bucket?

    Block public access, encrypt objects, and give each service narrowly scoped role permissions.

  3. How can a user download a private PDF?

    Authorize the user in the API, then return a short lived presigned URL or stream the object through the service.

  4. How do you handle failed uploads?

    Record a retryable status, use stable keys, and reconcile objects if the database step fails.

  5. Why not store PDFs in RDS?

    S3 is designed for object storage and independent file lifecycle; RDS is better for transactional metadata and queries.

10 · Quick revision notes

  • Bucket contains objects.
  • Object key identifies a file.
  • Keep buckets private by default.
  • Use task roles, not embedded keys.
  • Versioning helps recover changes.
  • Lifecycle rules manage retention.
  • Presigned URLs expire.
  • S3 and RDS need workflow coordination.

Interview answer depth

S3: Describe buckets, keys, object metadata, and the difference between object storage and a filesystem. Explain why report bytes belong in S3 while report state belongs in RDS.

Security: Mention Block Public Access, encryption, bucket policies, IAM roles, and KMS when customer-managed keys are used.

Presigned URLs: Explain that the API authorizes the user first, then creates a short-lived signed URL for one object. The URL is not a permanent credential.

Consistency: S3 success and an RDS transaction cannot share one ACID transaction. Use stable keys, retry states, and reconciliation for partial failure.

Scale: Stream large uploads, use multipart upload where needed, and avoid putting entire PDFs in JVM heap or database rows.
