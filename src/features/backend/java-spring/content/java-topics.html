Definitions and use cases for core Java concepts, from language fundamentals through JVM internals and modern language features.

Language Fundamentals

Variables

Named memory locations that store data values. Use case: storing user input, calculation results, configuration values.

Data Types

Define the type of data a variable can hold (int, double, boolean, char, etc.). Use case: ensuring type safety and memory optimization.

Operators

Symbols that perform operations on operands (+, -, *, /, %, ==, !=, etc.). Use case: mathematical calculations, comparisons, logical operations.

Control Statements

Direct program flow using if-else, switch, and loops. Use case: decision making, repetitive tasks, conditional execution.

Arrays

A collection of elements of the same type stored in contiguous memory. Use case: storing lists of data, matrix operations, bulk data processing.

Strings

A sequence of characters, immutable in Java. Use case: text processing, user interfaces, data manipulation.

Methods

Reusable blocks of code that perform specific tasks. Use case: code modularity, avoiding repetition, organizing functionality.

Regular Expressions

Pattern matching for string operations. Use case: data validation, text parsing, search and replace operations.

Date and Time API

Modern date/time handling via LocalDate, LocalTime, and LocalDateTime. Use case: date calculations, formatting, timezone handling.

Object-Oriented Programming

Classes

A blueprint for creating objects, encapsulating data and behavior. Use case: object-oriented design, modeling real-world entities.

Objects

Instances of classes with state and behavior. Use case: creating multiple instances, data encapsulation, real-world modeling.

Constructors

Special methods called when objects are created. Use case: object initialization, setting default values, parameter validation.

Inheritance

A mechanism where one class acquires the properties of another. Use case: code reusability, hierarchical relationships, polymorphism.

Polymorphism

The ability of objects to take multiple forms. Use case: method overriding, interface implementation, flexible code design.

Encapsulation

Hiding internal implementation details using access modifiers. Use case: data security, maintainable code, controlled access.

Abstraction

Hiding complex implementation details and showing only essential features. Use case: interface design, code simplification, modularity.

Interfaces

Contracts defining methods that implementing classes must provide. Use case: multiple inheritance, loose coupling, API design.

Abstract Classes

Classes that cannot be instantiated and may contain abstract methods. Use case: common base functionality, enforcing method implementation.

Packages

Namespaces that organize related classes and interfaces. Use case: code organization, avoiding naming conflicts, access control.

Inner Classes

Classes defined within other classes. Use case: logical grouping, accessing outer class members, event handling.

Static Members

Class-level variables and methods shared by all instances. Use case: utility methods, constants, factory methods, counters.

Final Keyword

Makes variables, methods, or classes unchangeable. Use case: constants, preventing inheritance, immutable objects.

Super Keyword

References parent class members and constructors. Use case: accessing parent methods, constructor chaining, method overriding.

This Keyword

References the current object instance. Use case: resolving naming conflicts, method chaining, constructor calls.

Access Modifiers

Control the visibility of classes, methods, and variables (public, private, protected, default). Use case: encapsulation, security, API design.

Method Overloading

Multiple methods with the same name but different parameters. Use case: flexible method usage, convenience methods, parameter variations.

Method Overriding

Redefining parent class methods in child classes. Use case: polymorphism, customizing inherited behavior, runtime method selection.

Wrapper Classes

Object representations of primitive types (Integer, Double, Boolean). Use case: collections usage, null values, utility methods.

Autoboxing/Unboxing

Automatic conversion between primitives and wrapper classes. Use case: seamless primitive-object integration, collections compatibility.

Enum

A special class representing a fixed set of constants. Use case: type-safe constants, switch statements, configuration options.

Immutable Objects

Objects whose state cannot be changed after creation. Use case: thread safety, hashmap keys, defensive programming, caching.

Unmodifiable Collections: List.copyOf(), Set.copyOf(), Map.copyOf(). Use case: defensive copying, immutable collections, thread safety.

Java 11 (2018, LTS)

String Methods: isBlank(), strip(), repeat(). Use case: string validation, whitespace handling, repetitive formatting.

HTTP Client (Standardized): Modern async HTTP requests replacing URLConnection. Use case: REST calls, microservice communication, cleaner HTTP handling.

Local Variable Syntax for Lambda: Use var in lambda parameters. Use case: lambda annotations, reduced verbosity, consistency with local variables.

Nest-based Access Control: Private access between nested classes without synthetic accessors. Use case: cleaner bytecode, internal class communication.

Java 12-13 (2019)

Switch Expressions (preview): Switch as an expression, not just a statement. Use case: cleaner conditional logic, functional-style code.

Text Blocks (preview): Multi-line strings without concatenation. Use case: SQL queries, JSON templates, HTML, embedded code blocks.

Records (preview): Immutable data carriers with automatic boilerplate (equals, hashCode, toString). Use case: DTOs, value objects, reducing verbosity.

Java 14 (2020)

Switch Expressions (standard): yield keyword for returning values from switch. Use case: functional expressions, cleaner pattern matching.

Records (standard in 16): Compact syntax for immutable value types with component accessors. Use case: data transfer, immutable domain objects.

Pattern Matching (preview): instanceof with type casting in one step. Use case: type-safe downcasting, visitor patterns.

NullPointerException Messages: Detailed messages showing which variable caused the exception. Use case: faster debugging.

Java 15 (2020)

Text Blocks (standard): Triple-quoted multi-line strings. Use case: SQL, JSON, embedded templates without escaping.

Records (second preview): Local record classes, sealed records. Use case: record-based encapsulation.

Hidden Classes: Runtime-generated classes not discoverable via reflection. Use case: bytecode frameworks, runtime generation.

Sealed Classes (preview): Restrict which classes can extend/implement. Use case: controlled hierarchies, domain modeling, exhaustive pattern matching.

Java 16 (2021)

Records (finalized): Final form with canonical constructor refinement. Use case: immutable data modeling, reducing boilerplate.

Pattern Matching (instanceof finalized): instanceof + cast combined. Use case: type narrowing without separate casts.

Sealed Classes (second preview): permits clause finalization. Use case: inheritance control.

Strongly Encapsulated JDK Internals: sun.misc.Unsafe and other internals no longer accessible. Use case: enforcing API contracts.

Java 17 (2021, LTS)

Sealed Classes (finalized): Full control over class hierarchies via permits clause. Use case: API design, domain modeling, exhaustive pattern matching.

Pattern Matching (switch preview): Pattern matching in switch expressions. Use case: powerful type and value-based dispatch.

Foreign Function & Memory API (preview): Safer access to native memory and functions. Use case: JNI replacement, off-heap memory, low-level operations.

Deprecation of Applet API: Legacy Applet classes removed. Use case: modernization, removing legacy code.

Java 18-20 (2022-2023)

Pattern Matching (switch finalized in 21): Full pattern matching in switch with guards. Use case: complex type-based logic, cleaner dispatch.

Record Patterns (preview): Destructuring records in patterns. Use case: extracting record fields in switch/if.

Virtual Threads (preview, Project Loom): Lightweight threads for high-concurrency applications. Use case: millions of concurrent tasks without thread pool overhead.

Structured Concurrency (preview): Parent-child task relationships, automatic cleanup. Use case: cancellation propagation, error handling in concurrent code.

Java 21 (2023, LTS)

Virtual Threads (finalized): Lightweight thread implementation improving scalability. Use case: high-throughput servers, reactive-like concurrency with blocking code.

Pattern Matching (finalized): instanceof and switch patterns, record patterns. Use case: exhaustive type handling, cleaner conditionals.

Record Patterns (finalized): Destructure records in patterns for field access. Use case: nested record unpacking, cleaner data extraction.

Generational ZGC: Low-latency garbage collector with generational support. Use case: applications requiring sub-millisecond pause times.

Unnamed Variables & Patterns: Use _ for unused variables. Use case: ignoring exception parameters, unused fields, cleaner code.

Structured Concurrency (finalized): Scope-based task management with automatic cancellation. Use case: reliable concurrent code, error propagation.

Common Exceptions: Java to Spring Boot

The same exception can have several causes. Read the first relevant application stack frame and the root cause before choosing a fix. Checked exceptions must be caught or declared; unchecked exceptions usually point to a broken input contract, invalid state, or programming mistake. Spring may wrap an underlying Java, JDBC, or Jackson exception.

Core Java Exceptions

  • NullPointerException: A missing request field, an uninitialized dependency, or an unexpected null result is used as an object. Check which reference is null and where it should have been validated or initialized.
  • IllegalArgumentException: A method receives a negative amount, blank ID, or unsupported option. Check the method contract and validate input at the boundary.
  • NumberFormatException: Text is blank, contains letters, or exceeds the target number type's range. Check the original value and expected numeric format. This is a subtype of IllegalArgumentException.
  • IllegalStateException: Code reuses a closed resource, runs an operation in the wrong workflow state, or collects duplicate map keys without a merge rule. Check the object's state and the operation's preconditions.
  • IndexOutOfBoundsException: Code reads an empty list, uses an invalid array index, or assumes a page contains an item. Check collection size before indexing.
  • NoSuchElementException: Optional.get() is called on an empty value, an iterator is exhausted, or an empty queue is read with remove(). Check whether absence is expected and handle it explicitly.
  • ClassCastException: Code casts to the wrong DTO or entity, uses a raw collection, or assumes a deserialized value has a particular type. Check the actual runtime type and remove unsafe casts.
  • UnsupportedOperationException: Code mutates an unmodifiable collection or calls an operation an implementation does not support. Check the API contract and choose a mutable copy or supported operation.
  • ConcurrentModificationException: Code structurally changes a collection during iteration, including from another thread. Check the iteration and mutation path; this can happen even in one thread.
  • ArithmeticException: Integer division uses zero, or BigDecimal.divide() needs a rounding rule. Check the divisor and the required precision policy.
  • DateTimeParseException: A date string has an invalid day, unexpected format, or missing component required by the formatter. Check the input and formatter together.

I/O and Serialization Exceptions

  • IOException (checked): A file read fails, a connection closes during transfer, or writing to a stream fails. Check the underlying cause, path or endpoint, and resource cleanup.
  • NoSuchFileException (checked): A path is wrong, the production working directory differs, or an expected mounted file is absent. Check the resolved absolute path and deployment configuration.
  • SQLException (checked): Raw JDBC encounters invalid SQL, a constraint violation, a connection failure, or a query timeout. Check the SQL state and vendor error; Spring data access often translates this exception.
  • InterruptedException (checked): A thread is interrupted during sleep(), a blocking queue operation, or shutdown. Propagate it when possible; otherwise restore the interrupt flag with Thread.currentThread().interrupt().
  • JsonProcessingException (Jackson, checked): Direct JSON parsing sees malformed text or an incompatible value, or object serialization fails. Check the input or object shape; Spring HTTP conversion may wrap the Jackson cause.
  • NotSerializableException (checked): Native Java object serialization encounters a class that does not implement Serializable. Check the object graph; this does not apply to ordinary JSON serialization.
  • ClassNotFoundException (checked): Class.forName() requests a missing class, a plugin is absent, or native Java deserialization cannot find a class. Check the requested name and runtime classpath; unlike NoClassDefFoundError, this comes from an explicit class lookup.

Spring MVC Request and Response Exceptions

  • HttpMessageNotReadableException: The request body is missing, JSON is malformed, or a JSON value cannot be converted to the target Java type. Inspect the request body and its nested Jackson cause.
  • MethodArgumentNotValidException: A @Valid request DTO violates constraints such as @NotBlank or @Size. Inspect field errors and return a clear 400 response.
  • HandlerMethodValidationException: Direct constraints on controller parameters or return values fail under Spring MVC method validation. Inspect parameter validation results; availability depends on the Spring version.
  • MethodArgumentTypeMismatchException: A path or query value cannot convert to a UUID, number, enum, or date. Check the supplied value and parameter type.
  • MissingServletRequestParameterException: A required @RequestParam is absent or supplied without a value. Check the API contract and caller's query string.
  • HttpRequestMethodNotSupportedException: A caller sends the wrong HTTP verb, such as POST to a GET route. Check the route mapping and client request.
  • HttpMediaTypeNotSupportedException: A request has an unsupported Content-Type or lacks a converter for its body type. Check the header and endpoint's consumes setting.
  • HttpMessageNotWritableException: Spring cannot serialize a response because of an unsupported type, bad object graph, or serialization failure. Inspect the nested cause and return DTOs with a controlled shape.
  • ResponseStatusException: Application code deliberately signals an HTTP status, such as 404 for a missing resource or 409 for a conflict. Check the business condition and keep the response message safe for clients.

Database, JPA, and Transaction Exceptions

  • DataIntegrityViolationException: An insert or update violates a unique key, foreign key, or NOT NULL constraint. Inspect the underlying constraint name and decide whether the conflict is a client error or an application bug.
  • ConstraintViolationException (Jakarta Validation): Service method validation or entity validation finds a value that violates a constraint. Inspect the property path and violation messages; this is different from the similarly named Hibernate database constraint exception.
  • EmptyResultDataAccessException: A query expecting at least one row, such as JdbcTemplate.queryForObject(), returns none. Check whether a missing row is expected and use an optional lookup when appropriate.
  • OptimisticLockingFailureException: Two requests update the same versioned row or code saves a stale entity. Check the version field and apply an explicit conflict or retry policy.
  • PessimisticLockingFailureException: A database lock cannot be acquired, or a deadlock or lock timeout is translated by Spring. Check transaction duration and lock order before retrying.
  • CannotGetJdbcConnectionException: The database is unavailable, connection settings are wrong, or the pool cannot supply a connection. Check database health, credentials, pool usage, and the root cause.
  • QueryTimeoutException: A query exceeds its configured time limit or is cancelled by the database. Check query plan, indexes, load, and timeout settings.
  • UnexpectedRollbackException: An inner operation marks a shared transaction rollback-only, but outer code still tries to commit. Find the earlier failure; catching it does not make that transaction safe to reuse.
  • LazyInitializationException (Hibernate): Code maps or serializes an unfetched relationship after the session closes. Fetch the data needed for a DTO inside the transaction and check query counts.

Security, Outbound HTTP, and Background Work

  • AuthenticationException (Spring Security): Credentials are invalid, expired, or cannot be authenticated. Check the authentication mechanism; the security filter chain often handles this before a controller runs.
  • AccessDeniedException (Spring Security): An authenticated user lacks a role or method permission. Check authorization rules and principal authorities; this differs from java.nio.file.AccessDeniedException.
  • HttpClientErrorException: A RestClient or RestTemplate call receives a 4xx response, such as 400, 404, or 429. Inspect the status and response body before deciding whether to retry.
  • HttpServerErrorException: An outbound HTTP call receives a 5xx response. Check the dependency's status and apply a bounded retry policy only when the operation is safe to retry.
  • ResourceAccessException: An outbound HTTP call fails to connect, times out, or hits another I/O problem. Check network, DNS, TLS, timeouts, and the nested cause.
  • WebClientResponseException: A WebClient call receives an error HTTP status. Inspect the status and body; transport failures use other exception types.
  • WebClientRequestException: A WebClient call fails before receiving an HTTP response because of DNS, connection, TLS, or timeout trouble. Inspect the nested network cause and dependency availability.
  • TimeoutException: Waiting for a Future or background result exceeds its limit. Check the operation's latency and whether cancellation or a fallback is needed.
  • CompletionException: A CompletableFuture stage fails and join() or a dependent stage reports a wrapper exception. Inspect getCause() to find the actual failure.
  • TaskRejectedException: A Spring executor rejects work because its queue is full or it is shutting down. Check executor capacity, task duration, and shutdown timing.

Application Startup Exceptions

  • BeanCreationException: A bean constructor, factory method, or initialization step fails. Follow nested causes to the failing bean and its configuration.
  • UnsatisfiedDependencyException: A required dependency is missing, ambiguous, or fails during creation. Check the injection point, component scanning, qualifiers, and nested cause.
  • NoSuchBeanDefinitionException: A component is outside scanning, a conditional bean was not created, or a requested type was never registered. Check the active profile and configuration conditions.

Important Java Errors

Error is a separate branch of Throwable. These usually indicate JVM resource exhaustion, a failing class initialization, or incompatible compiled code. Investigate the environment and root cause; do not treat them as routine recoverable request failures or catch Error broadly.

  • OutOfMemoryError: Heap is exhausted, too many threads are created, or another JVM memory area runs out. Check the exact error message, memory limits, heap dump, and allocation pattern.
  • StackOverflowError: Recursion has no stopping condition, object methods call each other repeatedly, or a cyclic object graph is traversed without protection. Check the repeated stack frames.
  • NoClassDefFoundError: A class existed at compile time but is missing at runtime, or its earlier initialization failed. Check the runtime classpath, packaged dependencies, and earlier cause.
  • NoSuchMethodError: Code was compiled against a different library version from the one loaded in production. Check dependency versions and the packaged artifact.
  • ExceptionInInitializerError: A static initializer or static field initialization throws an exception. Check its nested cause and avoid environment-dependent work in static initialization.
  • AssertionError: An explicit assertion or test assertion fails. Check the violated assumption; Java assert statements depend on whether assertions are enabled.

From My Own Work

1. A HashMap-based dedup silently collapsing a distinct-count check

Situation: A chat session uniqueness check counted distinct participants using a Set, but when the transaction coordinator was both the creator and a participant, their id deduplicated against itself.
Task: Fix the count check so it actually enforced "two distinct people."
Action: I reworked the uniqueness logic to model the creator as a required, distinct role rather than folding them into the same participant Set used for counting.
Result: It was a good reminder that Set-based deduplication is exactly the right tool for removing duplicates, and exactly the wrong tool when you need to count roles that can overlap in identity but not in meaning.

2. Choosing ExecutorService/CompletableFuture over WebFlux for a specific pipeline

Situation: A report pipeline needed to fire required calls that had to succeed together, and optional calls that could fail independently.
Task: Express that composition correctly without one failing call taking down the whole report.
Action: Since the codebase was already reactive, I used Mono.zip for the required group, since it fails the combined result if any one source errors, and Flux with onErrorResume for the optional group, so one failure degrades to a fallback instead of terminating the stream.
Result: The distinction that mattered wasn't reactive versus imperative concurrency, it was picking the primitive that matched whether a group of calls needed to succeed together or could fail independently.

3. Async decoupling a core action from a secondary system's health

Situation: A message send was calling a notification publish step synchronously, so a slow Service Bus broker directly added latency to sending a message.
Task: Stop a secondary system's slowness from degrading a core feature.
Action: I converted the publish call to fire-and-forget using @Async, with failures caught and logged inside that method rather than propagated to the caller.
Result: The core send path's latency became independent of the messaging system's health, which is the real value of Async, decoupling reliability, not just moving work off a thread.

4. Why a retry needed a fresh transaction, not a try-catch

Situation: A cache upsert used try-save-then-catch-on-conflict, but the retry read inside the same transaction as the failed insert kept failing.
Task: Make the retry actually succeed after catching the constraint violation.
Action: I scoped the retry to run in its own fresh transaction, since once a transaction hits an exception like a constraint violation it gets marked rollback-only in Spring/JPA, and catching the exception doesn't undo that marking.
Result: This is a subtle but common gotcha, exception handling in Java doesn't override transactional state that a framework is tracking separately underneath it.

5. WeakReference-adjacent reasoning for per-instance in-memory state

Situation: Presence tracking lived in one instance's memory, so a user's online status looked inconsistent once we scaled to multiple instances.
Task: Recognize that this wasn't just a performance concern, it was a correctness gap.
Action: In-memory state on one JVM instance doesn't survive or sync across others, so I moved presence into a shared Redis-backed service instead of trying to replicate or coordinate per-instance memory.
Result: It reinforced that any state held in a single JVM's heap is implicitly scoped to that instance, which is easy to forget once an application scales horizontally.

6. Immutable objects and thread safety in a concurrent notification pipeline

Situation: Notification events flowing through Service Bus consumers needed to be safely read by multiple concurrent handlers without defensive copying at every step.
Task: Avoid a class of concurrency bugs where one handler's mutation could affect another's view of the same event.
Action: I modeled notification payloads as immutable objects, no setters, all fields final, so any handler that received one could not accidentally corrupt it for a concurrently running handler.
Result: Immutability removed an entire category of thread-safety bugs by construction, rather than relying on every handler to behave defensively.

7. Optional as a signal, not a replacement for every nullable field

Situation: When making transactionId nullable end to end for enquiry sessions, there was a temptation to wrap every downstream read in Optional.
Task: Decide where Optional actually added clarity versus where it just added ceremony.
Action: I used Optional at method return boundaries where "no transaction" was a meaningful outcome the caller had to handle, but kept internal fields as plain nullable references where the null was already well understood context, not a public API contract.
Result: Optional is most valuable as a signal at an API boundary, overusing it internally just adds unwrapping noise without adding safety.

8. Diagnosing an N+1-like pattern with real profiling, not guessing

Situation: Chat operations were taking 30 to 60 seconds, and it wasn't obvious from reading the code which query was the problem.
Task: Find the actual bottleneck rather than optimizing the first suspicious-looking query.
Action: I used Hibernate's SQL logging and EXPLAIN ANALYZE against a realistically sized dataset, which surfaced a pattern of cumulative redundant queries across several lazy-loaded associations, not one single slow query.
Result: A query plan that looks fine on a handful of local rows can hide a pattern that only becomes visible, and expensive, at real data volumes.

9. Static initialization order mattering more than expected

Situation: A logging configuration bean was wiping out early application monitoring logs because it initialized after the APM appender had already registered.
Task: Fix the ordering without relying on luck or classpath scanning order.
Action: I used an explicit @DependsOn to force the log-clearing bean to initialize before the APM appender, since the JVM and Spring don't guarantee initialization order beyond explicit dependency edges you declare.
Result: It was a reminder that implicit ordering, whether class loading order or bean creation order, is never something to build correctness on without an explicit guarantee.

10. Records as a natural fit for immutable DTOs in a caching layer

Situation: A caching layer needed a value type to represent a cached API response that should never be mutated after being read from the cache.
Task: Avoid a mutable POJO where a caller could accidentally modify a shared cached instance and corrupt what other callers see.
Action: I used a Java record for the cached value shape, getting immutability, equals/hashCode, and a compact constructor for validation for free instead of hand-writing that boilerplate on a regular class.
Result: Records made the immutability guarantee explicit and enforced by the compiler, rather than a convention someone could accidentally violate with a setter.
