✅ JUnit Core Concepts

Definitions and use cases for JUnit testing.

Test Methods & Assertions

A test method is annotated with @Test and uses assertions to verify observable behavior. Prefer assertions that explain the business rule being protected, for example @Test void testAdd() { assertEquals(5, calculator.add(2, 3)); }.

JUnit 5 assertion reference
AssertionWhat it verifiesExample and practical detail
assertEquals(expected, actual)Two values are equal.assertEquals(5, calculator.add(2, 3)); Use the expected value first so failure messages read naturally.
assertNotEquals(unexpected, actual)Two values must differ.assertNotEquals(oldToken, newToken); Useful for uniqueness or state-change checks.
assertTrue(condition)
assertFalse(condition)		A boolean rule is true or false.assertTrue(user.isActive()); Prefer a domain predicate over asserting an internal field.
assertNull(value)
assertNotNull(value)		A result is absent or present.assertNotNull(response.body()); Use for optional results, response bodies, and generated IDs.
assertSame(expected, actual)
assertNotSame(unexpected, actual)		Two references point to the same or different object.assertSame(cachedUser, cache.get(id)); Use identity checks only when object identity is part of the contract.
assertArrayEquals(expected, actual)Arrays contain equal values in the same order.assertArrayEquals(new byte[]{1, 2}, payload); Better than assertEquals for arrays.
assertIterableEquals(expected, actual)Two iterables contain equal elements in order.assertIterableEquals(List.of("A", "B"), result); Works across iterable implementations.
assertLinesMatch(expected, actual)Text lines match, including supported patterns.assertLinesMatch(List.of("id=\\d+"), lines); Helpful for logs, reports, and generated text.
assertThrows(type, executable)The expected exception type is thrown.var ex = assertThrows(IllegalArgumentException.class, () -> service.create("")); Capture it to assert the message or error code.
assertDoesNotThrow(executable)A valid operation completes without an exception.assertDoesNotThrow(() -> validator.validate(request)); Also assert the returned result when possible.
assertAll(executables...)Several related assertions run together.assertAll(() -> assertEquals("Ada", user.name()), () -> assertTrue(user.active())); Reports all failures together.
assertTimeout(duration, executable)Code completes within a time limit.assertTimeout(Duration.ofSeconds(1), () -> service.load()); Good for bounded performance checks.
assertTimeoutPreemptively(duration, executable)Code is interrupted when it exceeds the limit.assertTimeoutPreemptively(Duration.ofMillis(250), task); Avoid around transactions or thread-local context.
assertInstanceOf(type, value)
assertNotInstanceOf(type, value)		A value has or does not have the expected runtime type.var event = assertInstanceOf(PaymentEvent.class, message); The first form returns the typed value.
fail(message)Stops a test explicitly on an invalid path.fail("Unsupported status: " + status); Useful for exhaustive branches.
Assertion message overloadsAdds context to a failure.assertEquals(expected, actual, () -> "userId=" + userId); Use a supplier when building the message is expensive.

Rule of thumb: assert the public result, state transition, emitted event, or durable side effect. Avoid asserting private implementation details unless they are part of the contract.

Test Lifecycle

Annotations controlling when setup and cleanup run:

  • @BeforeEach, runs before each test
  • @AfterEach, runs after each test
  • @BeforeAll, runs once before all tests, must be static
  • @AfterAll, runs once after all tests, must be static

Common pattern: @BeforeEach void setup() { db.createTables(); } paired with @AfterEach void cleanup() { db.clearData(); } to keep tests isolated from each other.

Parameterized Tests

Runs the same test logic against different input values using @ParameterizedTest, avoiding copy-pasted near-duplicate test methods:

  • @ValueSource(ints = {1, 2, 3, 4}), multiple simple inputs
  • @CsvSource({"1,1,2", "2,3,5"}), CSV-style multi-argument inputs
  • @MethodSource("testData"), pulls test data from a method
@ParameterizedTest
@ValueSource(strings = {"test@email.com", "user@domain.org"})
void testValidEmails(String email) {
    assertTrue(validator.isValid(email));
}

Mocking with Mockito

Mockito creates mock objects to isolate the unit under test from its dependencies.

  • @Mock, creates a mock object
  • @InjectMocks, injects the mocks into the class under test
@Mock PaymentService paymentService;
@InjectMocks OrderService orderService;

when(paymentService.process(any())).thenReturn(true);
verify(emailService).send("test@email.com");

Test Organization

  • @Tag("unit"), @Tag("integration"), tag tests for selective runs
  • @Suite + @SelectClasses({Test1.class, Test2.class}), group into suites
  • @SelectPackages("com.example.tests"), select by package

Exception Testing

assertThrows(IllegalArgumentException.class, () -> divide(5, 0));
assertThrows(UnauthorizedException.class, () -> deleteUser());

Integration Testing

Beyond isolated unit tests, Spring Boot provides slice tests for testing component interaction with real infrastructure:

  • @DataJpaTest, tests the repository/database layer only
  • @WebMvcTest, tests the web/controller layer only, with mocked service beans
  • @SpringBootTest, loads the full application context

Interview & Production Essentials

A strong test suite proves behavior at the right boundary. Keep most tests fast and deterministic, then add focused integration and end-to-end coverage where wiring, infrastructure, or user journeys can fail.

  • Test isolation: each test owns its data and cleanup; never depend on execution order or shared mutable state.
  • Deterministic time: inject java.time.Clock instead of sleeping so expiry, scheduling, and timeout boundaries are repeatable.
  • Failure paths: test timeouts, retries, fallbacks, malformed input, partial failures, and rollback—not only the happy path.
  • Idempotency and concurrency: race duplicate requests and verify one durable result, safe retries, and no duplicate side effects.
  • Contract tests: verify request/response compatibility between services so an API change fails before deployment.
  • Realistic infrastructure: use Testcontainers for database constraints, migrations, messaging, and serialization behavior that mocks or H2 can hide.
  • Test strength: use mutation testing or deliberate small code changes to confirm that meaningful tests actually fail when behavior breaks.
  • CI feedback: separate fast unit tests from slower tagged integration tests, and quarantine flaky tests with an owner and a fix deadline.

Interview framing: explain what each test isolates, which production failure it protects against, and why the chosen boundary gives the best confidence-to-runtime tradeoff.

Performance Testing

@Timeout(value = 5, unit = TimeUnit.SECONDS) fails a test if it takes longer than the given duration, useful for catching accidental performance regressions or hangs.

Quick Reference

import static org.junit.jupiter.api.Assertions.*;
import static org.mockito.ArgumentMatchers.any;
import static org.mockito.Mockito.*;

import java.util.concurrent.TimeUnit;
import org.junit.jupiter.api.*;
import org.junit.jupiter.api.extension.ExtendWith;
import org.junit.jupiter.params.ParameterizedTest;
import org.junit.jupiter.params.provider.ValueSource;
import org.mockito.*;
import org.mockito.junit.jupiter.MockitoExtension;

@Tag("unit") // Select this group in CI
@ExtendWith(MockitoExtension.class) // Creates and injects Mockito mocks
class UserServiceTest {

    @Mock UserRepository repository; // Fake external dependency
    @Mock EmailSender emailSender;
    @InjectMocks UserService userService; // Class being tested
    @Captor ArgumentCaptor<User> userCaptor; // Inspect a mock argument

    @BeforeEach
    void setUp() {
        // Keep each test independent; avoid shared mutable state.
        reset(repository, emailSender);
    }

    @AfterEach
    void tearDown() {
        // Close files, containers, or other resources here if needed.
    }

    @Test
    @Timeout(value = 1, unit = TimeUnit.SECONDS) // Catches hangs and regressions
    void createsUserAndSendsWelcomeEmail() {
        // Given: controlled dependency behavior
        when(repository.save(any(User.class))).thenAnswer(invocation -> invocation.getArgument(0));

        // When: call the unit under test
        User saved = userService.create("John", "john@example.com");

        // Then: assert the result and important side effects
        assertAll(
            () -> assertNotNull(saved),
            () -> assertEquals("John", saved.name()),
            () -> assertEquals("john@example.com", saved.email())
        );
        verify(repository).save(userCaptor.capture());
        verify(emailSender).send("john@example.com");
        assertEquals("John", userCaptor.getValue().name());
        verifyNoMoreInteractions(repository, emailSender);
    }

    @ParameterizedTest
    @ValueSource(strings = {"", " ", "not-an-email"}) // Reuse one test for edge cases
    void rejectsInvalidInput(String invalidEmail) {
        assertThrows(IllegalArgumentException.class,
            () -> userService.create("John", invalidEmail));
        verifyNoInteractions(repository, emailSender); // Validation fails before I/O
    }

    @Test
    void propagatesRepositoryFailureWithoutSendingEmail() {
        // Failure-path test: production dependencies can fail
        when(repository.save(any(User.class)))
            .thenThrow(new IllegalStateException("database unavailable"));

        assertThrows(IllegalStateException.class,
            () -> userService.create("John", "john@example.com"));
        verifyNoInteractions(emailSender); // No side effect after a failed save
    }
}

// These interfaces make the dependency boundaries explicit.
record User(String name, String email) {}
interface UserRepository { User save(User user); }
interface EmailSender { void send(String email); }

From My Own Work

1. Byte-for-byte before/after comparison tests on a billing-relevant refactor

Situation: I was extracting core valuation logic out of a paid appraisal endpoint into a shared service so a new free cache flow could reuse it, and the endpoint was billing relevant.
Task: Prove the refactor didn't change the endpoint's behavior at all, not just assume it based on reading the diff.
Action: I wrote comparison tests that ran the exact same request against the old and new code paths and asserted the responses matched byte for byte, running against the real Spring context rather than a mocked service, since a mock would hide a subtle wiring bug from the extraction.
Result: The refactor shipped with real confidence the billing-relevant endpoint's behavior was completely unchanged, which a unit test on the extracted method alone wouldn't have proven.

2. @Container + @DynamicPropertySource to catch real SQL Server behavior H2 missed

Situation: Repository tests ran against in-memory H2, but I needed to verify behavior specific to real SQL Server, unique constraint upserts and cascading deletes.
Task: Get tests running against a real database engine without slowing the whole suite down per test.
Action: I declared the container as a static field annotated @Container so it starts once and is shared across the test class, and used @DynamicPropertySource to inject its connection details before the Spring context boots.
Result: The tests caught real constraint and cascade behavior H2 would have silently handled differently, which is exactly the gap Testcontainers exists to close.

3. Recognizing what a mock hides during an extraction refactor

Situation: While verifying a service extraction, the fast path would have been to unit test the extracted method in isolation with its dependencies mocked.
Task: Decide whether that isolated test actually proved the extraction was safe.
Action: I insisted the comparison tests run against the real Spring context instead, since a mock only verifies the caller's code path against an assumed interface, it wouldn't catch a subtle bug in how the extracted service itself gets wired or its dependencies injected.
Result: That distinction, unit testing logic versus integration testing wiring, is exactly the kind of gap a refactor is most likely to introduce and a pure mock-based test is least likely to catch.

4. A test gap that would have caught a missing-branch bug earlier

Situation: A payment status update defaulted to Pending regardless of whether a payment transaction id existed, a missing branch rather than a broken one, and it shipped without being caught.
Task: Identify what test coverage would have caught this before it reached production.
Action: After fixing the bug, I added a test asserting the correct status for every known payment state, not just the happy path, so a default-only implementation fails a test immediately instead of only surfacing once real paid records hit it.
Result: It reinforced testing every explicit branch a status or state machine can be in, not just the primary path, since a missing else-branch produces no compile error and no obvious symptom until real data exercises it.

5. A cache key collision test that verifies uniqueness across parameters

Situation: A cache key generator initially left out a secondary parameter some endpoints accepted, causing two different requests to collide on the same key and return wrong cached data.
Task: Prevent the same class of bug from recurring on a future endpoint with a different overlooked parameter.
Action: After rebuilding the key generator to derive keys programmatically from every parameter reaching the call, I added a test that calls the same endpoint with two different values for every documented parameter and asserts the cache keys differ.
Result: This kind of test catches a missing parameter automatically instead of relying on someone noticing wrong-looking cached data days or weeks later.
