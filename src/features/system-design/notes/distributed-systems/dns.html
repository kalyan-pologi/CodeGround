Networking Essentials

🌐 DNS - Domain Name System

How domain names resolve to IP addresses: hierarchical lookup, caching, and record types.

📚 What It Is

Definition

A distributed, hierarchical system that translates human-readable domain names, like example.com, into machine IP addresses. "Distributed" is the key word: no single server holds the whole mapping. Responsibility is split across millions of servers organized in a tree.

Think of it as

The internet's phonebook. You look up a name and get back a number (IP) you can actually connect to. Without it you would have to memorize IP addresses for every site you visit, and every time a company changed hosting providers, every user would need the new number.

Built on

Transport: UDP for most queries, TCP for large/zone transfers. Port: 53. Query size: Tiny, usually under 512 bytes.
❓ Why Introduced

The Human Memory Problem

Computers address each other by IP, but IPs are hard for humans to remember and can change when infrastructure changes. Before DNS, an early version of the internet used a single flat file (HOSTS.TXT) manually synced across machines. That approach could never scale past a few thousand hosts. As the internet grew, keeping that file consistent everywhere became physically impossible, which is exactly the problem DNS was designed to solve.

Indirection Enables Change

DNS decouples a stable, memorable name from a mutable IP. A service can change servers or IPs without users needing to know or do anything differently. This indirection is also what makes load balancing, failover, and CDNs possible at the name resolution layer. The same idea shows up everywhere in system design: adding a layer of indirection to decouple "what something is called" from "where it currently lives."

Scale Requires Distribution

A single central lookup table doesn't scale globally: every query in the world would hit one place. DNS is hierarchical and distributed so no single server is a bottleneck or a single point of failure. The hierarchy also spreads ownership: a company controls its own domain's records without needing permission from whoever runs the root or TLD servers.
⚙️ How It Works - Resolution Path

Lookup Chain

1.Browser/OS cache checked first
2.Recursive resolver queried
3.Root nameserver, finds the TLD
4.TLD nameserver, finds authoritative NS
5.Authoritative nameserver returns the IP
The recursive resolver does the multi-hop work on the client's behalf and caches the result so the next user's query is fast.

Record Types

A: Domain to IPv4 address. AAAA: Domain to IPv6 address. CNAME: Alias pointing to another domain. MX: Mail server for the domain. TXT: Arbitrary text, used for verification, SPF, DKIM. NS: Which servers are authoritative for this domain.

Caching (TTL)

Every DNS record has a TTL (time to live), which tells resolvers how long they may cache it before re-querying the authoritative server. Low TTL means faster failover and propagation of changes, but more query load on your nameservers. High TTL means fewer queries and lower latency for users, but changes take longer to reach everyone, since old records linger in caches.
✅ When to Use / Use Cases

Every Service, Always

Every internet-facing service needs it. It's the required first step before any domain-based access works at all. Even internal microservices increasingly use DNS-based service discovery (like Kubernetes' internal DNS) instead of hardcoded IPs, for the same "stable name, mutable location" reason.

Load Balancing & Failover

DNS-based load balancing and failover: return different IPs to different clients based on health checks, region, or simple round robin. Used as a coarse, cheap first tier of routing before traffic even reaches a dedicated L4 or L7 load balancer inside a region.

Geo-Routing

Geo-routing (GeoDNS): resolvers can return the IP of the nearest region to cut latency, which is how many CDNs and multi-region services route users automatically. This is often the very first decision point in a global system's request path: which region does this user even talk to, decided before a single byte of the actual request is sent.
⚖️ Trade-offs

Caching TTL

High TTL gives fast lookups and low origin load, but slows propagation of an IP change, which can mean stale routing during a failover event. Low TTL trades that away: faster recovery and change propagation, at the cost of more queries hitting your nameservers and slightly slower average lookups for everyone.

Hierarchy Depth

More hops (root, then TLD, then authoritative) means more latency on a cold, uncached lookup, but each layer is independently cacheable and horizontally scalable. In practice this cost is mostly paid once: recursive resolvers cache root and TLD answers aggressively, so most real-world lookups skip straight to the authoritative server.

DNS Load Balancing

Simple and cheap to operate, but coarse. There's no per-request routing, and some clients ignore TTL and hold onto stale cached records longer than intended. Compared to an L4/L7 load balancer, DNS-based routing can't react to real-time server load, only to whichever IPs you chose to return at query time.
🚨 Failure Modes + Mitigations

Availability Failures

DNS server down: Multiple redundant NS records across providers. Slow first lookup: Caching plus deliberate TTL tuning. Whole DNS provider outage: Secondary DNS provider as a backup NS set. Resolver timeout: Client falls back to a secondary resolver.

Security Failures

DNS spoofing / cache poisoning: DNSSEC, cryptographically signed records. DDoS against a resolver: Anycast routing plus rate limiting. Domain hijacking: Registry lock, MFA on the registrar account. DNS tunneling for data exfiltration: Monitor for abnormal query patterns/volume.

Operational Failures

Stale cached IP after failover: Lower TTL ahead of a planned migration. Misconfigured record: Staged rollout, monitor before wide propagation. Forgotten expired domain: Auto-renewal plus expiry alerts. Wrong TTL set before a migration: Lower TTL days in advance, not at cutover time.
🚫 When NOT to Rely on It Alone

Not for Sub-Second Failover

Don't use DNS failover as your only mechanism when you need sub-second recovery. TTL and client-side caching mean propagation isn't instant, sometimes minutes.

Not for Fine-Grained Routing

For per-request routing, like a canary rollout to a small percentage of traffic or header-based routing, use an L7 load balancer instead of DNS tricks.

Not a Security Boundary

DNS alone doesn't authenticate or encrypt anything. It just resolves a name. Access control still has to happen at the app or network layer.
🗺️ Where It Fits in a System Diagram

Request Path

1.DNS resolve, before any connection
2.Load Balancer
3.App Server

Always First

Always the very first step before TCP or HTTP even begins. Resolve name to IP, then open the actual connection.

Cached After First Hit

Once resolved, the OS and browser cache the IP for the record's TTL, so most subsequent requests skip DNS entirely until it expires.
🌍 Real-World Examples

Managed DNS Providers

AWS: Route 53. Cloudflare: Cloudflare DNS. Google: Cloud DNS.

GeoDNS in Practice

Netflix and other large services use GeoDNS combined with health-checked failover to route users automatically to the nearest healthy region.

Protecting DNS Itself

Large providers run DNS on anycast networks with hundreds of PoPs, so a regional outage or attack doesn't take resolution down globally.
