Networking Essentials

⚖️ Load Balancing

Distributing traffic across servers: algorithms, L4 vs L7, active-passive vs active-active.

📚 What It Is

Definition

A component that distributes incoming traffic across multiple backend servers so no single server gets overwhelmed while others sit idle. From the outside, the whole backend pool looks like a single service. Clients only ever talk to the load balancer's address, never to individual servers directly.

L4 vs L7

L4routes by IP/port, transport layer only
L7routes by URL, header, or cookie, application layer
L4 speedfaster, less CPU, no payload inspection
L7 flexibilitysmarter routing, more CPU per request

Placement

Sits between clients and a pool of identical, or near-identical, backend instances, acting as the single entry point to that pool. Can exist at multiple points in a system at once: in front of app servers, in front of a cache cluster, or in front of database read replicas.
❓ Why Introduced

Single Server's Ceiling

A single server has a hard ceiling on throughput and open connections. Vertical scaling alone eventually runs out of headroom, and a single box has no failover. Even the biggest single machine you can buy eventually can't keep up with a growing user base, and it costs disproportionately more as you go up in size.

Enables Horizontal Scaling

Load balancing enables horizontal scaling: add more identical servers and spread traffic across them, instead of buying a bigger and bigger single machine. Commodity servers are cheaper per unit of throughput than one giant machine, so this also tends to be the more cost-effective way to scale.

Provides Failover

It also provides failover. If a server dies, the load balancer stops sending it traffic and the remaining healthy servers absorb the load automatically. This turns what would be a full outage on a single-server setup into a smaller capacity dip that users may not even notice.
⚙️ How It Works - Algorithms

Static

Round robincycle through servers evenly, one after another
Weighted round robinbias traffic toward stronger servers
IP hashsame client always lands on the same server (sticky)

Dynamic

Least connectionssend to the server with the fewest active connections right now
Least response timesend to whichever server is currently responding fastest
Resource-basedfactor in real CPU/memory usage reported by each server

Health Checks

The load balancer pings each backend on a regular interval. Unhealthy servers are pulled out of rotation until they pass a check again and recover. Checks can be shallow (does the port respond) or deep (does a real endpoint return a healthy status), and deep checks catch more failure modes but cost more to run frequently.
✅ When to Use / Which Layer

L4 (TCP-level)

Fast and protocol-agnostic. Good for WebSocket or other long-lived connections, since one client stays pinned to one server for the connection's whole lifetime. Also the right choice for non-HTTP protocols entirely, like raw TCP database connections or custom binary protocols, where there's no HTTP layer to inspect anyway.

L7 (HTTP-level)

Route by path or header, like sending /api to one pool and /static to another, plus SSL termination, A/B testing, and canary routing. Also the layer where you'd implement blue-green deployments, shifting a percentage of traffic to a new version based on request attributes.

Active-Passive vs Active-Active

Active-passive: a standby node only takes over on failure. Simple, but wastes idle capacity. Active-active: all nodes serve traffic simultaneously. Better use of capacity, more operationally complex to keep them in sync.
⚖️ Trade-offs

Round Robin

Round robin is simple but ignores actual server load, so one slow request can pile up unfair share of traffic on a single already-busy instance. It works well when all servers are truly identical in capacity and requests are roughly uniform in cost, which is often true but not guaranteed.

Least Connections

Least connections is smarter about real load, but costs more to compute and track accurately at very high request rates. It also assumes connection count correlates with actual load, which can be wrong if some connections are cheap and others are expensive to serve.

Sticky Sessions

Sticky sessions via IP hash simplify stateful apps that keep session data in memory, but create hot spots and complicate both scaling and failover, since you can't just move a client to another server freely. They also break down behind NAT or shared corporate IPs, where many different users can appear to come from the same source IP and get routed unevenly.
🚨 Failure Modes + Mitigations

Load Balancer Availability

LB itself is a single point of failure: run redundant LBs behind DNS or anycast. LB overwhelmed by traffic: autoscale the LB tier if using a software LB. Bad health check config: alert on rapid flapping between healthy and unhealthy.

Load Distribution Issues

Uneven load, one "hot" server: switch to least-connections or least-response-time. One slow server drags down p99: outlier detection, ejecting consistently slow nodes. Cold new instance gets full traffic share: slow start, ramping traffic gradually.

Failover Behavior

Thundering herd during failover: gradual traffic shift, client backoff with jitter. Failover flip-flopping: require sustained failure before marking unhealthy. Retry storm hitting remaining healthy nodes: circuit breakers, bounded retry budgets.
🚫 When NOT to Use

Skip It Early

Skip a dedicated load balancer for a single-instance service or local development. It adds complexity with no real benefit until you actually need to scale out.

Wrong Layer for the Job

Don't use L7 routing for raw high-throughput TCP or WebSocket workloads where the extra HTTP parsing overhead isn't worth it. Prefer L4 there instead.

Don't Over-Engineer Stickiness

Avoid sticky sessions if you can make the app stateless instead. Session affinity solves a symptom; storing session state externally (Redis) solves the actual problem.
🗺️ Where It Fits in a System Diagram

Typical Path

ClientDNS, then Load Balancer
thenApp server pool
thenDB or cache tier

Also Used Internally

Load balancing can also exist internally, between app servers and a downstream service tier, or in front of a database's read replicas.

Multi-Tier Setups

Large systems often chain load balancers: a global L4/anycast tier for region selection, then a regional L7 tier for fine-grained routing within that region.
