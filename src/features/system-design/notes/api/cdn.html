Networking Essentials

🌍 CDN - Content Delivery Network

Edge caching, push vs pull CDN, reducing latency for global users.

📚 What It Is

Definition

A geographically distributed network of edge servers that caches and serves content close to the user, instead of every single request hitting the origin server. From the origin's point of view, the CDN acts as a giant shared cache sitting in front of it, absorbing the vast majority of read traffic.

Push vs Pull

Push: You upload content to the CDN ahead of time. Pull: CDN fetches from origin on the first request, then caches it. Push fits: Small, stable content sets you control fully. Pull fits: Large or frequently changing content sets.

Edge Location

A PoP (point of presence) physically near a cluster of users, holding cached copies of content so those users get short round-trip times. Large CDNs run hundreds of PoPs worldwide, so most users are only a few milliseconds away from one, rather than hundreds of milliseconds from a single origin.
❓ Why Introduced

Distance Costs Latency

Physical distance directly costs latency. A user in Tokyo hitting an origin server in Virginia pays real round-trip time on every single request. The speed of light itself is the hard floor here. No amount of server optimization removes the physics of a signal crossing an ocean and back.

Concentrated Load

Serving every request from one origin also concentrates all the load there. A CDN offloads static, cacheable traffic so origin only handles requests that actually need it. This also means a traffic spike, like a viral post, gets absorbed by edge caches instead of directly threatening to take the origin down.

Two Problems, One Fix

CDNs solve both problems at once: move content physically closer to users, and absorb traffic before it ever reaches the origin server. This combination is why CDNs became standard infrastructure rather than a niche optimization: the cost savings and latency wins compound together.
⚙️ How It Works

Pull CDN Flow

1.Request arrives at nearest edge node
2.Cache miss, edge fetches from origin
3.Edge caches the response, serves it
4.Later requests served from edge, fast

Routing to Nearest Edge

Typically done via GeoDNS or anycast. The same domain resolves to a different, nearest IP address depending on where the request is coming from. Anycast is especially powerful: many PoPs announce the exact same IP, and internet routing itself sends each user to the topologically nearest one.

Cache Invalidation

Cached content expires by TTL, or is explicitly purged and invalidated when new content is deployed. Cache invalidation is famously one of the two hard problems in computer science. Some CDNs support tag-based purging, so you can invalidate every cached object related to one product or page without knowing every individual URL.
✅ When to Use

Static Assets

Static assets: images, JS and CSS bundles, videos, and downloadable files that don't change per request. These are the easiest win: identical bytes served to every user, so cache hit rates approach 100% once warmed.

Global Audiences

Globally distributed audiences. The further apart and more spread out your users are, the bigger the latency win from edge caching. Even a single-region origin can serve a global audience reasonably well once a CDN is in front of it, without standing up infrastructure in every region.

DDoS Absorption

Also useful for DDoS absorption. CDN edge nodes soak up volumetric attacks before they can ever reach the origin. A CDN operator's total edge capacity across hundreds of PoPs vastly exceeds what any single origin server could ever absorb on its own.
⚖️ Trade-offs

Push CDN

Predictable, since content is ready ahead of time, but you have to manage uploads yourself and pay to store content even if it's rarely accessed. Works well for a known, bounded content set, like a game's asset bundle, but becomes unwieldy for a large, constantly growing catalog.

Pull CDN

Simple to operate, since the CDN handles fetching automatically, but the first request per region is slow on a cache miss and origin still absorbs some load. This is the more common choice for most web applications, since it needs almost no extra operational work beyond setting cache headers correctly.

Freshness vs Performance

Freshness vs performance is the central tension. A long TTL is fast and cheap but risks serving stale content. A short TTL keeps content fresher but drives more origin hits. Cache-busting filenames (hashing content into the URL) sidestep this entirely for versioned assets: a long TTL is safe because a changed file simply gets a new URL.
🚨 Failure Modes + Mitigations

Freshness Failures

Stale content served after deploy: Cache-busting filenames or explicit purge. Purge doesn't reach every PoP fast: Short TTL as a safety net alongside explicit purge. Wrong content cached and served to everyone: Cache key includes all relevant request variance (headers, query params).

Availability Failures

Edge node goes down: Anycast automatically reroutes to next-nearest edge. Whole CDN provider outage: Multi-CDN setup with automatic failover. Origin unreachable on a miss: Serve stale cached content as a fallback.

Load Spike Failures

Cache stampede when a popular item expires: Stale-while-revalidate, request coalescing. Sudden viral traffic overwhelms one PoP: Anycast spreads load across nearby PoPs automatically. Cold cache after a config change: Pre-warm the cache before flipping traffic over.
🚫 When NOT to Use

Skip for Personalized Data

Don't put a CDN in front of highly personalized or frequently changing per-user data. Low cache hit rate makes the extra hop not worth it.

Skip for Small, Local Apps

Skip it for a small, single-region app with a local user base. The origin alone is already fast enough for those users.

Not a Substitute for Origin Scaling

A CDN reduces origin load, it doesn't eliminate the need to scale origin. Cache misses, dynamic endpoints, and API calls still hit it directly.
🗺️ Where It Fits in a System Diagram

Request Path

Client: CDN edge, cache hit means done here. cache miss: Falls through to Origin, behind LB and app servers.

Outermost Layer

Sits as the outermost layer, in front of your own DNS resolution and load balancer. Most traffic in a well-cached system never reaches origin at all.

Origin Shield

Some CDNs add a mid-tier "origin shield" cache, so even a spike of cache misses across many edge nodes collapses into one request to origin instead of many.
🌍 Real-World Examples

Major CDNs

Cloudflare: General purpose, DDoS protection. Akamai: Enterprise scale, longest-running. Fastly: Fast cache purge, edge compute. CloudFront: Tight AWS integration.

Video Streaming

Netflix and YouTube push video segments out to edge caches close to viewers to keep streaming latency and buffering low.

Netflix Open Connect

Netflix even runs its own custom CDN hardware placed directly inside ISP networks, skipping public internet transit for most of its traffic entirely.
