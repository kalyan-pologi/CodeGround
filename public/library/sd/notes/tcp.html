Networking Essentials

🌐 TCP / UDP / HTTP / WebSocket

How data travels across networks: connection types, reliability guarantees, and when to use each protocol.

📚 What They Are

Transport Layer

TCP is connection-oriented. It guarantees ordered, reliable delivery of every byte between two endpoints. UDP is connectionless. It fires datagrams with no guarantee of delivery, order, or duplicate protection. Both sit directly on top of IP and are identified in a packet by a protocol number (6 for TCP, 17 for UDP).

Application Layer

HTTP is a request/response protocol built on top of TCP, used for most client-server communication on the web. WebSocket starts life as a normal HTTP request, then "upgrades" the underlying TCP connection into a persistent, bidirectional channel. Both are text-based (HTTP/1.1) or binary-framed (HTTP/2, WebSocket frames) protocols that define message structure on top of a transport connection.

How They Stack

Layer 1IP, routing
Layer 2TCP or UDP
Layer 3HTTP or WebSocket
Each layer only knows about the one below it. HTTP has no idea whether it's riding on a fresh TCP connection or a reused one.
❓ Why Each Was Introduced

TCP

IP alone only guarantees "best effort" delivery. Packets can be lost, duplicated, or arrive out of order because routers may take different paths. Applications like file transfer or loading a web page need the data to arrive complete and in the right order, or the result is corrupted or unusable. TCP was built as a layer on top of unreliable IP that reconstructs a clean, ordered byte stream for the application.

UDP

TCP's reliability comes at a real cost: handshakes before any data flows, acknowledgments for every segment, and retransmissions on loss, all of which add latency. Some applications (video calls, live game state, DNS lookups) care more about speed and low latency than about every single packet arriving. UDP strips away all of TCP's bookkeeping so the app can send data with the minimum possible overhead and handle loss itself if it needs to.

HTTP & WebSocket

HTTP exists because once you have a reliable byte stream (TCP), you still need a shared "language" for computers to ask each other for resources: methods, status codes, headers. HTTP is fundamentally request driven. The client always speaks first and the server can only reply. WebSocket solves the case where the server needs to push data without being asked, like chat messages, live dashboards, or multiplayer game state, by keeping one TCP connection open in both directions.
⚙️ How It Works

TCP Handshake & Teardown

SetupSYN, SYN-ACK, ACK
Teardown4-way FIN/ACK
Every byte sent is tracked with sequence numbers. Unacknowledged bytes are retransmitted after a timeout. Flow control (receive window) prevents a fast sender from overwhelming a slow receiver. Congestion control backs off sending rate when the network itself seems overloaded. This handshake and teardown is state the client and server must maintain for the life of the connection, which matters a lot for load balancer design.

UDP

No handshake at all. You just send a packet, sometimes called "spray and pray." The receiver sees source IP/port, destination IP/port, and a binary payload. That's the entire contract. No ordering, no re-send, no flow control, and no congestion control by default, though protocols built on UDP (like QUIC) can add their own.

WebSocket Upgrade

1.Client sends HTTP GET with Upgrade header
2.Server responds 101 Switching Protocols
3.Connection now speaks WebSocket frames
4.Either side sends frames anytime
5.Stays open until either side closes it
Because it rides on the original TCP+HTTP handshake, WebSocket inherits cookies and auth from that initial HTTP request, which is convenient for reusing session info.
✅ When to Use / Use Cases

TCP

The default for basically everything: web pages, REST APIs, file transfer, databases, SSH, email. Anywhere correctness of the data matters more than shaving milliseconds off delivery. Any workflow with financial or state-changing consequences (payments, orders, inventory updates) needs TCP's guarantees, since a dropped or reordered byte can corrupt the result. Also the right choice whenever you need a simple mental model: write bytes in, read the same bytes out in order, on the other end.

UDP

Live video/audio streaming, online gaming position updates, VoIP, DNS lookups, and high-volume telemetry where occasional loss is acceptable. Also the base for custom protocols like QUIC (HTTP/3) that reimplement reliability themselves, more flexibly than TCP allows. Multicast and broadcast scenarios (sending one packet to many recipients at once) are only practical over UDP, since TCP is strictly point-to-point. Good fit whenever the newest update matters more than an old one, e.g. a player's current position; a stale position update arriving late is worse than useless, so no point retransmitting it.

HTTP vs WebSocket

HTTP for standard client-server request/response: REST APIs, loading web pages, most CRUD operations. WebSocket for high-frequency, persistent, bidirectional communication: chat apps, multiplayer games, live collaborative editing (Google Docs style), trading dashboards. A useful test: if you can describe the interaction as "the client asks, the server answers," reach for HTTP. If the server needs to speak first or speak often, unprompted, reach for WebSocket. HTTP/2 and HTTP/3 add server push and multiplexing, narrowing the gap somewhat, but they still don't give you a fully open bidirectional channel the way WebSocket does.
Interview nuance: real systems mix protocols. A video conferencing app might use TCP/HTTP for signaling and login, but UDP/WebRTC for the actual audio/video stream, because losing a video frame occasionally is fine but losing an auth token is not.
⚖️ Trade-offs

TCP vs UDP

TCP gives reliability and ordering, but pays for it with connection setup latency, more per-packet overhead (20 to 60 byte header vs UDP's 8 bytes), and head-of-line blocking: if one packet is lost, everything behind it waits. UDP gives speed and simplicity, but the application has to handle loss, ordering, and duplication itself, or just tolerate it.

HTTP vs WebSocket

HTTP is simple, cacheable, and stateless, which is good for horizontal scaling, but its request-response model means the server can never proactively push to the client. WebSocket gives real-time bidirectional push, but you now hold a stateful, persistent connection per client. That's expensive at scale (memory per connection) and constrains load balancing, and older proxies/firewalls sometimes don't support it well.

Cost Summary

TCP header: 20 to 60 bytes. UDP header: 8 bytes. TCP handshake: 1 extra round trip before data. WebSocket: 1 connection held open per client.
🚨 Failure Modes + Mitigations

Loss & Connection Failures

Packet loss (UDP): App-level tolerance, e.g. VoIP just drops the glitch. Connection state loss (WS): Reconnect with backoff, resync from last-seen message ID. TCP connection reset: Client retries with a fresh handshake. Partial message on disconnect: App-level framing so a receiver knows a message is incomplete.

Retry-Related Failures

Duplicate side effects on retry: Idempotency keys, e.g. for payments. Cascading retries (thundering herd): Exponential backoff with jitter. Retry storms after an outage: Circuit breakers to stop hammering a recovering service. Client timeout too aggressive: Tune timeout above p99 latency, not the average.

Infrastructure-Level Failures

Middleboxes killing idle connections: Heartbeat ping/pong frames. Slow start penalizing bursty traffic: Connection reuse (keep-alive, HTTP/2 multiplexing). NAT/firewall blocking UDP: Fall back to TCP, or use STUN/TURN for WebRTC. Load balancer drops sticky WS client: Client reconnect logic plus server-side session resync.
🚫 When NOT to Use

Don't use UDP

When you need guaranteed delivery or ordering, or need to support browsers without a fallback. Browsers don't support raw UDP outside of WebRTC.

Don't use WebSocket

Just because "real-time" sounds nice. If occasional server push (not high-frequency) is enough, SSE is much simpler and works over plain HTTP. If you don't need push at all, plain polling might be fine.

Interview Red Flag

Reaching for WebSocket without justifying it signals you didn't consider the operational cost of stateful connections at scale.
🗺️ Where It Fits in a System Diagram

Request Path

1.Client resolves domain via DNS
2.Connects through a Load Balancer
3.Hits an App Server
4.Talks to backend services / DB

L4 vs L7 Load Balancer

L4 forwards TCP connections blindly, which is good for WebSocket, since the same server must keep handling that client for the life of the connection. L7 terminates the connection and inspects the HTTP request itself, so it can route based on URL/headers/cookies, but that model doesn't naturally fit a long-lived bidirectional WebSocket.

Follow-up to Expect

If you design a system with WebSockets, expect a follow-up question on how your load balancer handles that.
🌍 Real-World Examples

TCP in the Wild

Web: HTTP/1.1, HTTP/2 (all over TCP). Databases: Postgres, MySQL client connections. Remote access: SSH, RDP. Messaging: Kafka's broker protocol.

UDP in the Wild

Naming: DNS lookups. Media: WebRTC audio/video. Gaming: Custom multiplayer position protocols. Modern web: QUIC, the transport under HTTP/3.

HTTP & WebSocket in the Wild

REST API: Elasticsearch, Stripe, most public APIs. Chat: Slack, Discord (WebSocket). Live state: Multiplayer games, trading dashboards.
Golden rule: default to TCP/HTTP/REST unless you have a specific reason not to. Interviewers want you to justify deviations, not show off knowledge for its own sake.
🎯 Interview-Grade Points to Internalize

Know Cold

Know the TCP vs UDP trade-off table cold. It's one of the most commonly probed comparisons in networking interviews. Be ready to explain header overhead (20 to 60 bytes for TCP vs 8 for UDP) and why that matters for high-frequency, small-payload traffic like game state updates.

Layering Understanding

WebSocket is an HTTP upgrade on an existing TCP connection, not a separate thing built from scratch. Saying this shows you understand the layering. Similarly, know that HTTP/3 changes the transport underneath (UDP via QUIC instead of TCP) while keeping the same HTTP semantics on top, which is a good example of clean layering.

"How would you scale WebSockets?"

L4 load balancing with least connections, not round robin, since connections are long-lived and unevenly loaded over time. Add a pub/sub layer, like Redis, so any server can push a message to a client connected to any other server in the fleet. Mention heartbeats to detect dead connections and horizontal sharding of connections across many WebSocket servers to bound memory per instance.
