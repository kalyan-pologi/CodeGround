Networking Essentials

🌐 Client-Server & P2P Architecture

Centralized vs decentralized: thin/thick clients, peer-to-peer networks, and when each fits.

📚 What It Is

Client-Server

A centralized model. Clients send requests, and a server (or cluster) holds the data and logic and responds. Roles are fixed: a client never serves another client directly, it always goes through the server.

Peer-to-Peer (P2P)

A decentralized model. Every node, called a peer, can act as both client and server, exchanging data directly with other peers. No single node is required for the system to keep functioning, though many real P2P systems still use a small coordination server.

Thin vs Thick Client

Thin: Minimal logic, server does almost all the work. Thick: Significant logic and state live on the client itself.
❓ Why Each Exists

Client-Server

Centralizing data and logic makes it easy to control access, keep data consistent across every user, and update behavior in one place instead of pushing an update to every client. It also makes reasoning about correctness far simpler: there's one source of truth, so conflicting writes and stale reads are much easier to prevent.

P2P

No single owner is needed to serve everyone. This distributes bandwidth and storage cost across participants, and removes a single point of control or failure for the network as a whole. It also grew out of situations where no company wanted to (or could afford to) bear the full cost of serving millions of large file downloads from a central origin.

Different Assumptions

The two models assume different things about trust and scale. Client-server assumes a trusted, capable server. P2P assumes there's no single trusted party but many peers willing to contribute resources. This is why P2P systems need extra mechanisms, like checksums and reputation, that client-server systems mostly get for free by trusting the server.
⚙️ How It Works

Client-Server

Client opens a connection to a known, fixed server address, sends a request, and gets a response back. The server side can be horizontally scaled behind a load balancer, so "the server" is often really a pool of many identical machines.

P2P

Peers first discover each other, using a tracker, a distributed hash table (DHT), or gossip protocol, then exchange data chunks directly with one another. No central server sits in the actual data path once peers have found each other.

Hybrid Systems

Many "P2P" systems still use a central server for discovery and coordination, like BitTorrent trackers, while the actual data transfer is peer-to-peer. This hybrid pattern gets most of P2P's bandwidth savings while keeping a simple, reliable bootstrap mechanism.
✅ When to Use

Client-Server

Most applications: web apps, mobile apps, APIs, and anything needing consistent state, access control, or centralized business logic. Also the right default whenever regulatory or compliance requirements demand a single, auditable place where data lives and access is controlled.

P2P

File sharing (BitTorrent), blockchain and crypto networks, video calls where WebRTC sends media directly between browsers, and CDN-like content distribution. Also useful for local-first collaboration tools syncing directly between nearby devices without round-tripping through a distant server.

Interview Default

Interview default: assume client-server unless the problem explicitly needs decentralization, such as no trusted central party, or fan-out cost that's too extreme for one origin to bear alone. If you do reach for P2P in an interview, be ready to justify it against the added complexity, since interviewers will push on whether it's actually necessary.
⚖️ Trade-offs

Client-Server

Simple to reason about and secure, since there's one place to enforce rules, but the server is a bottleneck and a single point of failure unless it's deliberately scaled and replicated. Operating cost also scales with usage in a predictable, centralized way, which makes capacity planning and billing simpler, but keeps that cost squarely on one owner.

P2P

Scales bandwidth with the number of users and is resilient to any single peer leaving, but it's much harder to secure, keeping data consistent across peers is hard, and peers are unreliable since they can disconnect at any time (churn). Debugging is also harder: there's no single log or dashboard showing the whole system's state, since that state is scattered across every participating peer.

Thin vs Thick Clients

Thin clients make upgrades easy: change the server and every client benefits immediately, but they need connectivity to function. Thick clients can work offline but are harder to keep consistently updated across a whole user base. Most modern apps land somewhere in between, keeping some logic and cached state on the client for responsiveness while treating the server as the source of truth.
🚨 Failure Modes + Mitigations

Client-Server

Server overload: Horizontal scaling behind a load balancer. Server is a single point of failure: Replicas plus automatic failover. Slow degradation under load: Autoscaling on CPU/latency thresholds.

P2P

Peer churn: Redundant chunk replication across many peers. Malicious or corrupt peers: Checksums and hash verification per chunk. Tracker/bootstrap node down: Multiple trackers or DHT-based discovery.
🚫 When NOT to Use

Skip P2P

Don't reach for P2P for typical CRUD apps. The complexity of NAT traversal, peer discovery, and keeping data consistent rarely pays off compared to a simple server. P2P also makes debugging and monitoring much harder, since there's no single place to look at what the whole system is doing.

Skip Pure Client-Server

Don't rely on pure client-server for massive, cost-sensitive fan-out of large files to millions of users at once. Consider a CDN or P2P-assisted delivery instead. A single origin serving every byte to every user doesn't scale economically once file sizes and audience size both grow large.

🌍 Real-World Examples

Client-Server

Almost everything: Every web and mobile app. APIs: Stripe, Twilio, most SaaS backends.

P2P

File sharing: BitTorrent. Crypto: Bitcoin, Ethereum. Media: WebRTC, early Skype.
