Question: Why can a Kubernetes pod be OOMKilled even when Java heap usage is below its maximum, and how would you troubleshoot JVM and container memory consumption?

Short answer

The container memory limit applies to total charged memory, not only Java heap. RSS can include heap, metaspace, JIT code cache, thread stacks, direct buffers, native/JNI allocations, GC structures, and other process memory. The kernel can kill the process when the cgroup limit is exceeded even if heap used is below -Xmx; in that case the JVM may not throw OutOfMemoryError or write a heap dump.

Internal working and investigation

  1. Confirm the termination reason and exit code with kubectl describe pod and kubectl get pod -o yaml. Distinguish OOMKilled from liveness-restart or node eviction.
  2. Compare the pod's memory limit with container working-set/RSS graphs and the JVM's heap used, heap committed, and configured max. Heap committed may be higher than heap used.
  3. Inspect thread count/stack size, direct buffer pools, metaspace, class loaders, code cache, and native libraries. Enable Native Memory Tracking before startup if its overhead is acceptable, then compare jcmd <pid> VM.native_memory summary over time.
  4. Leave headroom: do not set -Xmx equal to the pod limit. Size heap plus non-heap, native memory, and a safety margin from measured peak traffic.
  5. Fix the source of growth—unbounded buffers, excess threads, leaks, or large batch requests—before merely raising the limit.

Runnable Java 17 diagnostic example

Save as MemoryBudgetDemo.java. This prints JVM-reported values; the numeric values depend on your machine and flags.

import java.lang.management.ManagementFactory;
import java.lang.management.MemoryUsage;

public class MemoryBudgetDemo {
    public static void main(String[] args) {
        MemoryUsage heap = ManagementFactory.getMemoryMXBean().getHeapMemoryUsage();
        System.out.println("heapUsedMiB=" + heap.getUsed() / 1_048_576);
        System.out.println("heapCommittedMiB=" + heap.getCommitted() / 1_048_576);
        System.out.println("heapMaxMiB=" + heap.getMax() / 1_048_576);
        System.out.println("threads=" + ManagementFactory.getThreadMXBean().getThreadCount());
    }
}

Expected output shape: four labeled numeric lines, such as heapUsedMiB=1, heapCommittedMiB=16, heapMaxMiB=256, and threads=6. Those numbers are examples, not fixed results. This API does not report total container RSS.

Real-world commands and edge cases

kubectl describe pod <pod> -n <namespace>
kubectl top pod <pod> -n <namespace> --containers
jcmd <pid> VM.native_memory summary
jcmd <pid> GC.heap_info

Heap dumps diagnose heap retention, not every native allocation. NMT does not account for all third-party native allocations. Account for sidecars separately and verify whether the reported metric is usage, working set, or RSS before comparing graphs. Reproducing under a container with the same CPU/memory limits is more reliable than testing on an unconstrained laptop.

Common follow-up interview questions and answers

  • Why no heap dump? The kernel killed the container before the JVM could throw a Java OOM exception.
  • Is -Xmx the process memory limit? No; it only caps Java heap, not all JVM/native memory.
  • Can virtual threads help? They can reduce platform-thread stack pressure for many blocking tasks, but other memory and downstream limits remain.
  • What if memory rises while heap stays flat? Look at direct buffers, native/JNI memory, metaspace, threads, and mmap/page-cache behavior.

Interview-ready answer

OOMKilled is a container-level memory event, while -Xmx limits only Java heap. I would compare cgroup usage with heap used/committed and inspect threads, direct buffers, metaspace, code cache, and native memory. I would use pod events, JVM metrics, and NMT where available, then leave measured non-heap headroom below the pod limit and fix the growing allocation source.
