Question: How would you implement the producer-consumer pattern using BlockingQueue, Semaphore, wait(), notify(), notifyAll(), and CountDownLatch?

Short answer

Producers create work; consumers process it. A bounded BlockingQueue is the default choice because put() waits when full and take() waits when empty, giving natural backpressure. A Semaphore controls how many operations may run at once; a CountDownLatch coordinates one-time start or completion. wait()/notifyAll() can build a queue manually but require careful condition loops and monitor ownership.

Internal working, step by step

  1. Give the queue a finite capacity. This bounds memory and slows producers when consumers cannot keep up.
  2. Each producer calls put(item); each consumer calls take(). Queue operations provide thread-safe handoff and visibility.
  3. Choose a shutdown protocol: a poison pill per consumer, interruption, or an explicit “producers done and queue empty” condition.
  4. Use a semaphore only for a separate capacity, such as ten database calls, and release every permit in finally.
  5. Use a latch to release threads together or wait for a fixed number of workers. A latch cannot be reset; use a Phaser or CyclicBarrier for repeated phases.

Runnable Java 17 example

Save as ProducerConsumerDemo.java. Two producers publish 1–10, two consumers sum them, and a poison value stops each consumer.

import java.util.concurrent.*;
import java.util.concurrent.atomic.AtomicInteger;

public class ProducerConsumerDemo {
    static void await(CountDownLatch latch) {
        try { latch.await(); }
        catch (InterruptedException e) {
            Thread.currentThread().interrupt();
            throw new IllegalStateException(e);
        }
    }

    public static void main(String[] args) throws InterruptedException {
        BlockingQueue<Integer> queue = new ArrayBlockingQueue<>(3);
        CountDownLatch start = new CountDownLatch(1);
        AtomicInteger sum = new AtomicInteger();
        AtomicInteger count = new AtomicInteger();
        Thread[] producers = new Thread[2];
        Thread[] consumers = new Thread[2];

        for (int p = 0; p < 2; p++) {
            final int first = p * 5 + 1;
            producers[p] = new Thread(() -> {
                await(start);
                try {
                    for (int n = first; n < first + 5; n++) queue.put(n);
                } catch (InterruptedException e) { Thread.currentThread().interrupt(); }
            });
        }
        for (int c = 0; c < 2; c++) {
            consumers[c] = new Thread(() -> {
                await(start);
                try {
                    while (true) {
                        int n = queue.take();
                        if (n == -1) return;
                        sum.addAndGet(n);
                        count.incrementAndGet();
                    }
                } catch (InterruptedException e) { Thread.currentThread().interrupt(); }
            });
        }
        for (Thread t : consumers) t.start();
        for (Thread t : producers) t.start();
        start.countDown();
        for (Thread t : producers) t.join();
        queue.put(-1);
        queue.put(-1);
        for (Thread t : consumers) t.join();
        System.out.println("processed=" + count.get() + ", sum=" + sum.get());
    }
}

Expected output: processed=10, sum=55. Individual processing order is nondeterministic; the aggregate is not.

How the lower-level alternatives work

With a hand-built queue, use synchronized (lock), then while (queue.isEmpty()) lock.wait() in consumers and while (queue.isFull()) lock.wait() in producers. Mutate the queue and call lock.notifyAll() while holding the same monitor. Use while, not if, because a thread can wake spuriously or another thread can consume the condition first. notify() may wake the wrong kind of waiter when both producers and consumers share one monitor. Prefer BlockingQueue unless you truly need custom synchronization.

Real-world use and edge cases

A bounded queue separates request intake from a slower worker pool, but it does not make work durable; a process crash loses in-memory items. For durable jobs use a broker or database-backed queue. Define what happens when producers fail, consumers throw, shutdown begins, or the poison value could be valid data. Preserve interrupt status, avoid silently dropping tasks, and monitor queue depth and processing lag. A semaphore around downstream calls can cap concurrency independently of queue length.

Common follow-up interview questions and answers

  • What happens when a bounded queue is full? put() blocks; offer() can return false or time out, letting the caller apply an overload policy.
  • Why use notifyAll()? Multiple condition types may wait on one monitor; waking everyone lets each recheck its own condition.
  • Can a latch be reused? No. Its count only moves toward zero.
  • Does a semaphore protect shared data? A single permit can act like a mutex, but a multi-permit semaphore merely limits concurrency; it does not make arbitrary updates atomic.

Interview-ready answer

I would start with a bounded BlockingQueue: producers block or time out when it is full, consumers block when it is empty, and each consumer gets a clear shutdown signal. I use a semaphore for an independent downstream concurrency limit and a latch for one-time coordination. I use wait()/notifyAll() only when implementing a custom condition protocol, always testing conditions in a loop under the same monitor.
