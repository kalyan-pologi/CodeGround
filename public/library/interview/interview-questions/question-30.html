Question: A SQL query performs well with 100 records but becomes extremely slow with millions of records. How would you analyze execution plans, indexing, joins, and query optimization?

Short answer

Reproduce the slow query with representative data and parameters, then inspect its actual execution plan and time. Look for full scans, wrong row estimates, large sorts/hash joins, expensive nested loops, missing selective indexes, and unnecessary rows/columns. Tune the query and schema together, refresh statistics where appropriate, and measure again rather than assuming an index always helps.

Step-by-step diagnosis

  1. Capture the exact SQL, bind values, latency, returned row count, frequency, and database version. A query can be fast for one parameter and slow for another due to skew.
  2. Run EXPLAIN (ANALYZE, BUFFERS) in PostgreSQL on a safe representative system. Compare estimated versus actual rows and find where time and reads accumulate.
  3. Inspect predicates and join keys. An index on (tenant_id, created_at, id) can serve a tenant filter plus ordered pagination; leading-column order matters for B-tree indexes.
  4. Remove unnecessary SELECT *, limit early when semantically valid, avoid functions/casts on indexed columns when they prevent useful index access, and replace N+1 application queries.
  5. Check statistics, table bloat, partition pruning, memory for sorts/hashes, locks, and concurrent load. Re-run the plan after each change and compare p95 latency and write overhead.

Runnable Java 17 JDBC example

In a PostgreSQL JDBC project, the following code uses bind parameters so the database can execute the query safely. Replace the connection settings with your environment.

import java.sql.*;

public class RecentOrders {
    public static void main(String[] args) throws Exception {
        String sql = "select id from orders "
            + "where tenant_id=? and created_at >= ? "
            + "order by created_at, id limit ?";
        try (Connection db = DriverManager.getConnection(
                "jdbc:postgresql://localhost:5432/app", "app", "password");
             PreparedStatement query = db.prepareStatement(sql)) {
            query.setLong(1, 7);
            query.setTimestamp(2, Timestamp.valueOf("2026-01-01 00:00:00"));
            query.setInt(3, 20);
            try (ResultSet rows = query.executeQuery()) {
                int count = 0;
                while (rows.next()) count++;
                System.out.println("rows=" + count);
            }
        }
    }
}

Expected output shape: rows=0 through rows=20, depending on data. The query cannot return more than 20 rows. A useful supporting PostgreSQL index is CREATE INDEX ON orders (tenant_id, created_at, id);. Verify the real plan; an index is not guaranteed to be chosen for every data distribution.

Real-world edge cases

An index speeds reads but costs storage and write maintenance. Low-selectivity predicates may make a sequential scan cheaper. Joining two large tables without selective filters can produce a huge intermediate result. Deep OFFSET pagination still visits/skips many rows; keyset pagination may be better. EXPLAIN ANALYZE actually executes the query, so use caution with writes or expensive production statements. Always compare under representative concurrency, not just an empty test database.

Common follow-up interview questions and answers

  • Why did an index not help? The planner may estimate scanning is cheaper, or the query cannot use the index effectively.
  • Why are row estimates important? Wrong estimates can cause a poor join order or algorithm.
  • Can SELECT * hurt? Yes; it transfers more data and may prevent an index-only plan.
  • What is an N+1 query? One parent query followed by one child query per result, multiplying database round trips.

Interview-ready answer

I start with the exact slow SQL and representative data, then use the database's actual plan to find scans, join costs, sorts, and row-estimate errors. I align indexes with filters, join keys, and ordering, reduce unnecessary data, and check statistics and pagination. I measure the revised plan and end-to-end latency under load because an index or rewrite can help one query while hurting writes or another query.
