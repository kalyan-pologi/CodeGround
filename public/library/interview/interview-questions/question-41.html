Question: How would you prevent message loss and duplicate processing in Kafka using producer acknowledgments, idempotent producers, transactions, offset management, and delivery guarantees?

Short answer

Choose guarantees for each boundary. Configure durable topics and producer acks=all with idempotence so producer retries do not duplicate writes within Kafka's supported scope. Commit consumer offsets only after successful processing. Kafka transactions can atomically publish to Kafka and commit consumed offsets for Kafka-to-Kafka flows, but they do not automatically make an external database or payment provider part of the transaction. Use an outbox and idempotent consumers for those side effects.

Internal working and delivery modes

  • At-most-once: commit/advance before processing; a crash may lose work.
  • At-least-once: process then commit; a crash between the two can replay a record, so duplicates are possible.
  • Kafka exactly-once processing: transactional producer writes output records and consumed offsets atomically within Kafka. External systems still need their own atomic/deduplication design.

Idempotent producer sequencing lets the broker recognize retried batches from the same producer session. Acknowledgments and replication reduce loss risk; configuration must be consistent with desired durability. A committed offset records where the consumer will resume, not proof that every external side effect succeeded.

Runnable Java 17 configuration illustration

Save as KafkaConfigDemo.java. It prints a safe producer configuration; actual publishing requires the Kafka client dependency and a running cluster.

import java.util.Properties;

public class KafkaConfigDemo {
    public static void main(String[] args) {
        Properties producer = new Properties();
        producer.setProperty("acks", "all");
        producer.setProperty("enable.idempotence", "true");
        producer.setProperty("retries", "10");
        System.out.println("acks=" + producer.getProperty("acks"));
        System.out.println("idempotent=" +
            producer.getProperty("enable.idempotence"));
    }
}

Expected output:

acks=all
idempotent=true

Real-world processing sequence and edge cases

  1. Producer persists a business change and outbox event in one database transaction; relay sends with a stable event ID.
  2. Consumer begins its DB transaction, inserts (consumer_group,event_id) under a unique constraint, applies the business change, and commits.
  3. Only after DB success does it commit the Kafka offset. If it crashes before offset commit, replay is harmless because the DB dedupe row already exists.

Handle poison messages with bounded retries and a dead-letter path. Monitor under-replicated partitions, producer errors, lag, and dedupe rates. Kafka transactions need careful configuration and can be fenced on producer ownership changes. Never claim end-to-end exactly-once across Kafka, SQL, and an external provider without a specific cross-system protocol.

Common follow-up interview questions and answers

  • Does acks=all prevent duplicates? No; it is about acknowledgment durability. Producer idempotence and consumer deduplication address duplicates.
  • Why process before offset commit? A premature commit could skip unprocessed work after a crash.
  • Can a message still be replayed? Yes, especially after a consumer crash or rebalance; business side effects must tolerate it.
  • What does a transactional producer cover? Kafka records and consumed offsets participating in that Kafka transaction, not arbitrary database changes.

Interview-ready answer

I configure replicated topics, acks=all, and an idempotent producer for durable Kafka writes. Consumers process before committing offsets and make external side effects idempotent with event IDs and database uniqueness. Kafka transactions can give exactly-once Kafka-to-Kafka processing, but I use outbox plus deduplication when a database or provider is involved. I monitor errors, lag, and replay.
