Question: Write a Java program to demonstrate deadlock and explain how to prevent it using lock ordering or tryLock().

Short answer

Deadlock occurs when two threads each hold a lock the other needs. A stable global lock order removes the circular wait. ReentrantLock.tryLock(timeout) can also let a thread abandon/retry instead of waiting forever, but both acquired locks must be released correctly. The program below deliberately deadlocks daemon threads, detects them, and then shows a safe ordered operation; daemon threads let the demonstration exit.

Runnable Java 17 program

Save as DeadlockDemo.java.

import java.lang.management.ManagementFactory;
import java.lang.management.ThreadMXBean;
import java.util.concurrent.CountDownLatch;

public class DeadlockDemo {
    static void await(CountDownLatch latch) {
        try { latch.await(); }
        catch (InterruptedException e) {
            Thread.currentThread().interrupt();
            throw new IllegalStateException(e);
        }
    }
    static void takeOppositeLocks(Object first, Object second,
                                  CountDownLatch bothHolding) {
        synchronized (first) {
            bothHolding.countDown();
            await(bothHolding);
            synchronized (second) { /* unreachable after deadlock */ }
        }
    }
    static void ordered(Object low, Object high) {
        synchronized (low) {
            synchronized (high) { /* safe shared work */ }
        }
    }
    public static void main(String[] args) throws InterruptedException {
        Object a = new Object();
        Object b = new Object();
        CountDownLatch bothHolding = new CountDownLatch(2);
        Thread one = new Thread(() -> takeOppositeLocks(a, b, bothHolding));
        Thread two = new Thread(() -> takeOppositeLocks(b, a, bothHolding));
        one.setDaemon(true);
        two.setDaemon(true);
        one.start();
        two.start();
        bothHolding.await();

        ThreadMXBean monitor = ManagementFactory.getThreadMXBean();
        boolean detected = false;
        for (int i = 0; i < 100; i++) {
            if (monitor.findDeadlockedThreads() != null) {
                detected = true;
                break;
            }
            Thread.sleep(10);
        }
        System.out.println("deadlockDetected=" + detected);

        Object low = new Object();
        Object high = new Object();
        Thread safe1 = new Thread(() -> ordered(low, high));
        Thread safe2 = new Thread(() -> ordered(low, high));
        safe1.start();
        safe2.start();
        safe1.join();
        safe2.join();
        System.out.println("orderedCompleted=true");
    }
}

Expected output:

deadlockDetected=true
orderedCompleted=true

The detector normally sees the forced monitor cycle within the polling window. On an unusually stalled system, the first line could be false because diagnosis is time-bound; the deadlocked daemon threads still demonstrate the lock cycle.

Internal working and prevention

Thread one owns A and waits for B; thread two owns B and waits for A. Both have already passed the latch, so neither can proceed. The safe threads always acquire low before high, eliminating circular wait. For real entities, order by a unique immutable ID and use a tie-breaker when IDs can be equal. With tryLock, acquire the first lock, try the second for a bounded time, release the first in finally if the second fails, and retry with backoff. Avoid slow IO inside locks.

Common follow-up interview questions and answers

  • How diagnose production deadlock? Capture thread dumps or use ThreadMXBean.findDeadlockedThreads() to see owners and waiting locks.
  • Does tryLock guarantee progress? Not alone; repeated collisions can livelock without backoff or fairness.
  • What if locks are on different object instances? They do not coordinate shared state unless every path uses the same locks.
  • Can DB transactions deadlock too? Yes; database row locks also need consistent ordering and retry handling.

Interview-ready answer

Deadlock is circular waiting: each thread holds one lock and waits for the other. I prevent it by imposing one global lock acquisition order, keeping critical sections short, and using timed tryLock with safe release/retry when ordering is impractical. In production I inspect thread dumps or deadlock detection to identify the exact lock cycle.
