Question: How does dependency injection work in Spring, and how would you handle multiple beans, bean scopes, circular dependencies, and constructor vs. field injection?

Short answer

Dependency injection means a class declares what it needs and Spring's ApplicationContext supplies those objects. Prefer constructor injection for required dependencies: it makes them explicit, non-null after construction, and easy to replace in tests. When multiple beans match one type, use @Qualifier or a deliberate @Primary. Choose scopes intentionally and redesign circular dependencies rather than hiding them.

Internal working and design choices

  1. Component scanning and @Bean methods register bean definitions. On creation, the container resolves constructor arguments by type and qualifiers.
  2. A singleton is one bean instance per application context, not one per JVM. A prototype creates a new instance on lookup; request/session scopes belong to web contexts.
  3. If a singleton directly injects a prototype once, it does not magically get a new prototype on every method call. Use ObjectProvider or an appropriate scoped proxy when dynamic lookup is required.
  4. A → B → A constructor cycle cannot be satisfied. Break the cycle by separating responsibilities or introducing an event/interface boundary; @Lazy is a workaround, not usually a good design.

Runnable Spring Boot example

In a Spring Boot project with the core starter, place this in src/main/java/demo/DiDemo.java.

package demo;

import org.springframework.beans.factory.annotation.Qualifier;
import org.springframework.boot.CommandLineRunner;
import org.springframework.boot.SpringApplication;
import org.springframework.boot.autoconfigure.SpringBootApplication;
import org.springframework.context.annotation.Bean;
import org.springframework.stereotype.Component;
import org.springframework.stereotype.Service;

@SpringBootApplication
public class DiDemo {
    public static void main(String[] args) { SpringApplication.run(DiDemo.class, args); }

    @Bean
    CommandLineRunner demo(OrderService orders) {
        return args -> System.out.println(orders.confirmation());
    }
}

interface Notifier { String send(); }

@Component("emailNotifier")
class EmailNotifier implements Notifier {
    public String send() { return "email sent"; }
}

@Component("smsNotifier")
class SmsNotifier implements Notifier {
    public String send() { return "sms sent"; }
}

@Service
class OrderService {
    private final Notifier notifier;
    OrderService(@Qualifier("emailNotifier") Notifier notifier) {
        this.notifier = notifier;
    }
    String confirmation() { return notifier.send(); }
}

Expected application output: email sent. Without the qualifier, injection is ambiguous because two beans implement Notifier.

Real-world use and edge cases

Field injection hides required dependencies and makes plain unit construction harder; setter injection is appropriate for a truly optional dependency. Do not store per-request mutable state in a singleton service—concurrent requests share it. A request-scoped bean injected into a singleton needs a proxy/provider. An interface is useful when implementations vary, but do not create interfaces solely for every class without a reason. A very large constructor is a signal that the class may have too many responsibilities.

Common follow-up interview questions and answers

  • @Primary versus @Qualifier? Primary sets a default candidate; qualifier selects a named candidate at a specific injection point.
  • Is a Spring singleton thread-safe? Not automatically; concurrent callers share its mutable fields.
  • Why constructor injection? Required dependencies are explicit and the object is complete as soon as construction finishes.
  • Can Spring solve constructor cycles? It normally reports an unresolvable cycle; redesign the dependency graph.

Interview-ready answer

Spring registers bean definitions, resolves dependencies when creating beans, and injects them through constructors, setters, or fields. I prefer constructor injection for required collaborators. I resolve multiple implementations with qualifiers or a deliberate primary bean, choose scope based on lifetime, and keep singleton state thread-safe. A constructor cycle usually means the design should be split rather than patched with lazy injection.
