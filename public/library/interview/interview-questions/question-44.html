Question: How would you implement Redis caching using cache-aside, TTL, eviction, cache invalidation, and distributed locking while preventing stale data and cache stampedes?

Short answer

With cache-aside, read Redis first; on miss, load from the authoritative database and cache the result with a TTL. On a write, commit the database change and invalidate or update the cache according to a clear consistency policy. Bound Redis memory with an eviction policy and size monitoring. Prevent many simultaneous misses from overwhelming the database using single-flight, short-lived locks, TTL jitter, or early refresh, but never assume a cache is perfectly current.

Internal working, step by step

  1. Construct a stable key including tenant and schema/version where needed. GET it; deserialize only validated data.
  2. On miss, query the DB, then SET with a TTL. Cache “not found” briefly if safe to prevent repeated misses.
  3. For a write, update the DB transaction first, then delete the cache key. A crash between commit and deletion can leave stale data until TTL; use an event/outbox or versioning if a tighter guarantee is needed.
  4. Add TTL jitter to spread expirations, cap cache size, and choose an eviction policy matching the workload.
  5. For stampedes, one loader can acquire a short lease (SET key token NX PX ...); others wait briefly or serve acceptable stale data. Release only if the token still matches, typically with an atomic script.

Runnable Java 17 cache-aside illustration

Save as CacheAsideDemo.java. This local map models the read/invalidating sequence; Redis adds distributed storage, TTL, and eviction.

import java.util.Map;
import java.util.concurrent.ConcurrentHashMap;

public class CacheAsideDemo {
    static final Map<String, String> db = new ConcurrentHashMap<>();
    static final Map<String, String> cache = new ConcurrentHashMap<>();

    static String read(String key) {
        return cache.computeIfAbsent(key, db::get);
    }
    static void write(String key, String value) {
        db.put(key, value);
        cache.remove(key);
    }
    public static void main(String[] args) {
        write("product:7", "old");
        System.out.println(read("product:7"));
        write("product:7", "new");
        System.out.println(read("product:7"));
    }
}

Expected output:

old
new

The example has no TTL; production Redis commands must set one. computeIfAbsent also does not solve distributed stampedes across many app instances.

Real-world edge cases and follow-ups

A simple Redis lock is a lease, not a universal correctness guarantee. If a worker pauses past lock expiry, another worker may start; use fencing/version checks for operations where duplicate work is harmful. Never use a cache as the only financial source of truth. Measure hit rate, miss storm size, eviction count, memory, stale-read tolerance, and DB fallback latency. Avoid caching sensitive data without access controls and encryption policy.

  • What is a cache stampede? Many clients miss the same hot key at once and all query the origin.
  • Does deleting on write guarantee fresh reads? Not across every race or crash; TTL/versioning and invalidation ordering matter.
  • Why add TTL jitter? To prevent many keys expiring simultaneously.
  • What is eviction versus expiry? Expiry removes keys by TTL; eviction removes keys to satisfy memory policy.

Interview-ready answer

I use cache-aside with the database as source of truth, TTL-bounded entries, and invalidation after writes. I size Redis and watch evictions and hit rate. For hot-key misses I add single-flight or a short token-based lease with safe release and TTL jitter; for correctness-critical updates I use database constraints or versioning rather than trusting a distributed cache lock.
