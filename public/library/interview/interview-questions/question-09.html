Question: How do CompletableFuture, Future, and ExecutorService differ, and how would you execute and combine multiple asynchronous API calls with timeout and exception handling?

Short answer

ExecutorService owns and schedules tasks. Future represents one submitted result but is mainly a blocking handle. CompletableFuture is both a result and a composable pipeline: it supports transformations, combination, timeout, and recovery without blocking every step.

import java.time.Duration;
import java.util.concurrent.CompletableFuture;
import java.util.concurrent.Executors;

public class CompletableFutureDemo {
    public static void main(String[] args) {
        try (var pool = Executors.newFixedThreadPool(4)) {
            CompletableFuture<String> profile = CompletableFuture
                    .supplyAsync(() -> "profile", pool);
            CompletableFuture<String> balance = CompletableFuture
                    .supplyAsync(() -> "balance", pool);

            String result = profile.thenCombine(balance,
                            (p, b) -> p + "+" + b)
                    .orTimeout(2, java.util.concurrent.TimeUnit.SECONDS)
                    .exceptionally(error -> "fallback")
                    .join();

            System.out.println(result);
        }
    }
}

Expected output: profile+balance. If either operation fails or exceeds two seconds, the result becomes fallback.

Internal working and production rules

  • supplyAsync runs a value-producing task; runAsync runs a task with no result.
  • thenApply transforms a result; thenCompose flattens a dependent asynchronous call; thenCombine joins independent calls.
  • Use an application-owned executor for blocking or isolated work. The default common pool is not automatically safe for every workload.
  • orTimeout completes exceptionally after a deadline; it does not necessarily interrupt the underlying remote HTTP call. Configure the HTTP client timeout too.
  • Use handle, exceptionally, or exceptionallyCompose for recovery, and preserve enough context for logging and tracing.

Follow-up questions

  • Does Future.get() make work asynchronous? Submission may be asynchronous, but get blocks the caller. CompletableFuture enables non-blocking composition.
  • When use allOf? When many independent futures must all finish. It returns CompletableFuture<Void>, so collect the individual results separately.
  • How do you avoid resource leaks? Bound the executor, shut it down, configure client timeouts, and avoid creating an unbounded executor per request.

Interview-ready answer

ExecutorService schedules work, Future exposes a mostly blocking handle, and CompletableFuture composes asynchronous stages. I use an explicit bounded executor, start independent API calls concurrently, combine them with thenCombine or allOf, set both future and client timeouts, and recover or propagate failures deliberately.

Step-by-step orchestration

Imagine an order endpoint that needs customer, inventory, and pricing data. Customer and inventory are independent, so start them together. Pricing may depend on the customer tier, so compose it after the customer future. This avoids blocking the request thread while each remote call is waiting.

import java.util.concurrent.*;

public class ApiCompositionDemo {
    static CompletableFuture<String> call(String name, Executor executor) {
        return CompletableFuture.supplyAsync(() -> name, executor);
    }

    public static void main(String[] args) {
        ExecutorService pool = Executors.newFixedThreadPool(4);
        try {
            CompletableFuture<String> customer = call("customer", pool);
            CompletableFuture<String> inventory = call("inventory", pool);

            CompletableFuture<String> response = customer
                    .thenCombine(inventory, (c, i) -> c + "+" + i)
                    .orTimeout(1, TimeUnit.SECONDS)
                    .handle((value, error) -> error == null
                            ? value : "degraded-response");

            System.out.println(response.join());
        } finally {
            pool.shutdown();
        }
    }
}

Expected output: customer+inventory. If a stage fails or exceeds the timeout, the handler prints degraded-response.

Future versus CompletableFuture

TypeWhat it providesLimitation
ExecutorServiceTask submission, scheduling, pooling, shutdownMust size and operate the executor correctly
FutureCancellation, completion check, blocking getHard to compose several results without blocking
CompletableFutureNon-blocking transformations, combination, timeout, recoveryChains can become difficult to debug; executor choice still matters

thenApply maps a completed value, thenCompose chains a dependent future, thenCombine joins two independent futures, and allOf waits for many. The Async variants schedule the continuation asynchronously; the non-async variants may run it on the thread that completes the previous stage.

Timeout, cancellation, and exception behavior

  • orTimeout completes the future exceptionally; it does not guarantee that a remote socket call is interrupted.
  • completeOnTimeout supplies a fallback value, which is appropriate only when degraded data is safe.
  • exceptionally handles failures and returns a replacement value; handle receives either a value or error.
  • join throws an unchecked CompletionException; get throws checked exceptions and can be interrupted.
  • Cancellation is cooperative. Configure timeouts in the HTTP client, database driver, and load balancer as well as in the future.

Executor sizing and real-world safeguards

Use a bounded executor or a well-understood virtual-thread strategy. For CPU-bound work, start near the number of available processors. For blocking I/O, the pool can be larger, but it must be bounded by downstream capacity, connection pools, rate limits, and memory. Add correlation IDs, metrics for queue time and remote latency, retries only for transient errors, and a circuit breaker for unhealthy dependencies.

Additional follow-up answers

  • What is the difference between thenCompose and thenCombine? Compose is for a dependent second future; combine is for two futures that can run independently.
  • How do you collect results from allOf? Keep the typed futures, await allOf, then call join on each completed future.
  • Should every failure be retried? No. Retry only transient failures, use exponential backoff and jitter, and avoid retrying validation or authorization errors.
  • Why can async code still block? Calling join or get blocks the caller, and the task itself may block on I/O. Async composition does not make a blocking dependency non-blocking.
