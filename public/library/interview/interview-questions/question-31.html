Question: How do database transactions and ACID properties work, and how does Spring manage commits, rollbacks, isolation levels, propagation, and connection pooling?

Short answer

A transaction groups database operations into a unit that either commits or rolls back. ACID means atomicity, consistency with declared invariants, isolation from concurrent transactions, and durability after commit. Spring's transaction interceptor obtains a connection/entity manager from a pool, binds it to the current thread, and commits or rolls back at the method boundary. Propagation decides how nested service calls share transactions; isolation controls concurrent visibility as implemented by the database.

Internal working and trade-offs

  1. Acquire a connection, begin a transaction (often by disabling auto-commit), and run statements on that same connection.
  2. Commit on success; roll back on a qualifying exception. Spring's default declarative rollback is for unchecked exceptions and Error.
  3. REQUIRED joins an existing transaction; REQUIRES_NEW suspends it and needs an independent connection; NESTED uses savepoints when supported.
  4. Isolation such as read committed, repeatable read, or serializable trades anomalies against locks, retries, and throughput. The actual guarantees depend on the database.

Runnable Java 17 + H2 example

With H2 on the classpath, save as RollbackDemo.java. It demonstrates JDBC rollback, the operation Spring delegates to a transaction manager.

import java.sql.*;

public class RollbackDemo {
    public static void main(String[] args) throws Exception {
        try (Connection db = DriverManager.getConnection("jdbc:h2:mem:tx")) {
            db.createStatement().execute(
                "create table ledger(id int primary key, amount int)");
            db.setAutoCommit(false);
            try {
                db.createStatement().execute("insert into ledger values(1, 50)");
                throw new IllegalStateException("simulate failure");
            } catch (IllegalStateException e) {
                db.rollback();
            }
            db.setAutoCommit(true);
            try (ResultSet rows = db.createStatement().executeQuery(
                    "select count(*) from ledger")) {
                rows.next();
                System.out.println("rows=" + rows.getInt(1));
            }
        }
    }
}

Expected output: rows=0. A transaction requires all participating statements to use its managed connection; opening a separate connection may escape it.

Real-world edge cases

Keep transactions short and do not hold DB connections while waiting on slow remote services. REQUIRES_NEW can exhaust a small pool when outer transactions hold connections. A local DB transaction does not atomically commit Kafka or another microservice's database; use an outbox/saga where needed. Strong isolation does not replace unique constraints or business invariants. Retries after serialization failure must rerun the whole transaction and avoid duplicate external effects.

Common follow-up interview questions and answers

  • What is atomicity? All changes in the transaction commit together or are rolled back together.
  • Does Spring choose the isolation behavior? It requests an isolation level; the database enforces it.
  • Why can a caught exception still commit? The transaction proxy sees normal return unless code marks rollback-only.
  • Is a connection pool a transaction manager? No. The pool lends connections; the manager controls transaction boundaries.

Interview-ready answer

ACID transactions commit a consistent group of database changes or roll them back. Spring wraps externally invoked transactional methods, binds a pooled connection to the thread, and decides commit/rollback by its rules. I choose propagation and isolation based on the business invariant and database behavior, keep transactions short, size the pool for concurrency, and use an outbox/saga for work outside one database.
