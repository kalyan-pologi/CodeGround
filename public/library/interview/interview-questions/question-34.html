Question: How would you design a scalable payment processing system using Spring Boot, REST APIs, Kafka, Redis, databases, and load balancing to handle thousands of requests per second?

Short answer

Separate accepting a payment request from durable payment processing. Put Spring Boot instances behind a load balancer, require an idempotency key, validate/authenticate the request, and atomically store a payment record plus outbox event in a database. A relay publishes events to Kafka; workers process them with idempotent state transitions and an external payment provider. Redis may cache non-authoritative reads or rate-limit counters, but the database is the source of truth for money and duplicate prevention.

Flow and internal working

  1. Ingress: API Gateway/load balancer applies TLS, authentication, rate limiting, and routing to stateless instances. The API validates currency, amount in minor units, merchant, and idempotency key.
  2. Durability: in one DB transaction, insert a unique (merchant_id, idempotency_key) request record and an outbox event. Return a stable payment ID/status; repeat requests return the original result.
  3. Messaging: relay publishes the outbox event to Kafka with payment ID as key, preserving per-payment partition order. Consumers can see duplicates, so claim work with a unique constraint/state transition.
  4. Provider: call the processor with its own idempotency key and timeout. Persist success/failure/pending transitions and reconcile uncertain results via provider lookup/webhooks.
  5. Scale: partition Kafka work, tune DB indexes/pools, autoscale on queue lag and latency, and load-test at target RPS. Redis can help with read cache/rate limits but never replace a durable ledger.

Runnable Java 17 miniature

Save as PaymentIdempotencyDemo.java. This models duplicate-request behavior in one process; production uses a database uniqueness constraint across all instances.

import java.util.concurrent.ConcurrentHashMap;
import java.util.concurrent.atomic.AtomicInteger;

public class PaymentIdempotencyDemo {
    record Payment(String id, String status) {}
    static final ConcurrentHashMap<String, Payment> requests =
        new ConcurrentHashMap<>();
    static final AtomicInteger sequence = new AtomicInteger();

    static Payment create(String merchant, String key) {
        return requests.computeIfAbsent(merchant + ":" + key,
            ignored -> new Payment("pay-" + sequence.incrementAndGet(), "PENDING"));
    }

    public static void main(String[] args) {
        System.out.println(create("shop", "request-1"));
        System.out.println(create("shop", "request-1"));
        System.out.println("created=" + sequence.get());
    }
}

Expected output:

Payment[id=pay-1, status=PENDING]
Payment[id=pay-1, status=PENDING]
created=1

Real-world edge cases and follow-ups

Never treat a timeout as proof the provider did not charge; reconcile by idempotency key. Store money as exact decimal or integer minor units, not double. Keep a balanced ledger/audit trail and separate payment authorization from settlement/refund. Kafka is not a database transaction across your DB and the provider; outbox plus idempotent consumers handles the dual-write gap. Monitor authorization rate, provider latency, DB saturation, consumer lag, duplicate count, and reconciliation backlog.

  • Why not use Redis for the balance? Cache loss/eviction and stale reads are unacceptable as the sole financial source of truth.
  • How do you scale consumers? Add partitions and consumers after measuring processing time and downstream limits.
  • What if Kafka publish fails after DB commit? The outbox row remains for relay retry.
  • What if a provider webhook arrives twice? Deduplicate by provider event ID and enforce a legal state transition.

Interview-ready answer

I would use stateless Spring Boot APIs behind a load balancer, a durable payment table with unique idempotency keys, and a transactional outbox to Kafka. Workers would process keyed events idempotently, call the provider with a provider-side idempotency key, and reconcile uncertain outcomes. Redis would support cache or rate limits, not financial truth. I would scale only within DB/provider limits and monitor latency, lag, duplicates, and reconciliation.
