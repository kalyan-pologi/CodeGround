Question: A Java application crashes with OutOfMemoryError after running for several days. How would you identify memory leaks using heap dumps, GC logs, and profiling tools?

Short answer

First identify the exact failure: Java heap space, metaspace, direct buffer/native memory, or an OS/container kill. A heap that rises after each full collection suggests retained objects, but a large live set or a traffic spike is not automatically a leak. Capture a heap dump and GC/JFR evidence, compare retained objects and paths to GC roots, then fix the code that keeps them reachable.

Diagnosis, step by step

  1. Preserve the exception message, process/container memory graph, heap usage after GC, allocation rate, thread count, and deployment timeline.
  2. Configure -XX:+HeapDumpOnOutOfMemoryError and a protected -XX:HeapDumpPath with enough disk space; enable -Xlog:gc* and a bounded Java Flight Recorder recording. Dumps may contain secrets and personal data.
  3. Open the dump in a heap analyzer. Sort by retained size, not just shallow object count; inspect dominator tree and paths to GC roots. Compare an early and late dump to identify growing owners.
  4. Typical roots are static maps, caches without eviction, unclosed listeners, thread locals in long-lived pools, queues with producers faster than consumers, class loaders, and accidental ORM result accumulation.
  5. If heap is stable but resident memory grows, inspect direct buffers, thread stacks, metaspace, JNI/native allocations, and container limits. Native Memory Tracking can help for JVM-native allocations when enabled at startup.

Runnable Java 17 example: bound retained objects

Save as BoundedCacheDemo.java. A cache without an eviction rule would retain every entry as long as it remains reachable.

import java.util.LinkedHashMap;
import java.util.Map;

public class BoundedCacheDemo {
    public static void main(String[] args) {
        Map<Integer, byte[]> cache = new LinkedHashMap<>(16, 0.75f, true) {
            protected boolean removeEldestEntry(Map.Entry<Integer, byte[]> eldest) {
                return size() > 3;
            }
        };
        for (int i = 1; i <= 10; i++) cache.put(i, new byte[1_024]);
        System.out.println("entries=" + cache.size());
        System.out.println("oldestPresent=" + cache.containsKey(1));
    }
}

Expected output:

entries=3
oldestPresent=false

This is a local illustration. A production cache also needs concurrency behavior, expiry, metrics, and sizing by bytes rather than merely entry count.

Useful commands and edge cases

jcmd <pid> GC.heap_dump /secure/path/heap.hprof
jcmd <pid> Thread.print
jcmd <pid> VM.native_memory summary
# JVM startup examples:
-XX:+HeapDumpOnOutOfMemoryError -Xlog:gc*:file=/logs/gc.log:time,level,tags

A heap dump can pause the process and be very large; capture safely and restrict access. A single heap dump does not prove growth over time. Repeated full GCs with little memory reclaimed are evidence of pressure, not proof of a particular leak. Increasing -Xmx may delay failure but does not fix unbounded retention. A pod killed by the kernel may not produce a Java OutOfMemoryError or heap dump at all.

Common follow-up interview questions and answers

  • What is retained size? Memory that could become collectible if a particular object and everything uniquely reachable through it were removed.
  • What is a GC root? A starting reference such as a live thread stack, static field, or JVM handle that keeps an object reachable.
  • Can Java leak memory despite GC? Yes. GC cannot collect objects still strongly reachable even if the application no longer needs them.
  • What if heap usage is low? Investigate direct/native memory, thread stacks, metaspace, other processes, and container limits.

Interview-ready answer

I would classify the OOM first, compare post-GC live heap over time, and capture GC logs, JFR, and a protected heap dump. In the dump I would inspect dominators and paths to roots to find the owner retaining a growing collection, then reproduce and fix that retention. If the heap is stable, I would shift to native memory, threads, direct buffers, and container limits rather than assuming a heap leak.
