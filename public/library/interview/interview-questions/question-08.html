Question: How would you process millions of records efficiently using Java Streams, batching, and pagination without exhausting memory?

Short answer

Do not load all records into a collection. Read a bounded page, process it, write or publish a bounded batch, release references, and continue from a stable cursor. Prefer keyset pagination such as WHERE id > :lastId ORDER BY id LIMIT :size over large offsets.

import java.util.List;

public class BatchDemo {
    record Order(long id, String status) {}

    static List<Order> fetchAfter(long lastId, int size) {
        // In production this method executes a keyset-paginated SQL query.
        return List.of();
    }

    public static void main(String[] args) {
        long lastId = 0;
        int pageSize = 500;
        while (true) {
            List<Order> page = fetchAfter(lastId, pageSize);
            if (page.isEmpty()) break;

            page.stream()
                    .filter(order -> "READY".equals(order.status()))
                    .forEach(order -> System.out.println("process " + order.id()));

            lastId = page.get(page.size() - 1).id();
        }
    }
}

Important design points

  • Bound memory: keep page and batch sizes finite; do not call collect(toList()) over an unbounded source.
  • Stable ordering: use a unique, indexed cursor such as (created_at, id) so records are not skipped or repeated.
  • Batch writes: use JDBC batching or a bulk API and commit at a controlled boundary.
  • Backpressure: limit workers and queue capacity so a fast reader cannot overwhelm a slow database or downstream service.
  • Restartability: checkpoint the last successful cursor and make processing idempotent.

Offset pagination is simple but becomes slower as the offset grows and can shift when rows are inserted or deleted. Keyset pagination is usually faster and more stable. A database streaming cursor can also work, but configure fetch size, transaction scope, timeout, and driver behavior carefully.

Edge cases and follow-ups

  • Handle a record that changes while paging; define whether the job uses a snapshot, an upper-bound ID, or an eventually consistent view.
  • Retry failed batches without duplicating side effects. Use an idempotency key or a durable processing table.
  • Do not parallelize database reads blindly; connection pools and database locks are finite.
  • For a file, use Files.lines(path) with try-with-resources and process one bounded batch at a time.

Interview-ready answer

I process a bounded page at a time, use keyset pagination on an indexed stable key, transform the page with a stream, write in batches, and release references before reading the next page. I add backpressure, checkpoint the last successful cursor, and make retries idempotent. That keeps memory, database load, and recovery behavior predictable.

Why pagination strategy matters

With offset pagination, the database may scan or discard many rows before reaching a large offset. Inserts and deletes can also shift later pages. Keyset pagination starts from the last value already seen and uses an index:

SELECT id, status, amount
FROM orders
WHERE (created_at, id) > (:lastCreatedAt, :lastId)
ORDER BY created_at, id
LIMIT :pageSize;

The second column makes the cursor unique when multiple records have the same timestamp. The cursor must be saved only after the corresponding batch has completed successfully.

Batching without retaining data

import java.util.ArrayList;
import java.util.List;

public class StreamingBatchDemo {
    static void writeBatch(List<String> batch) {
        System.out.println("write " + batch);
    }

    public static void main(String[] args) {
        List<String> batch = new ArrayList<>(3);
        for (int id = 1; id <= 8; id++) {
            batch.add("record-" + id);
            if (batch.size() == 3) {
                writeBatch(batch);
                batch.clear();
            }
        }
        if (!batch.isEmpty()) writeBatch(batch);
    }
}

Expected output: write [record-1, record-2, record-3], then record-4 through record-6, then record-7 and record-8. Only the current batch is retained.

Transactions, checkpoints, and retries

  1. Read a page after the saved cursor.
  2. Validate and transform records without keeping the entire dataset.
  3. Write the batch in one bounded transaction or downstream request.
  4. Commit the side effect and checkpoint together when possible.
  5. Advance the cursor and continue.

If the process fails after writing but before checkpointing, the page may be retried. Therefore writes need an idempotency key, a unique constraint, an upsert, or a durable processed-record table. Increasing the page size improves throughput only until database locks, transaction logs, network payloads, or memory become the bottleneck.

Streams, cursors, and resource ownership

A stream backed by a database cursor owns an external resource. Always close it:

try (var rows = repository.streamOrders()) {
    rows.filter(Order::isReady)
        .forEach(this::process);
}

Do not return a lazy stream after its transaction or connection has closed. Also avoid opening one transaction for millions of records; use a deliberate transaction boundary and understand the consistency requirement.

Production edge cases

  • Records inserted during the job can be included twice or missed unless the job uses a snapshot, an upper-bound cursor, or a defined consistency policy.
  • A record deleted between page reads should be treated as a normal missing record or logged according to business rules.
  • Large text or binary columns can exhaust memory even with small row counts; select only required columns.
  • Parallel workers require bounded queues and separate connection limits. More workers can reduce performance by exhausting the database pool.
  • Monitor page latency, batch latency, cursor progress, retry count, memory, queue depth, and downstream errors.

Additional follow-up answers

  • What page size should you choose? Start with a measured value such as 100–1,000, then tune using memory, transaction duration, database latency, and payload size.
  • When is offset pagination acceptable? Small administrative screens or stable, small datasets where simplicity is more valuable than deep-page performance.
  • How do you provide progress? Track the stable cursor, processed count, failed count, and estimated upper bound; do not use only page number when rows can change.
  • How do you prevent a failed record from blocking the entire job? Isolate bad records into a quarantine or dead-letter table while preserving an auditable retry path.
