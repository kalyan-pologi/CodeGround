Question: A Spring Boot API becomes slow under high traffic even though CPU utilization is low. How would you investigate thread contention, connection pools, blocking calls, and resource exhaustion?

Short answer

Low CPU with high latency usually means requests are waiting rather than computing. Check where the time goes: servlet worker queue, locks, database connection acquisition, SQL execution, downstream HTTP calls, and retry storms. Correlate request traces with pool utilization, thread dumps, and p95/p99 latency before increasing thread counts.

Step-by-step investigation

  1. Compare traffic, errors, p95/p99 latency, active requests, and throughput before and after the regression. Separate endpoint and dependency latency.
  2. Inspect repeated thread dumps. Many WAITING threads on a pool indicate resource scarcity; many BLOCKED threads on one monitor indicate contention.
  3. Inspect JDBC pool active/idle/pending metrics, acquisition time, slow-query logs, database locks, and connection leaks. A 10-connection pool can bottleneck 200 request workers.
  4. Inspect outbound HTTP timeouts, DNS/TLS time, retry counts, Kafka lag, and external rate limits. A missing timeout can hold a worker indefinitely.
  5. Apply one targeted fix: optimize SQL, bound concurrency, adjust a correctly sized pool, remove a coarse lock, add a timeout, or return controlled overload. Load-test the result.

Runnable Java 17 example: a scarce downstream resource

Save as DownstreamLimitDemo.java. A semaphore models a one-connection dependency. The second request cannot acquire it while the first holds it.

import java.util.concurrent.Semaphore;

public class DownstreamLimitDemo {
    public static void main(String[] args) {
        Semaphore connections = new Semaphore(1);
        boolean first = connections.tryAcquire();
        boolean second = connections.tryAcquire();
        System.out.println("first=" + first + ", second=" + second);
        if (first) connections.release();
        System.out.println("retry=" + connections.tryAcquire());
    }
}

Expected output: first=true, second=false followed by retry=true. A real service should use timed acquisition and release in finally; a leaked permit resembles a leaked connection.

Real-world fixes and edge cases

Expose secured Spring Boot Actuator health and metrics, trace a request across DB and HTTP dependencies, and record pool wait separately from SQL time. Increasing Tomcat threads may make latency worse if the database is already saturated. Virtual threads may reduce thread cost while waiting but do not expand the DB pool. Cache only when consistency and invalidation are defined. Keep circuit breakers and bounded retries around remote calls; retrying every request against a failing service magnifies overload.

Common follow-up interview questions and answers

  • Why low CPU? Threads may be blocked on IO, locks, pool acquisition, or rate limits rather than running on cores.
  • Would more request threads help? Only if the bottleneck is worker availability and downstream capacity can serve more concurrent work.
  • Which pool metric matters most? Active/idle, pending borrowers, acquisition time, and timeouts together reveal pressure.
  • What is the fastest diagnostic? A trace plus a thread dump during the slow period often narrows the waiting point quickly.

Interview-ready answer

I would treat low CPU and high latency as a waiting problem. I would trace requests, inspect thread dumps, JDBC pool pending/acquisition metrics, slow SQL, locks, and outbound-call timeouts. Then I would fix the saturated dependency or contention point and enforce backpressure, rather than blindly increasing threads. I would verify the change with production-like load and p99 latency.
