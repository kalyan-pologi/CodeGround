Question: How would you design efficient pagination, composite indexing, partitioning, and sharding for a database table containing 100 million records?

Short answer

Start with real access patterns, retention, and latency targets; 100 million rows alone does not require sharding. Use selective indexes aligned with filters and ordering, bounded pages, and keyset/cursor pagination for deep sequential browsing. Partition when pruning or maintenance by date/tenant genuinely helps. Shard only after one database cannot meet measured capacity or availability requirements, because cross-shard queries and transactions become much harder.

Design, step by step

  1. Identify common queries such as “recent orders for one tenant,” their selectivity, sort order, and expected page size.
  2. For WHERE tenant_id=? ORDER BY created_at DESC, id DESC, test a composite B-tree index on (tenant_id, created_at DESC, id DESC). The leading tenant column helps narrow the scan.
  3. Use a unique tie-breaker (id) in the sort and cursor. Deep OFFSET can require scanning many skipped rows and can shift as rows are inserted.
  4. Partition by a stable key such as time only if queries can prune partitions and operations benefit. Maintain indexes, retention, and statistics on each partition.
  5. If sharding is necessary, choose a stable shard key (often tenant ID), plan rebalancing/hot-tenant handling, and define how global analytics and uniqueness work.

Runnable Java 17 cursor example

Save as CursorDemo.java. This in-memory example illustrates the “after last seen ID” idea; SQL performs the actual indexed scan.

import java.util.List;

public class CursorDemo {
    static List<Integer> page(List<Integer> descendingIds, int afterId, int size) {
        return descendingIds.stream()
            .filter(id -> id < afterId)
            .limit(size)
            .toList();
    }

    public static void main(String[] args) {
        List<Integer> ids = List.of(105, 104, 103, 102, 101);
        System.out.println(page(ids, Integer.MAX_VALUE, 2));
        System.out.println(page(ids, 104, 2));
    }
}

Expected output:

[105, 104]
[103, 102]

In SQL, use a tuple cursor such as WHERE tenant_id=? AND (created_at,id) < (?,?) ORDER BY created_at DESC,id DESC LIMIT 20 with matching index and consistent timestamp/ID types.

Real-world edge cases

Cursor tokens should be opaque or signed and include all filter/sort values. Inserts and deletes can still affect a live feed; define whether pages reflect a snapshot. A composite index is most effective when query predicates constrain its leading columns. Too many indexes slow writes. Partitioning is not automatic query speedup if predicates cannot prune; sharding adds routing, cross-shard joins, distributed uniqueness, and operational cost. Measure before introducing it.

Common follow-up interview questions and answers

  • Why keyset over deep offset? It can seek from an indexed cursor instead of skipping millions of rows.
  • Why include ID in ordering? Timestamps can tie; a unique tie-breaker prevents ambiguous page boundaries.
  • Does partitioning replace indexes? No. Queries may still need indexes within selected partitions.
  • What makes a shard key bad? Hotspots, frequent moves, or queries that require fan-out to all shards.

Interview-ready answer

I would design from actual query patterns, create composite indexes matching tenant/filter/order fields, cap page size, and use keyset pagination for deep browsing. I would partition only where pruning and lifecycle management help, and shard only after measuring a single database's limits. The shard key, rebalancing, global uniqueness, and cross-shard queries must be designed before distributing the data.
