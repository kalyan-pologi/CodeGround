Question: How does Java garbage collection work, and how would you compare and tune G1GC, ZGC, and other collectors for throughput and low latency?

Short answer

GC finds objects no longer reachable from roots and reclaims their memory. Most Java collectors exploit the observation that many objects die young, but their algorithms trade CPU, memory overhead, throughput, and pause time differently. G1 balances throughput with pause goals using heap regions; ZGC targets very short pauses by doing much work concurrently. Choose from measured application latency and allocation behavior, not a universal “best GC” claim.

Internal working, step by step

  1. New objects are usually allocated cheaply in a thread-local allocation buffer or the young generation.
  2. GC traces from roots such as thread stacks and static references. Unreachable objects can be reclaimed; reachable objects may be copied, marked, or compacted depending on the collector.
  3. Young collections handle short-lived objects. Long-lived objects eventually occupy old-generation space. A too-small heap or excessive live set increases collection frequency and pressure.
  4. Stop-the-world phases pause application threads; concurrent phases run alongside them but use CPU and memory. Compare p99/p999 latency and throughput, not only average pause duration.

Runnable Java 17 example: reachability

Save as ReachabilityDemo.java. This demonstrates when a reference stops retaining an object; it does not predict when a collector will run.

import java.util.ArrayList;
import java.util.List;

public class ReachabilityDemo {
    public static void main(String[] args) {
        List<byte[]> retained = new ArrayList<>();
        for (int i = 0; i < 3; i++) retained.add(new byte[1_024]);
        System.out.println("reachable=" + retained.size());
        retained.clear();
        System.out.println("reachableThroughList=" + retained.size());
    }
}

Expected output:

reachable=3
reachableThroughList=0

After clear(), those arrays are eligible for collection if no other strong references exist. Their actual collection time is deliberately unspecified; avoid treating System.gc() as a correctness mechanism.

Tuning and real-world edge cases

Start with a supported JDK, sensible -Xmx and container headroom, then collect -Xlog:gc*, allocation rate, live-set size, pause percentiles, and CPU. G1 often needs only heap sizing and a pause target such as -XX:MaxGCPauseMillis; a goal is not a hard guarantee. Consider ZGC when strict tail-latency targets justify its trade-offs. Test under production-like load and compare throughput, p99 latency, GC CPU, RSS, and failure modes. A memory leak, oversized cache, or too many queued requests must be fixed in application behavior before collector tuning helps.

Common follow-up interview questions and answers

  • Does GC prevent all memory leaks? No. Strongly reachable but useless objects remain live.
  • Does a larger heap always help? It may reduce collection frequency but raises memory cost and can hide unbounded retention.
  • Why compare tail latency? A small average pause can hide occasional long pauses that violate an API's SLA.
  • Can you tune GC without logs? It is guesswork; use GC logs, heap and allocation metrics, and workload experiments.

Interview-ready answer

GC reclaims objects that are no longer reachable from roots. I compare collectors against a real workload: G1 is a general balance of throughput and pause goals, Parallel favors throughput, and ZGC targets very low pauses with concurrent-work overhead. I first measure live set, allocation rate, GC logs, CPU, and p99 latency, then tune heap and collector settings one change at a time. I do not expect GC tuning to fix an application leak or an undersized container.
