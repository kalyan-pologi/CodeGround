Question: A Kubernetes pod repeatedly crashes, restarts, or fails health checks. How would you troubleshoot it using kubectl, logs, resource limits, readiness probes, and liveness probes?

Short answer

First determine whether the container process exits, the kernel OOM-kills it, or kubelet restarts it after a failed startup/liveness probe. Use Pod status, events, previous-container logs, and probe configuration. Readiness failure removes a Pod from Service traffic but normally does not restart it; liveness failure can trigger restart. Fix the specific cause rather than increasing every timeout.

Investigation, step by step

  1. kubectl get pods -n app -o wide shows phase, restarts, node, and readiness. kubectl describe pod NAME -n app shows events and last termination reason/exit code.
  2. kubectl logs NAME -n app --previous gets logs from the container that just crashed; current logs can be from a new process.
  3. If OOMKilled, compare memory limit, JVM heap and non-heap use, direct buffers, and thread count. If the process exits normally/with error, inspect startup config, migrations, secrets, and dependency connectivity.
  4. If probes fail, check path, port, timeout, initial delay, and whether the endpoint represents startup, liveness, or readiness. Probe from inside the Pod and inspect server bind address.
  5. Confirm image tag/digest and rollout history, then fix config or roll back. Observe readiness and restart count after the change.

Runnable diagnostic commands

kubectl get pods -n app -o wide
kubectl describe pod orders-abc -n app
kubectl logs orders-abc -n app --previous
kubectl get pod orders-abc -n app -o jsonpath='{.status.containerStatuses[0].lastState.terminated.reason}'
kubectl rollout history deployment/orders -n app

Expected output shape: the JSONPath command may print OOMKilled, Error, or nothing if there is no previous termination. Events may show Unhealthy probe failures; logs reveal the app-side cause. Do not assume a blank result means success.

Real-world edge cases

A startup probe protects slow-starting apps from premature liveness restarts. A readiness probe that depends on a flaky external service may remove all replicas from traffic; design it to reflect ability to serve safely. A too-aggressive liveness probe can create a restart loop during temporary slowness. Resource requests affect scheduling; memory limits can cause OOM kills. CPU limits may throttle a pod and make probes time out even without high observed CPU. Inspect node pressure and sidecars too.

Common follow-up interview questions and answers

  • Does readiness failure restart a container? Normally no; it marks the Pod unready for Service routing.
  • Why use --previous? To see logs from the terminated instance during a restart loop.
  • What is CrashLoopBackOff? Kubelet is backing off repeated container restarts; inspect the underlying exit reason.
  • Can low heap usage still mean OOMKilled? Yes; the container limit includes non-heap/native memory.

Interview-ready answer

I start with Pod status, events, last termination reason, and previous-container logs to distinguish app crash, OOM kill, and probe-triggered restart. I compare probe path/timing with startup behavior and inspect resource limits and JVM memory. Readiness controls traffic; liveness controls restart. I fix the confirmed root cause or roll back, then verify stable ready replicas and no new restarts.
