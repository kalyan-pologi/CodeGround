Question: How does HashMap work internally, and what happens during hash collisions, resizing, and concurrent modification?

Short answer

HashMap stores key-value pairs in an array of buckets. It hashes the key, converts the hash into a bucket index, and then searches that bucket using equals. If two keys map to the same bucket, a collision is handled by storing multiple entries in that bucket. In modern Java, a crowded bucket can change from a linked list into a balanced red-black tree. When the map grows past its threshold, it resizes and redistributes entries. Its iterators are fail-fast: structural modification during iteration usually throws ConcurrentModificationException, but this is a best-effort bug detector rather than a thread-safety guarantee.

Start with the basics

What is a map?

A map associates a unique key with a value. For example, an employee ID can identify an employee record:

Map<Integer, String> employees = new HashMap<>();
employees.put(101, "Maya");
employees.put(102, "Luis");

System.out.println(employees.get(101)); // Maya
  • Keys are unique. Adding the same key replaces its old value.
  • Values may repeat.
  • HashMap permits one null key and multiple null values.
  • It does not guarantee insertion order. Use LinkedHashMap for insertion/access order or TreeMap for sorted keys.
  • It is not synchronized and should not be shared for concurrent writes without coordination.

Internal structure

A simplified map looks like this:

table
  [0] - empty
  [1] - Entry(keyA, valueA) -> Entry(keyB, valueB)
  [2] - empty
  [3] - TreeNode(keyC, valueC)
  ...

Each entry contains a key, value, hash, and a link to the next entry when the bucket uses a linked list. The implementation uses internal node classes, but this is the useful mental model:

class Entry<K, V> {
    final int hash;
    final K key;
    V value;
    Entry<K, V> next;
}

Step 1: Hash the key

When you call put(key, value) or get(key), Java obtains the key's hash code and spreads high bits into low bits so more of the hash participates in bucket selection. The conceptual Java 8+ operation is:

int h = key.hashCode();
int spreadHash = h ^ (h >>> 16);

This matters because bucket selection uses the low bits. A key whose hashCode() differs mostly in high bits can still be distributed more evenly after spreading.

Step 2: Calculate the bucket index

For a table length n, HashMap conceptually calculates:

int index = (n - 1) & spreadHash;

The table length is kept as a power of two, such as 16, 32, or 64. That lets a bitwise AND replace a slower remainder operation. This is an implementation detail; application code should never depend on a specific bucket number.

Step 3: Search the bucket

HashMap first compares the stored hash. If the hash matches, it compares keys using identity or equals:

if (storedHash == requestedHash
        && (storedKey == requestedKey
            || requestedKey.equals(storedKey))) {
    return storedValue;
}
  • hashCode narrows the search to a bucket.
  • equals identifies the exact key inside that bucket.

Hash collisions

A collision occurs when different keys select the same bucket. A collision is not automatically an error. HashMap stores both entries in that bucket and uses equals to distinguish them.

Runnable collision example

import java.util.HashMap;
import java.util.Map;

public class HashCollisionDemo {
    static final class Key {
        private final String name;

        Key(String name) {
            this.name = name;
        }

        @Override
        public int hashCode() {
            return 42; // Deliberately force a collision.
        }

        @Override
        public boolean equals(Object other) {
            return other instanceof Key key && name.equals(key.name);
        }

        @Override
        public String toString() {
            return name;
        }
    }

    public static void main(String[] args) {
        Map<Key, Integer> scores = new HashMap<>();
        scores.put(new Key("A"), 10);
        scores.put(new Key("B"), 20);

        System.out.println(scores.get(new Key("A")));
        System.out.println(scores.get(new Key("B")));
        System.out.println(scores.size());
    }
}

Expected output:

10
20
2

All keys return the same hash, but equals still separates A from B. With a small number of collisions, the bucket is commonly a linked list. In Java 8 and later, a sufficiently crowded bucket can be treeified into a red-black tree, improving a long collision search from approximately O(n) to O(log n).

Treeification details

OpenJDK implementations commonly use these thresholds:

  • TREEIFY_THRESHOLD = 8: a bucket may be converted to a tree when it becomes crowded.
  • UNTREEIFY_THRESHOLD = 6: a tree can become a list again after removals.
  • MIN_TREEIFY_CAPACITY = 64: before treeifying, HashMap prefers resizing if the table is still small.

These are implementation details, not API contracts. The practical interview point is that good hash distribution matters, and modern Java has a tree fallback for unusually long collision chains.

Resizing and load factor

HashMap starts with a table capacity and a load factor. The default load factor is 0.75. The resize threshold is approximately:

threshold = capacity * loadFactor

With capacity 16 and load factor 0.75, the map resizes when it grows beyond roughly 12 entries. Resizing normally doubles the table capacity. Entries are redistributed because the new index can change when the table length changes.

Why does resizing cost time?

Adding one entry is usually O(1), but resizing requires visiting existing entries. That individual operation is expensive, so HashMap has amortized O(1) insertion rather than a strict O(1) guarantee for every call. If you know the expected size, choose an appropriate initial capacity:

Map<String, Integer> counts = new HashMap<>(1_000);

Do not blindly use a huge capacity. It consumes memory and can make iteration more expensive. Capacity, load factor, key distribution, and actual workload should guide tuning.

Duplicate keys and nulls

Map<String, String> users = new HashMap<>();
users.put("u1", "old email");
String previous = users.put("u1", "new email");

System.out.println(previous);
System.out.println(users.get("u1"));

Expected output:

old email
new email

The key remains one entry. The new value replaces the old value, and put returns the previous value. A plain HashMap also permits one null key, while ConcurrentHashMap rejects null keys and values.

Concurrent modification

What does fail-fast mean?

HashMap iterators track a modification count. A structural change such as adding or removing a mapping changes that count. The iterator remembers the count from its creation and usually throws ConcurrentModificationException if it detects a mismatch.

import java.util.HashMap;
import java.util.Map;

public class ConcurrentModificationDemo {
    public static void main(String[] args) {
        Map<String, Integer> values = new HashMap<>();
        values.put("keep", 1);
        values.put("remove", 2);

        for (String key : values.keySet()) {
            if (key.equals("remove")) {
                values.remove(key); // Usually throws ConcurrentModificationException.
            }
        }
    }
}

Typical result:

Exception in thread "main" java.util.ConcurrentModificationException

The exception is not a guarantee that every unsafe modification will be detected. It is a best-effort fail-fast check. It does not make HashMap thread-safe.

Safe removal during iteration

values.entrySet().removeIf(entry -> entry.getKey().equals("remove"));

Or use the iterator's own removal operation:

var iterator = values.entrySet().iterator();
while (iterator.hasNext()) {
    if (iterator.next().getKey().equals("remove")) {
        iterator.remove();
    }
}

What if multiple threads access the map?

Concurrent reads are not a substitute for safe publication and coordinated writes. Concurrent writes can race, lose updates, and interact badly with resizing. Use the collection that matches the requirement:

  • ConcurrentHashMap for a general-purpose concurrent map.
  • Collections.synchronizedMap for a synchronized wrapper; iteration still requires external synchronization.
  • An immutable map such as Map.of when data never changes.
  • A database or distributed cache when state must be shared across application instances.

HashMap versus ConcurrentHashMap

import java.util.concurrent.ConcurrentHashMap;

var counts = new ConcurrentHashMap<String, Integer>();
counts.merge("orders", 1, Integer::sum);
counts.merge("orders", 1, Integer::sum);

System.out.println(counts.get("orders"));

Expected output:

2

merge makes the read-update-write operation atomic for that key. ConcurrentHashMap also provides weakly consistent iterators: they do not normally throw ConcurrentModificationException, and they may reflect some updates that happen during iteration.

Key correctness rules

Why must keys be immutable?

If a key changes in a way that affects equals or hashCode after insertion, the map may no longer find the entry in the bucket where it was placed.

import java.util.HashMap;
import java.util.Map;

public class MutableKeyDemo {
    static final class UserKey {
        String id;
        UserKey(String id) { this.id = id; }
        @Override public int hashCode() { return id.hashCode(); }
        @Override public boolean equals(Object o) {
            return o instanceof UserKey k && id.equals(k.id);
        }
    }

    public static void main(String[] args) {
        UserKey key = new UserKey("A");
        Map<UserKey, String> map = new HashMap<>();
        map.put(key, "Alice");
        key.id = "B";

        System.out.println(map.get(key));
        System.out.println(map.containsKey(key));
    }
}

Typical output:

null
false

The entry may still physically exist, but the changed key now hashes to a different location. Prefer immutable key types such as String, enums, records with immutable components, or carefully designed value objects.

equals and hashCode contract

  • If two objects are equal, they must have the same hash code.
  • Unequal objects may share a hash code; that is a collision, not a contract violation.
  • If a key's equality-relevant state changes while it is in the map, lookup behavior becomes unsafe.

Real-world examples

  • Request deduplication: map an idempotency key to a completed response, but use a database uniqueness constraint when multiple application instances can receive the same request.
  • Configuration lookup: map a property name or enum to a typed setting. Make the map immutable after startup if request threads read it.
  • Local cache: map a product ID to a cached value with explicit expiration and a concurrency strategy. A plain HashMap is not a production cache.
  • Counting: use merge in a single-threaded map, or ConcurrentHashMap.merge for concurrent counters.
  • Database identity map: use an entity ID as a stable key, not a mutable field such as a display name.

Common follow-up interview questions and answers

1. Why are HashMap capacities powers of two?

Power-of-two capacity allows the efficient index calculation (n - 1) & hash. Resizing also lets entries stay in the old index or move by the old capacity based on one additional hash bit.

2. What happens if two keys have the same hash code?

They go to the same bucket. HashMap then uses equals to decide whether the key is the same or whether this is a separate entry. Different keys with the same hash are valid.

3. What happens if equals is overridden but hashCode is not?

Equal objects may produce different hashes and land in different buckets. A lookup using an equal object can fail. Always override both consistently.

4. What happens if hashCode is overridden but equals is not?

Different objects can collide more often, and logically equivalent keys may not replace one another. The map may still function, but it will not represent the intended key identity.

5. Is HashMap synchronized?

No. Use ConcurrentHashMap, a synchronized wrapper, external locking, immutable data, or a distributed store depending on scope and consistency requirements.

6. Can HashMap have a null key?

Yes, one null key and multiple null values. ConcurrentHashMap does not allow null keys or values because null would be ambiguous with “no mapping” during concurrent operations.

7. Why does ConcurrentModificationException happen?

An iterator detected a structural modification not performed through that iterator. It is a fail-fast diagnostic, not proof that every concurrent modification was detected.

8. Does changing a value count as structural modification?

Replacing the value for an existing key usually does not change the map's structure. Adding or removing a mapping does. Do not rely on implementation-specific details when designing concurrent code.

9. HashMap versus Hashtable?

Hashtable is a legacy synchronized map that disallows null keys and values. Prefer HashMap for single-threaded use and ConcurrentHashMap for concurrent use.

10. HashMap versus LinkedHashMap versus TreeMap?

HashMap optimizes general lookup without order, LinkedHashMap preserves insertion or access order, and TreeMap keeps keys sorted using natural ordering or a comparator.

11. Why should initial capacity be chosen carefully?

Too little capacity causes repeated resizing; too much wastes memory and can make iteration scan many empty buckets. Estimate expected entries and account for the load factor.

12. Does HashMap protect against malicious collisions?

Modern Java's tree bins reduce the impact of very long collision chains, but application code should still use good key types and avoid attacker-controlled pathological hashing where possible. Hashing is not a substitute for input validation or rate limiting.

Interview-ready answer

HashMap stores entries in an array of buckets. It spreads the key's hash, selects a bucket with a bitwise index calculation, and uses hash plus equals to find the exact key. Different keys can collide in one bucket; the bucket is normally a linked list and can become a red-black tree when it is crowded. HashMap resizes when size exceeds capacity times load factor, usually doubling capacity and redistributing entries, so puts are O(1) amortized rather than guaranteed O(1) individually. HashMap is not thread-safe. Its iterators are fail-fast and may throw ConcurrentModificationException when the map is structurally changed during iteration, but that is only a best-effort diagnostic. For concurrent access I would use ConcurrentHashMap and atomic operations such as merge or compute.

Quick checklist

  • Know the path: hashCode -> spread -> bucket index -> hash/equality check.
  • Know collisions: list first, tree fallback in modern Java.
  • Know resizing: threshold is approximately capacity times load factor.
  • Know the contract: equal keys must have equal hashes; keys should be effectively immutable.
  • Know concurrency: HashMap is unsafe for concurrent writes; fail-fast is not synchronization.
  • Know alternatives: LinkedHashMap, TreeMap, ConcurrentHashMap, synchronizedMap, and immutable maps.

Question: How do equals(), hashCode(), ==, and compareTo() differ, and what happens when they are implemented incorrectly?

Short answer

== compares primitive values or object references. equals compares logical equality when a class overrides it. hashCode supplies a hash used by hash-based collections and must agree with equals. compareTo defines ordering for Comparable. Breaking these contracts causes duplicate set entries, failed map lookups, incorrect sorting, or inconsistent tree-based collections.

How the operations differ

OperationPurposeTypical use
==Primitive value or reference identityCheck whether two references point to the same object
equalsLogical equalityCompare business values such as two account IDs
hashCodeHash bucket selectionHashMap, HashSet, and related collections
compareToRelative ordering: negative, zero, or positiveTreeMap, TreeSet, and sorting

Runnable example

import java.util.*;

record EmployeeId(String value) implements Comparable<EmployeeId> {
    @Override
    public int compareTo(EmployeeId other) {
        return value.compareTo(other.value);
    }
}

public class EqualityDemo {
    public static void main(String[] args) {
        String first = new String("java");
        String second = new String("java");

        System.out.println(first == second);
        System.out.println(first.equals(second));
        System.out.println(first.hashCode() == second.hashCode());
        System.out.println(new EmployeeId("E2").compareTo(new EmployeeId("E10")) > 0);
    }
}

Expected output:

false
true
true
true

The last result is true because lexicographical string ordering compares the first character that differs; it is not numeric ordering. If numeric ordering is needed, compare parsed numbers or use a numeric field.

Internal working

  1. HashMap first uses hashCode to select a bucket.
  2. It then uses equals to identify the exact key inside that bucket.
  3. HashSet uses the same rules because it is backed by a map.
  4. TreeMap and TreeSet use ordering, usually compareTo or a supplied Comparator, instead of hash lookup.

What goes wrong when contracts are broken?

  • Override equals without hashCode: equal objects can enter different hash buckets, so contains or get may fail.
  • Use mutable fields in equality: changing a key after insertion can make the entry unreachable.
  • Make compareTo inconsistent with equality: a TreeSet can treat two unequal objects as duplicates when comparison returns zero.
  • Use subtraction such as this.age - other.age: integer overflow can produce the wrong ordering. Use Integer.compare.

Real-world example

A payment service may identify a request with PaymentId. Its equality should use the stable payment ID, not mutable status or display fields. That makes idempotency maps, database entity lookups, and deduplication predictable.

Follow-up questions

  • Should equal objects always have the same hash code? Yes. The reverse is not required; collisions are allowed.
  • Can compareTo return any negative or positive number? Yes. Only the sign matters, although zero must mean equivalent ordering.
  • Why is BigDecimal a common interview edge case? Its equals considers scale while compareTo does not, so new BigDecimal("1.0") and new BigDecimal("1.00") compare as equal by ordering but not by equals.

Interview-ready answer

== checks primitive values or reference identity, while equals checks logical equality. Hash-based collections use hashCode to find a bucket and equals to find the exact key, so equal objects must have equal hashes. compareTo defines ordering for sorted collections. Breaking these contracts causes failed lookups, duplicate set entries, or incorrect tree ordering.

Equality contract step by step

A correct equals implementation is reflexive, symmetric, transitive, consistent, and returns false for null. The hash contract adds that equal objects must have equal hash codes. It does not require unequal objects to have different hashes. compareTo must be antisymmetric, transitive, and consistent enough for the sorted collection's intended equality.

import java.util.*;

final class AccountId {
    private final String value;
    AccountId(String value) { this.value = Objects.requireNonNull(value); }

    @Override public boolean equals(Object other) {
        return other instanceof AccountId id && value.equals(id.value);
    }
    @Override public int hashCode() { return value.hashCode(); }
}

public class EqualityContractDemo {
    public static void main(String[] args) {
        Set<AccountId> ids = new HashSet<>();
        ids.add(new AccountId("A-1"));
        System.out.println(ids.contains(new AccountId("A-1")));
    }
}

Expected output: true. The second object is a different reference, but it is logically equal and has the same hash.

Sorted collection trap

A TreeSet uses comparison to decide whether a value is already present. If compareTo returns zero for two objects whose equals returns false, the second object is discarded by the tree set. This is legal for some domain types, but it surprises developers when sorted and hash-based collections are expected to agree.

record Product(String code, String description)
        implements Comparable<Product> {
    @Override public int compareTo(Product other) {
        return code.compareTo(other.code); // ordering identity is code
    }
}

var products = new java.util.TreeSet<Product>();
products.add(new Product("P1", "First"));
products.add(new Product("P1", "Updated description"));
System.out.println(products.size()); // 1

Practical rules

  • Base equality on stable identity or value fields, never mutable display state.
  • Use Objects.equals and Objects.hash to handle nulls consistently.
  • Use Integer.compare, Long.compare, or a comparator instead of subtraction.
  • Document whether natural ordering is consistent with equality.
  • Test equality with a matrix: same reference, equal values, different values, null, subclass, and changed fields.

Additional follow-up answers

  • Why does String pooling make == confusing? String literals may share an interned instance, so identity can appear to work. Always use equals for string content.
  • Should subclasses participate in equality? Carefully. Class-based equality can preserve symmetry; an instanceof design must account for subclass state.
  • What is BigDecimal's inconsistency? equals considers scale while compareTo considers numeric value, so 1.0 and 1.00 behave differently in hash and sorted collections.

Question: How do you design an immutable Java class, and why does immutability help with thread safety?

Short answer

An immutable object cannot change after construction. Make the class difficult or impossible to extend, keep fields private and final, initialize them in the constructor, provide no setters, validate inputs, and make defensive copies of mutable objects. Immutability removes shared state changes, so multiple threads can safely read the same object without locks.

Rules for an immutable class

  1. Declare the class final, or carefully control subclassing.
  2. Make state private final.
  3. Set every field during construction.
  4. Do not expose setters or mutable internal state.
  5. Defensively copy mutable input and output such as Date, arrays, and collections.
  6. Validate invariants before publishing the object.

Runnable example

import java.util.*;

public final class UserProfile {
    private final String name;
    private final List<String> roles;

    public UserProfile(String name, List<String> roles) {
        this.name = Objects.requireNonNull(name);
        this.roles = List.copyOf(roles);
    }

    public String name() { return name; }
    public List<String> roles() { return roles; }
}

class ImmutableDemo {
    public static void main(String[] args) {
        List<String> input = new ArrayList<>(List.of("USER"));
        UserProfile profile = new UserProfile("Maya", input);
        input.add("ADMIN");

        System.out.println(profile.name());
        System.out.println(profile.roles());
        try {
            profile.roles().add("ADMIN");
        } catch (UnsupportedOperationException ex) {
            System.out.println("roles cannot be changed");
        }
    }
}

Expected output:

Maya
[USER]
roles cannot be changed

Internal working and thread safety

Threads can safely share an immutable object because its fields never change after construction. A properly constructed object also benefits from the Java Memory Model's final-field guarantees: other threads can reliably observe final fields after safe publication. Immutability does not automatically make referenced objects safe; the whole object graph must be immutable or safely wrapped.

Edge cases

  • Collections.unmodifiableList prevents mutation through that view but does not copy the original list. Changes to the original list may still be visible.
  • A final reference cannot be reassigned, but the referenced object can still be mutable.
  • Returning an internal array directly breaks immutability. Return a copy.
  • Lazy caching inside an immutable object needs safe publication or synchronization.
  • Serialization, reflection, and deserialization can bypass normal constructors, so sensitive classes may need extra protection.

Real-world examples

Value objects such as money, coordinates, configuration snapshots, request objects, cache keys, and Java records are good candidates. Immutable configuration can be shared by request threads without defensive locking.

Follow-up questions

  • Are records always immutable? No. A record's fields are final, but a field may refer to a mutable list or object. Use defensive copies.
  • Why use a builder? A builder helps create complex immutable objects while keeping the final object itself unchangeable.
  • Is immutability faster? It can reduce locking and simplify caching, but defensive copying may add allocation cost.

Interview-ready answer

An immutable class is fully initialized in its constructor and never changes afterward. I use private final fields, no setters, validation, defensive copies, and controlled inheritance. Since threads only read stable state, immutable objects can be shared without locks, are safe as map keys, and are easier to reason about.

Deep immutability and defensive copying

Immutability is a property of the reachable state, not just the top-level reference. A final List<String> prevents replacing the list reference, but it does not prevent callers from adding to the list. Copy mutable inputs on the way in and return an immutable copy or a copy on the way out.

import java.util.*;

public final class Schedule {
    private final Date start;
    private final List<String> attendees;

    public Schedule(Date start, List<String> attendees) {
        this.start = new Date(start.getTime());
        this.attendees = List.copyOf(attendees);
    }

    public Date start() { return new Date(start.getTime()); }
    public List<String> attendees() { return attendees; }
}

List.copyOf also rejects null elements and returns an unmodifiable list. If elements themselves are mutable, copy or make those elements immutable too.

Safe publication and the Java Memory Model

Final fields receive special initialization guarantees when the constructor completes normally and the object is not allowed to escape during construction. For shared mutable objects, use a safe publication mechanism such as a final field of another safely published object, a volatile reference, a lock, a concurrent collection, or a static initialization boundary. Immutability reduces the number of visibility and race problems, but it does not fix unsafe publication of a partially constructed object.

Builder and validation example

public final class ConnectionConfig {
    private final String host;
    private final int port;

    private ConnectionConfig(Builder builder) {
        if (builder.port < 1 || builder.port > 65535) {
            throw new IllegalArgumentException("invalid port");
        }
        host = java.util.Objects.requireNonNull(builder.host);
        port = builder.port;
    }

    public static class Builder {
        private String host;
        private int port = 443;
        public Builder host(String value) { host = value; return this; }
        public Builder port(int value) { port = value; return this; }
        public ConnectionConfig build() { return new ConnectionConfig(this); }
    }
}

The builder is mutable while constructing the value; the resulting configuration is immutable after build. This is useful when there are many optional fields or cross-field validation rules.

Common advanced pitfalls

  • Do not let this escape from a constructor through a listener, thread, callback, or overridable method.
  • Do not assume Collections.unmodifiableList is a snapshot; it can still reflect changes to the original list.
  • Do not use mutable objects as keys in a hash map unless their equality state is stable for the key's lifetime.
  • Lazy memoization changes internal state. Use a safe holder, volatile field, or synchronization if multiple threads can initialize it.
  • Serialization frameworks and reflection may bypass normal invariants; validate at deserialization boundaries.

Additional follow-up answers

  • Why does immutability help caching? A stable object can be safely reused and its hash code can remain stable for the lifetime of a map key.
  • Is StringBuilder immutable? No; it is intentionally mutable and is not a thread-safe value object.
  • Can an immutable object contain a cache? Yes, but the cache is internal mutable state and must be safely synchronized or made safely visible.

Question: How does Java memory management work, including heap, stack, references, pass-by-value, and object allocation?

Short answer

Objects and arrays are normally allocated on the heap and managed by the garbage collector. Each thread has its own stack containing method frames, local variables, and references. A reference is a value that points to an object; it is not the object itself. Java is always pass-by-value: for objects, the value passed is a copy of the reference.

Heap, stack, and references

  • Heap: shared memory for objects, arrays, and most application data.
  • Stack: per-thread call frames containing parameters, locals, and return information.
  • Reference: a variable value used to reach an object; multiple references can point to one object.
  • Metaspace: native memory used for class metadata in modern HotSpot JVMs.

Runnable pass-by-value example

class Box { int value; Box(int value) { this.value = value; } }

public class MemoryDemo {
    static void change(Box box) {
        box.value = 20;
        box = new Box(30);
    }

    static void reassign(int value) {
        value = 99;
    }

    public static void main(String[] args) {
        Box box = new Box(10);
        int number = 1;
        change(box);
        reassign(number);
        System.out.println(box.value);
        System.out.println(number);
    }
}

Expected output:

20
1

The method receives a copy of the reference. It can mutate the shared object through that copy, but assigning the parameter to a new object does not change the caller's reference.

Object allocation and garbage collection

  1. The JVM loads class metadata and checks the requested type.
  2. It allocates space for the object and initializes fields to default values.
  3. The constructor runs and establishes the object's state.
  4. When no GC-root path can reach the object, it becomes eligible for collection.

GC roots include active stack references, static fields, JNI references, and running threads. An object being eligible for collection does not mean it is collected immediately.

Performance details

HotSpot may optimize allocation with thread-local allocation buffers, escape analysis, scalar replacement, and stack allocation-like optimizations. These are implementation optimizations; Java code should not depend on a particular object location.

Edge cases

  • StackOverflowError usually indicates excessive recursion or very large stack frames.
  • OutOfMemoryError: Java heap space can mean too many live objects or a leak.
  • Native buffers, thread stacks, metaspace, and direct memory can exhaust a container even when heap usage looks normal.
  • Calling System.gc() is only a request and is not a reliable memory-management strategy.

Real-world example

In a web service, each request creates temporary DTOs and parsing objects. Those objects become collectible after the request finishes unless a cache, static collection, thread local, listener, or long-lived task retains them.

Follow-up questions

  • Does Java pass objects by reference? No. It passes a copy of the reference by value.
  • When is an object garbage collected? When it is unreachable from GC roots and a collector decides to reclaim it.
  • Can local variables live on the heap? The language does not guarantee physical placement; the JVM may optimize representation.

Interview-ready answer

Java normally stores objects on the shared heap and method frames on each thread's stack. References are values pointing to heap objects, and garbage collection reclaims objects that are unreachable from GC roots. Java is always pass-by-value: an object parameter is a copied reference, so a method can mutate the object but cannot replace the caller's reference.

What a method call contains

Each thread has its own call stack. A method invocation creates a frame containing parameters, local variables, an operand stack, and return information. A local reference in a frame points to an object in the shared heap. Because each thread has separate frames, local primitive variables are naturally isolated; the object reached by a shared reference is not isolated.

class Counter { int value; }

static void update(Counter counter) {
    counter.value++;       // changes the shared object
    counter = new Counter(); // changes only this copied parameter
    counter.value = 99;
}

The caller observes the increment but not the reassignment. This is the precise meaning of “Java passes object references by value.”

Garbage collection in stages

  1. New objects are normally allocated in a young-generation region or thread-local allocation buffer.
  2. Short-lived objects are reclaimed by young collections; surviving objects may be promoted.
  3. Collectors identify reachable objects from GC roots and reclaim or compact unreachable regions.
  4. Different collectors trade throughput, pause time, footprint, and latency. Choose based on measurement.

A memory leak in Java usually means an unintended live reference, not a failure to manually free memory. Common retention paths include static maps, unbounded caches, listeners that are never removed, ThreadLocals in pooled threads, and queues whose consumers are slower than producers.

Heap, native memory, and containers

The Java heap is only one part of a process. A production memory budget may include heap, metaspace, code cache, thread stacks, direct buffers, native libraries, the garbage collector, and memory-mapped files. A container can be killed even when heap usage is below -Xmx. Size the JVM with the container limit and inspect both JVM and operating-system metrics.

// Useful diagnostic commands in a running JVM:
jcmd <pid> GC.heap_info
jcmd <pid> GC.class_histogram
jcmd <pid> Thread.print

Reference types and reachability

  • Strong reference: ordinary reference; the object remains reachable.
  • Weak reference: does not keep an otherwise unreachable object alive; useful for certain caches.
  • Soft reference: historically used for memory-sensitive caches, but eviction behavior is not a reliable cache policy.
  • Phantom reference: supports post-reachability cleanup coordination; use modern cleanup patterns carefully.

Reference types do not replace explicit cache size limits, expiration, or observability. A bounded cache with clear eviction rules is usually easier to operate.

Advanced edge cases

  • Large arrays and humongous objects can be handled differently by a collector and may cause fragmentation or long pauses.
  • Deep recursion can exhaust a thread stack even when plenty of heap remains.
  • Thread creation consumes native stack memory; thousands of platform threads can exhaust a process before heap does.
  • Finalization is deprecated and should not be used for resource management; use try-with-resources and explicit ownership.
  • Escape analysis may eliminate an allocation, but this is a JVM optimization and should not change program semantics.

Additional follow-up answers

  • Can System.gc() fix a leak? No. It may request collection, but reachable leaked objects remain and the call can hurt latency.
  • What is the difference between a memory leak and high allocation rate? A leak retains objects unintentionally; high allocation creates many temporary objects that may still be collected normally.
  • Why does a heap dump help? It shows retained objects and reference paths, allowing you to find what is keeping memory reachable.

Question: How do Java generics, type erasure, reflection, and annotations work internally?

Short answer

Generics provide compile-time type safety and are mostly implemented through type erasure, so ordinary generic type arguments are removed from runtime bytecode. The compiler inserts casts where needed. Reflection inspects classes, methods, fields, and annotations at runtime. Annotations are metadata whose retention determines whether they exist only in source, in class files, or at runtime.

Generics and type erasure

import java.util.*;

public class GenericsDemo {
    public static void main(String[] args) {
        List<String> names = new ArrayList<>();
        names.add("Maya");
        String name = names.get(0); // compiler inserts a cast to String
        System.out.println(name);

        System.out.println(names instanceof List<?>);
    }
}

Expected output:

Maya
true

At runtime, the JVM generally sees an ArrayList, not an ArrayList<String>. This is why List<String>.class is illegal and why instanceof List<String> is not allowed.

Reflection and annotations

import java.lang.annotation.*;

@Retention(RetentionPolicy.RUNTIME)
@Target(ElementType.TYPE)
@interface Endpoint { String value(); }

@Endpoint("/orders")
class OrderController { }

public class ReflectionDemo {
    public static void main(String[] args) {
        Class<OrderController> type = OrderController.class;
        Endpoint endpoint = type.getAnnotation(Endpoint.class);
        System.out.println(type.getSimpleName());
        System.out.println(endpoint.value());
    }
}

Expected output:

OrderController
/orders

Frameworks such as Spring use reflection and runtime annotations to discover controllers, services, configuration, validation rules, and dependency injection metadata.

Important limitations and edge cases

  • Generic type arguments are normally unavailable at runtime, although frameworks can preserve them using a type token or subclass metadata.
  • Static fields cannot use a class's type parameter.
  • Primitive types cannot be generic arguments; use wrappers such as Integer.
  • Heap pollution can occur through raw types, unchecked casts, arrays, or unsafe varargs.
  • Reflection can bypass normal access checks and has performance and security implications.
  • SOURCE, CLASS, and RUNTIME retention control annotation visibility.

Real-world examples

Spring's @RestController, Jackson's serialization annotations, JUnit's @Test, and Bean Validation annotations are all examples of metadata-driven behavior. Generic repositories such as Repository<Order, Long> communicate type information to the compiler and sometimes to frameworks through reflection metadata.

Follow-up questions

  • Why can you not create new T()? Erasure removes the runtime type, so the compiler cannot know which constructor to call.
  • What is a bounded type parameter? A declaration such as <T extends Number> restricts accepted types and exposes the bound's operations.
  • What is the difference between reflection and annotation processing? Reflection runs at runtime; annotation processors inspect source during compilation and can generate code.

Interview-ready answer

Generics give compile-time type safety, but Java usually implements them through type erasure and inserts casts into bytecode. Reflection inspects runtime classes and members. Annotations provide metadata, and runtime-retained annotations can be read by frameworks such as Spring. The trade-off is that generic type arguments are usually unavailable at runtime and raw or unchecked operations can create heap pollution.

Compile-time generic checking

The compiler checks that values added to a parameterized type match its type argument. When a value is read, the compiler inserts the required cast. This gives source-level safety without creating a separate runtime class for every type argument.

import java.util.*;

public class GenericSafetyDemo {
    static <T> T first(List<T> values) {
        return values.get(0);
    }

    public static void main(String[] args) {
        List<String> names = new ArrayList<>();
        names.add("Maya");
        String first = first(names);
        System.out.println(first);
    }
}

Expected output: Maya. The generic method preserves the relationship between the input and return type at compile time.

Wildcards and type variance

  • List<? extends Number> is a producer: safely read numbers, but cannot add an arbitrary Number.
  • List<? super Integer> is a consumer: safely add Integers, but reads return Object.
  • List<T> is used when a method needs to preserve or relate one exact type parameter.
static double total(List<? extends Number> values) {
    return values.stream().mapToDouble(Number::doubleValue).sum();
}

static void addDefaults(List<? super Integer> values) {
    values.add(0);
    values.add(1);
}

The mnemonic is PECS: Producer Extends, Consumer Super. It is a design rule for method APIs, not a rule that changes the runtime representation.

Type erasure limitations

  • You cannot use new T() without supplying a factory or class token.
  • You cannot create a generic array such as new T[10] safely.
  • You cannot overload methods only by generic type arguments because their erased signatures collide.
  • Use a type token such as Class<T> or a framework type reference when runtime type information is required.
static <T> T create(Class<T> type) throws ReflectiveOperationException {
    return type.getDeclaredConstructor().newInstance();
}

Reflection versus annotation processing

Reflection runs after compilation and can inspect loaded classes. Annotation processing runs during compilation and can validate source or generate code. Runtime reflection is flexible but may cost startup time and can be affected by module access, native-image restrictions, or obfuscation. Compile-time generation can improve startup and fail earlier.

Frameworks often combine both: Spring scans class metadata, builds bean definitions, and then uses reflection or generated accessors to create and wire objects. Retention policy determines whether an annotation is available to that runtime scanner.

Heap pollution and raw types

List raw = new ArrayList<String>();
raw.add(42); // unchecked operation

List<String> names = raw;
// String value = names.get(0); // ClassCastException at the inserted cast

Use compiler warnings as design feedback. If unchecked conversion is unavoidable, isolate it in a small, documented boundary and validate the data immediately.

Additional follow-up answers

  • Why are generic arrays unsafe? Arrays retain their component type at runtime, while generic arguments are erased, so the two type systems can conflict.
  • What is reification? Reification means type information is available at runtime. Java reifies raw class and array types but generally erases generic arguments.
  • What does Class<?> mean? A Class object for some unknown type; it is safer than a raw Class.
  • When use annotation processing? For compile-time validation or generated mappings, clients, configuration, and metadata when runtime reflection would be costly or fragile.

Question: How would you choose between HashMap, ConcurrentHashMap, Hashtable, CopyOnWriteArrayList, and TreeMap for different real-world applications?

Short answer

Choose based on ordering, concurrency, read/write ratio, null policy, and required operations. Use HashMap for ordinary single-threaded or externally synchronized key-value access, ConcurrentHashMap for concurrent map operations, TreeMap for sorted keys and range queries, and CopyOnWriteArrayList for many reads with very rare writes. Avoid new uses of legacy Hashtable unless compatibility requires it.

Comparison table

import java.util.*;
import java.util.concurrent.*;

public class CollectionChoiceDemo {
    public static void main(String[] args) {
        Map<String, Integer> fastLookup = new HashMap<>();
        Map<String, Integer> sharedCounts = new ConcurrentHashMap<>();
        Map<Integer, String> sorted = new TreeMap<>();
        List<String> listeners = new CopyOnWriteArrayList<>();

        fastLookup.put("order-1", 100);
        sharedCounts.merge("success", 1, Integer::sum);
        sorted.put(2, "medium");
        sorted.put(1, "low");
        listeners.add("audit-listener");

        System.out.println(fastLookup.get("order-1"));
        System.out.println(sharedCounts.get("success"));
        System.out.println(sorted.firstKey());
        System.out.println(listeners);
    }
}

Concurrency details

ConcurrentHashMap makes individual operations and methods such as putIfAbsent, compute, and merge safe for concurrent use. A sequence such as “check then put” is not automatically atomic; use one of those compound operations. Its iterators are weakly consistent rather than fail-fast.

Hashtable synchronizes individual methods, but a sequence of calls still needs external coordination. CopyOnWriteArrayList gives readers a stable snapshot-like array and is useful for listener registries, configuration observers, or routing tables with rare changes.

Real-world decision examples

  • Per-request local lookup: HashMap.
  • Application-wide counters or a token registry: ConcurrentHashMap with merge or compute.
  • Time windows, sorted IDs, or range queries: TreeMap.
  • Event listeners read on every request but changed only during startup: CopyOnWriteArrayList.
  • Old library contract requiring a synchronized map: Hashtable, preferably behind a compatibility boundary.

Edge cases and common mistakes

  • Do not use CopyOnWriteArrayList for a high-volume queue or frequently updated collection.
  • Do not assume ConcurrentHashMap makes the values themselves thread-safe.
  • Do not use TreeMap when you only need lookup and do not need ordering.
  • Do not use a synchronized wrapper as a replacement for understanding iteration and compound-operation locking.
  • Do not select a collection only by benchmark numbers; measure the actual workload, memory pressure, and contention.

Follow-up questions

  • Why does ConcurrentHashMap reject null? A null result can clearly mean “no mapping” during concurrent operations, so allowing null would make APIs such as get ambiguous.
  • When is LinkedHashMap a better choice? When insertion or access order matters, such as a simple LRU-style structure.
  • What if I need a thread-safe sorted map? Consider ConcurrentSkipListMap, external synchronization, or a design that avoids shared mutation.

Interview-ready answer

I choose HashMap for ordinary unsynchronized lookup, ConcurrentHashMap for shared concurrent map updates, TreeMap for sorted keys and ranges, and CopyOnWriteArrayList for read-heavy lists with very rare writes. Hashtable is mainly a legacy compatibility choice. I also check whether compound operations need atomic methods such as compute or merge.

Selection by workload

Start with the operation the application needs rather than the collection name. If the key is arbitrary and lookup dominates, a hash map is usually appropriate. If users ask for “all records between these two keys,” a sorted map is a better fit. If readers greatly outnumber writes and readers must not block while a small list changes, copy-on-write can be ideal.

import java.util.*;
import java.util.concurrent.*;

public class CollectionWorkloadDemo {
    public static void main(String[] args) {
        Map<String, String> cache = new HashMap<>();
        NavigableMap<Integer, String> byPriority = new TreeMap<>();
        ConcurrentMap<String, Long> counters = new ConcurrentHashMap<>();
        List<Runnable> listeners = new CopyOnWriteArrayList<>();

        cache.put("token", "abc");
        byPriority.put(10, "normal");
        byPriority.put(1, "urgent");
        counters.merge("requests", 1L, Long::sum);
        listeners.add(() -> { });

        System.out.println(byPriority.firstEntry().getValue());
        System.out.println(counters.get("requests"));
    }
}

Expected output: urgent and 1.

Concurrency and atomicity

Thread safety of a collection does not automatically make a multi-step business operation atomic. This is unsafe even with a concurrent map:

if (!map.containsKey(key)) {
    map.put(key, value); // another thread can win between the two calls
}

Use putIfAbsent, computeIfAbsent, compute, or merge when the operation matches their semantics. Keep mapping functions short and do not recursively modify the same map from inside them.

Ordering and comparator correctness

TreeMap uses natural ordering or a comparator for placement and equality. The comparator must be transitive and consistent with the domain. A comparator that returns zero for distinct keys causes one value to replace or hide another. Null keys are generally not accepted by natural ordering, though a comparator can explicitly define a null policy.

CopyOnWriteArrayList iterators observe a snapshot of the backing array. A write copies the array, so reads are cheap and stable while writes are O(n) and allocate. It is excellent for listener lists and poor for queues, counters, or frequently changing collections.

Memory and performance trade-offs

  • HashMap uses extra bucket and node memory and has good average lookup, but iteration cost depends on capacity as well as size.
  • ConcurrentHashMap supports concurrent access without one global lock for normal operations, but contention can still occur on hot keys.
  • Hashtable synchronizes methods with a legacy coarse-grained model and rejects nulls; it is rarely the best new design.
  • TreeMap provides O(log n) operations and range views such as subMap, headMap, and tailMap.
  • CopyOnWriteArrayList can consume substantial memory during writes because old and new arrays coexist briefly.

Real-world decision examples

  • Per-request variables: local HashMap.
  • Feature flags read on every request and changed only by refresh events: immutable snapshot or CopyOnWriteArrayList for listeners.
  • Rate-limit counters shared by request threads: ConcurrentHashMap with atomic updates, or a distributed store for multiple instances.
  • Time-based scheduling and range lookup: TreeMap or a specialized queue.
  • Cross-process session state: none of these alone; use a database, Redis, or another shared system.

Additional follow-up answers

  • Why not use Hashtable for all thread-safe maps? Its coarse synchronization and legacy API are usually less suitable than ConcurrentHashMap.
  • When use a synchronized wrapper? When a simple legacy map needs synchronized individual operations and the caller can synchronize during iteration and compound actions.
  • What if sorted concurrent access is required? Consider ConcurrentSkipListMap, which provides sorted concurrent operations with different performance characteristics.
  • Why is a cache not just a HashMap? A production cache needs expiration, size bounds, concurrency behavior, eviction, metrics, and often cross-instance consistency.

Question: How do Java Streams work internally, and when can parallelStream() reduce performance compared to sequential streams?

Short answer

A Stream is a lazy pipeline over a data source. Intermediate operations such as filter and map describe work; a terminal operation such as collect, count, or reduce starts traversal. A sequential stream normally processes one element at a time. A parallel stream splits a splittable source, runs pieces in the common ForkJoinPool, and combines the results.

Internal working

  1. Source: an array, collection, generator, file, or custom Spliterator.
  2. Pipeline: each intermediate operation adds a stage but usually does not execute immediately.
  3. Traversal: the terminal operation pulls elements through the stages. Stateless operations can be fused into one pass.
  4. Parallel execution: a Spliterator repeatedly splits the source. worker tasks process partitions and a combiner merges partial results.
import java.util.List;
import java.util.stream.Collectors;

public class StreamPipelineDemo {
    public static void main(String[] args) {
        List<String> names = List.of("ana", "bob", "luis", "maria");

        List<String> result = names.stream()
                .filter(name -> name.length() > 3)
                .map(String::toUpperCase)
                .sorted()
                .collect(Collectors.toList());

        int total = List.of(2, 4, 6, 8).stream()
                .mapToInt(Integer::intValue)
                .sum();

        System.out.println(result);
        System.out.println(total);
    }
}

Expected output: [LUIS, MARIA] followed by 20. Nothing in the first pipeline runs until collect is called.

When parallel streams hurt

  • The input is small, so splitting and merging cost more than the work.
  • The operation is cheap, sequential, or difficult to split, such as a linked list traversal.
  • The lambda performs blocking I/O. The common pool is not an appropriate general-purpose I/O pool.
  • The pipeline mutates shared state, causing locks, races, or contention.
  • The terminal operation needs ordering or an expensive merge.
  • Other application code is already using the common pool.

Use parallelism for sufficiently large, CPU-bound, independent work with a cheap combiner. Measure both modes with realistic data; never assume that more threads means more throughput.

Real-world example and edge cases

CPU-heavy image transformations over millions of independent images may benefit from controlled parallelism. Database calls inside parallelStream() commonly make latency and connection-pool pressure worse. Also avoid side effects such as adding to a non-thread-safe ArrayList; prefer collectors designed for parallel reduction or an explicit executor.

Follow-up questions

  • Are streams reusable? No. A stream is consumed after a terminal operation; create a new stream from the source.
  • What is the difference between map and flatMap? map transforms one item into one item; flatMap transforms one item into a stream and flattens the nested streams.
  • Are intermediate operations always lazy? They are generally lazy, although stateful operations such as sorted may buffer elements when the terminal operation runs.

Interview-ready answer

Streams build a lazy pipeline over a source. A terminal operation triggers traversal, and the implementation can fuse stages into one pass. A parallel stream splits the source with a Spliterator and combines worker results. It can be slower for small inputs, cheap operations, blocking I/O, ordered pipelines, poor splitters, or shared mutable state, so I benchmark the real workload before using it.

Step-by-step pipeline example

Suppose the source contains orders. filter rejects cancelled orders, map changes an order into its amount, and sum consumes the pipeline. The stream does not create an intermediate list unless the code explicitly asks it to.

import java.util.List;

record Order(String id, String status, int amount) {}

public class StreamOrderDemo {
    public static void main(String[] args) {
        List<Order> orders = List.of(
                new Order("A", "PAID", 40),
                new Order("B", "CANCELLED", 100),
                new Order("C", "PAID", 60));

        int total = orders.stream()
                .filter(order -> "PAID".equals(order.status()))
                .mapToInt(Order::amount)
                .sum();

        System.out.println(total);
    }
}

Expected output: 100. Each order flows through the stages only when the terminal operation requests the next result.

Spliterator and parallel execution

A Spliterator exposes elements through tryAdvance and can divide work through trySplit. An ArrayList splits cheaply because it has indexed storage. A source that cannot split evenly gives parallel workers less useful work. The parallel implementation creates fork/join tasks, processes partitions, and combines partial results according to the collector or reduction operation.

List<Integer> values = java.util.stream.IntStream.rangeClosed(1, 100)
        .boxed()
        .parallel()
        .filter(number -> number % 2 == 0)
        .toList();

// The result is correct, but the order guarantee and merge cost still matter.

For ordered streams, preserving encounter order can require buffering and coordination. An unordered source or unordered() may improve throughput only when the business result does not depend on order.

Reduction and collector correctness

A parallel reduction must be associative and compatible with its identity. Addition is safe because (a + b) + c equals a + (b + c). String concatenation may be correct but can be expensive. A mutable accumulator must not be shared unsafely between workers; use a proper collector rather than mutating an external list.

// Safe reduction: identity 0 and associative addition.
int sum = java.util.stream.IntStream.of(1, 2, 3, 4)
        .parallel()
        .reduce(0, Integer::sum);

// Dangerous pattern: shared mutable state.
var output = new java.util.ArrayList<Integer>();
java.util.stream.IntStream.range(0, 10_000)
        .parallel()
        .forEach(output::add); // race and lost updates are possible

Production decision checklist

  • Measure sequential and parallel versions with representative data, warm-up, and realistic hardware.
  • Check CPU saturation, allocation rate, garbage collection, and downstream latency—not only elapsed time.
  • Use a dedicated executor when the work needs isolation or has blocking behavior; do not overload the common pool.
  • Keep lambdas stateless and avoid network, database, file, or lock waits inside a parallel stream.
  • Prefer a normal loop when it is clearer, easier to debug, and just as fast.

Additional follow-up answers

  • What is short-circuiting? Operations such as findFirst, anyMatch, and limit can stop traversal early, although ordered parallel execution may still need coordination.
  • Why can findAny be faster than findFirst? findAny can return whichever worker finds a match first; findFirst must preserve encounter order.
  • What is a stateful intermediate operation? Operations such as sorted and distinct need to remember or coordinate across elements and may require buffering.
  • Can a stream be used twice? No. After a terminal operation it is closed; recreate it from the source.

Question: How would you process millions of records efficiently using Java Streams, batching, and pagination without exhausting memory?

Short answer

Do not load all records into a collection. Read a bounded page, process it, write or publish a bounded batch, release references, and continue from a stable cursor. Prefer keyset pagination such as WHERE id > :lastId ORDER BY id LIMIT :size over large offsets.

import java.util.List;

public class BatchDemo {
    record Order(long id, String status) {}

    static List<Order> fetchAfter(long lastId, int size) {
        // In production this method executes a keyset-paginated SQL query.
        return List.of();
    }

    public static void main(String[] args) {
        long lastId = 0;
        int pageSize = 500;
        while (true) {
            List<Order> page = fetchAfter(lastId, pageSize);
            if (page.isEmpty()) break;

            page.stream()
                    .filter(order -> "READY".equals(order.status()))
                    .forEach(order -> System.out.println("process " + order.id()));

            lastId = page.get(page.size() - 1).id();
        }
    }
}

Important design points

  • Bound memory: keep page and batch sizes finite; do not call collect(toList()) over an unbounded source.
  • Stable ordering: use a unique, indexed cursor such as (created_at, id) so records are not skipped or repeated.
  • Batch writes: use JDBC batching or a bulk API and commit at a controlled boundary.
  • Backpressure: limit workers and queue capacity so a fast reader cannot overwhelm a slow database or downstream service.
  • Restartability: checkpoint the last successful cursor and make processing idempotent.

Offset pagination is simple but becomes slower as the offset grows and can shift when rows are inserted or deleted. Keyset pagination is usually faster and more stable. A database streaming cursor can also work, but configure fetch size, transaction scope, timeout, and driver behavior carefully.

Edge cases and follow-ups

  • Handle a record that changes while paging; define whether the job uses a snapshot, an upper-bound ID, or an eventually consistent view.
  • Retry failed batches without duplicating side effects. Use an idempotency key or a durable processing table.
  • Do not parallelize database reads blindly; connection pools and database locks are finite.
  • For a file, use Files.lines(path) with try-with-resources and process one bounded batch at a time.

Interview-ready answer

I process a bounded page at a time, use keyset pagination on an indexed stable key, transform the page with a stream, write in batches, and release references before reading the next page. I add backpressure, checkpoint the last successful cursor, and make retries idempotent. That keeps memory, database load, and recovery behavior predictable.

Why pagination strategy matters

With offset pagination, the database may scan or discard many rows before reaching a large offset. Inserts and deletes can also shift later pages. Keyset pagination starts from the last value already seen and uses an index:

SELECT id, status, amount
FROM orders
WHERE (created_at, id) > (:lastCreatedAt, :lastId)
ORDER BY created_at, id
LIMIT :pageSize;

The second column makes the cursor unique when multiple records have the same timestamp. The cursor must be saved only after the corresponding batch has completed successfully.

Batching without retaining data

import java.util.ArrayList;
import java.util.List;

public class StreamingBatchDemo {
    static void writeBatch(List<String> batch) {
        System.out.println("write " + batch);
    }

    public static void main(String[] args) {
        List<String> batch = new ArrayList<>(3);
        for (int id = 1; id <= 8; id++) {
            batch.add("record-" + id);
            if (batch.size() == 3) {
                writeBatch(batch);
                batch.clear();
            }
        }
        if (!batch.isEmpty()) writeBatch(batch);
    }
}

Expected output: write [record-1, record-2, record-3], then record-4 through record-6, then record-7 and record-8. Only the current batch is retained.

Transactions, checkpoints, and retries

  1. Read a page after the saved cursor.
  2. Validate and transform records without keeping the entire dataset.
  3. Write the batch in one bounded transaction or downstream request.
  4. Commit the side effect and checkpoint together when possible.
  5. Advance the cursor and continue.

If the process fails after writing but before checkpointing, the page may be retried. Therefore writes need an idempotency key, a unique constraint, an upsert, or a durable processed-record table. Increasing the page size improves throughput only until database locks, transaction logs, network payloads, or memory become the bottleneck.

Streams, cursors, and resource ownership

A stream backed by a database cursor owns an external resource. Always close it:

try (var rows = repository.streamOrders()) {
    rows.filter(Order::isReady)
        .forEach(this::process);
}

Do not return a lazy stream after its transaction or connection has closed. Also avoid opening one transaction for millions of records; use a deliberate transaction boundary and understand the consistency requirement.

Production edge cases

  • Records inserted during the job can be included twice or missed unless the job uses a snapshot, an upper-bound cursor, or a defined consistency policy.
  • A record deleted between page reads should be treated as a normal missing record or logged according to business rules.
  • Large text or binary columns can exhaust memory even with small row counts; select only required columns.
  • Parallel workers require bounded queues and separate connection limits. More workers can reduce performance by exhausting the database pool.
  • Monitor page latency, batch latency, cursor progress, retry count, memory, queue depth, and downstream errors.

Additional follow-up answers

  • What page size should you choose? Start with a measured value such as 100–1,000, then tune using memory, transaction duration, database latency, and payload size.
  • When is offset pagination acceptable? Small administrative screens or stable, small datasets where simplicity is more valuable than deep-page performance.
  • How do you provide progress? Track the stable cursor, processed count, failed count, and estimated upper bound; do not use only page number when rows can change.
  • How do you prevent a failed record from blocking the entire job? Isolate bad records into a quarantine or dead-letter table while preserving an auditable retry path.

Question: How do CompletableFuture, Future, and ExecutorService differ, and how would you execute and combine multiple asynchronous API calls with timeout and exception handling?

Short answer

ExecutorService owns and schedules tasks. Future represents one submitted result but is mainly a blocking handle. CompletableFuture is both a result and a composable pipeline: it supports transformations, combination, timeout, and recovery without blocking every step.

import java.time.Duration;
import java.util.concurrent.CompletableFuture;
import java.util.concurrent.Executors;

public class CompletableFutureDemo {
    public static void main(String[] args) {
        try (var pool = Executors.newFixedThreadPool(4)) {
            CompletableFuture<String> profile = CompletableFuture
                    .supplyAsync(() -> "profile", pool);
            CompletableFuture<String> balance = CompletableFuture
                    .supplyAsync(() -> "balance", pool);

            String result = profile.thenCombine(balance,
                            (p, b) -> p + "+" + b)
                    .orTimeout(2, java.util.concurrent.TimeUnit.SECONDS)
                    .exceptionally(error -> "fallback")
                    .join();

            System.out.println(result);
        }
    }
}

Expected output: profile+balance. If either operation fails or exceeds two seconds, the result becomes fallback.

Internal working and production rules

  • supplyAsync runs a value-producing task; runAsync runs a task with no result.
  • thenApply transforms a result; thenCompose flattens a dependent asynchronous call; thenCombine joins independent calls.
  • Use an application-owned executor for blocking or isolated work. The default common pool is not automatically safe for every workload.
  • orTimeout completes exceptionally after a deadline; it does not necessarily interrupt the underlying remote HTTP call. Configure the HTTP client timeout too.
  • Use handle, exceptionally, or exceptionallyCompose for recovery, and preserve enough context for logging and tracing.

Follow-up questions

  • Does Future.get() make work asynchronous? Submission may be asynchronous, but get blocks the caller. CompletableFuture enables non-blocking composition.
  • When use allOf? When many independent futures must all finish. It returns CompletableFuture<Void>, so collect the individual results separately.
  • How do you avoid resource leaks? Bound the executor, shut it down, configure client timeouts, and avoid creating an unbounded executor per request.

Interview-ready answer

ExecutorService schedules work, Future exposes a mostly blocking handle, and CompletableFuture composes asynchronous stages. I use an explicit bounded executor, start independent API calls concurrently, combine them with thenCombine or allOf, set both future and client timeouts, and recover or propagate failures deliberately.

Step-by-step orchestration

Imagine an order endpoint that needs customer, inventory, and pricing data. Customer and inventory are independent, so start them together. Pricing may depend on the customer tier, so compose it after the customer future. This avoids blocking the request thread while each remote call is waiting.

import java.util.concurrent.*;

public class ApiCompositionDemo {
    static CompletableFuture<String> call(String name, Executor executor) {
        return CompletableFuture.supplyAsync(() -> name, executor);
    }

    public static void main(String[] args) {
        ExecutorService pool = Executors.newFixedThreadPool(4);
        try {
            CompletableFuture<String> customer = call("customer", pool);
            CompletableFuture<String> inventory = call("inventory", pool);

            CompletableFuture<String> response = customer
                    .thenCombine(inventory, (c, i) -> c + "+" + i)
                    .orTimeout(1, TimeUnit.SECONDS)
                    .handle((value, error) -> error == null
                            ? value : "degraded-response");

            System.out.println(response.join());
        } finally {
            pool.shutdown();
        }
    }
}

Expected output: customer+inventory. If a stage fails or exceeds the timeout, the handler prints degraded-response.

Future versus CompletableFuture

TypeWhat it providesLimitation
ExecutorServiceTask submission, scheduling, pooling, shutdownMust size and operate the executor correctly
FutureCancellation, completion check, blocking getHard to compose several results without blocking
CompletableFutureNon-blocking transformations, combination, timeout, recoveryChains can become difficult to debug; executor choice still matters

thenApply maps a completed value, thenCompose chains a dependent future, thenCombine joins two independent futures, and allOf waits for many. The Async variants schedule the continuation asynchronously; the non-async variants may run it on the thread that completes the previous stage.

Timeout, cancellation, and exception behavior

  • orTimeout completes the future exceptionally; it does not guarantee that a remote socket call is interrupted.
  • completeOnTimeout supplies a fallback value, which is appropriate only when degraded data is safe.
  • exceptionally handles failures and returns a replacement value; handle receives either a value or error.
  • join throws an unchecked CompletionException; get throws checked exceptions and can be interrupted.
  • Cancellation is cooperative. Configure timeouts in the HTTP client, database driver, and load balancer as well as in the future.

Executor sizing and real-world safeguards

Use a bounded executor or a well-understood virtual-thread strategy. For CPU-bound work, start near the number of available processors. For blocking I/O, the pool can be larger, but it must be bounded by downstream capacity, connection pools, rate limits, and memory. Add correlation IDs, metrics for queue time and remote latency, retries only for transient errors, and a circuit breaker for unhealthy dependencies.

Additional follow-up answers

  • What is the difference between thenCompose and thenCombine? Compose is for a dependent second future; combine is for two futures that can run independently.
  • How do you collect results from allOf? Keep the typed futures, await allOf, then call join on each completed future.
  • Should every failure be retried? No. Retry only transient failures, use exponential backoff and jitter, and avoid retrying validation or authorization errors.
  • Why can async code still block? Calling join or get blocks the caller, and the task itself may block on I/O. Async composition does not make a blocking dependency non-blocking.

Question: How do functional interfaces, lambda expressions, method references, and Optional work in Java 8?

Short answer

A functional interface has exactly one abstract method, such as Predicate, Function, Consumer, or Supplier. A lambda supplies the implementation, and a method reference is shorter syntax for a compatible existing method. Optional models a possibly absent return value; it is not a replacement for every nullable field or parameter.

import java.util.Optional;
import java.util.function.Function;

public class FunctionalDemo {
    @FunctionalInterface
    interface Discount { int apply(int price); }

    public static void main(String[] args) {
        Discount tenPercent = price -> price * 90 / 100;
        Function<String, String> normalize = String::trim;

        String name = Optional.ofNullable("  Ada  ")
                .map(normalize)
                .filter(value -> !value.isEmpty())
                .orElse("unknown");

        System.out.println(tenPercent.apply(100));
        System.out.println(name);
    }
}

Expected output: 90 and Ada.

Internal working and pitfalls

The compiler converts a lambda to a functional-interface instance, commonly through invokedynamic; it is not literally a new named method in source. Lambdas can capture only final or effectively final local variables. Method references still obey the target functional interface signature. Optional.map transforms a present value, flatMap avoids nested optionals, and orElseGet evaluates its fallback lazily while orElse evaluates it immediately.

  • Use Optional mainly for return values where absence is expected.
  • Do not call get() without checking; prefer orElseThrow or a transformation chain.
  • Do not put Optional in JPA entities or serialize it casually without understanding the framework contract.
  • Keep lambdas small and side-effect free, especially inside streams.

Follow-up questions

  • Can an interface have default methods? Yes. It may have many default or static methods, but only one abstract method to remain functional.
  • What is the difference between Predicate and Function? A predicate returns boolean; a function maps a value to another value.
  • Why is orElseGet often preferred? Its supplier runs only when the optional is empty, avoiding unnecessary work.

Interview-ready answer

A functional interface has one abstract method. Lambdas and method references provide implementations that the compiler targets to that interface, while Optional represents an absent-or-present return value. I use these features for clear transformations, avoid side effects and Optional.get, and choose orElseGet when fallback creation is expensive.

Functional interfaces in detail

InterfaceMethodExample use
Predicate<T>boolean test(T)Filtering or validation

@FunctionalInterface asks the compiler to enforce the one-abstract-method rule. Default and static methods do not count as abstract methods. A lambda is compatible with a target type, so the same lambda syntax can mean different things depending on the expected interface.

Lambda capture and method references

import java.util.function.*;

public class LambdaDetailsDemo {
    static String clean(String value) { return value.trim().toUpperCase(); }

    public static void main(String[] args) {
        String prefix = "ID-"; // effectively final
        Function<String, String> lambda = value -> prefix + clean(value);
        Function<String, String> reference = LambdaDetailsDemo::clean;

        System.out.println(lambda.apply("  a1  "));
        System.out.println(reference.apply("  hello  "));
    }
}

Expected output: ID-A1 and HELLO. A local variable captured by a lambda must be final or effectively final; otherwise its changing stack lifetime would not match the lambda's lifetime.

The compiler typically implements lambdas with invokedynamic. This is an implementation mechanism, not a reason to rely on a particular generated class name. Captured values are stored in the lambda object, so capturing large objects can unintentionally extend their lifetime.

Optional operations and common mistakes

import java.util.Optional;

public class OptionalDemo {
    static String city(String input) {
        return Optional.ofNullable(input)
                .map(String::trim)
                .filter(value -> !value.isEmpty())
                .orElseGet(() -> "unknown");
    }

    public static void main(String[] args) {
        System.out.println(city("  Chicago  "));
        System.out.println(city("   "));
    }
}

Expected output: Chicago and unknown. map converts a present value and turns a null mapper result into empty; flatMap is used when the mapper already returns an Optional. orElse evaluates its argument immediately, while orElseGet invokes the supplier only when needed.

  • Do not use Optional.get() as a disguised null check.
  • Do not use Optional for every field, setter, or method parameter unless the API convention explicitly requires it.
  • Be careful with orElse when the fallback performs I/O, allocates, or has side effects.
  • Use primitive variants such as OptionalInt when appropriate to avoid boxing.
  • A lambda can throw unchecked exceptions, but checked exceptions need handling or an adapter.

Real-world use

Use predicates for validation rules, functions for DTO mapping, consumers for metrics or audit events, suppliers for lazy defaults, and Optional for repository methods such as findById. Keep business side effects outside long transformation chains so failures and debugging remain clear.

Additional follow-up answers

  • Why are lambdas useful in streams? They represent behavior as values, allowing operations such as filtering and mapping to be composed.
  • Can a lambda modify a captured local variable? It cannot reassign a captured local variable, but it can mutate a referenced mutable object—which should be avoided in parallel pipelines.
  • What is the difference between a method reference and a lambda? A method reference is shorthand when an existing method already matches the target signature; both create behavior for a functional interface.
  • How is Optional different from null? Optional makes absence explicit in an API return type, but it does not eliminate all nulls or replace validation.

Question: What are the important Java 17 and Java 21 features, including records, sealed classes, pattern matching, switch expressions, and virtual threads?

Short answer

Java 17 is an LTS release with records, sealed classes, pattern matching for instanceof, text blocks, and modernized APIs. Java 21 is an LTS release that finalizes pattern matching for switch, record patterns, sequenced collections, and virtual threads. These features reduce boilerplate and improve concurrency, but they do not remove the need to manage blocking calls, memory, and service limits.

public class ModernJavaDemo {
    record User(String name, int age) {}

    sealed interface Result permits Success, Failure {}
    record Success(String value) implements Result {}
    record Failure(String message) implements Result {}

    static String describe(Result result) {
        return switch (result) {
            case Success success -> "value=" + success.value();
            case Failure failure -> "error=" + failure.message();
        };
    }

    public static void main(String[] args) throws Exception {
        User user = new User("Maya", 30);
        if (user instanceof User(String name, int age) && age >= 18) {
            System.out.println(name + " is an adult");
        }
        System.out.println(describe(new Success("ok")));
        try (var executor = java.util.concurrent.Executors.newVirtualThreadPerTaskExecutor()) {
            executor.submit(() -> System.out.println("virtual thread" )).get();
        }
    }
}

Expected output: Maya is an adult, value=ok, and virtual thread (the last line may appear in a different scheduling context).

Feature details and limitations

  • Records: concise immutable data carriers with generated accessors, constructor, equals, hashCode, and toString. A record is shallowly immutable; mutable fields still need defensive copies.
  • Sealed classes: restrict permitted subtypes and let the compiler reason about an exhaustive hierarchy.
  • Pattern matching: combines type checks, casts, record destructuring, and switch expressions in a safer form.
  • Virtual threads: are lightweight threads suited to large numbers of mostly blocking tasks. They improve concurrency, not CPU capacity, and should not be used to hide unbounded downstream calls.
  • Migration: verify library compatibility, compiler release settings, reflection behavior, container images, monitoring, and framework support before changing the runtime.

Follow-up questions

  • Are virtual threads faster than platform threads for CPU work? No. They mainly reduce the cost of waiting and allow many concurrent blocking tasks.
  • Can a record extend a class? No, records implicitly extend java.lang.Record, but they can implement interfaces.
  • Why use a sealed hierarchy? It makes domain states explicit and allows exhaustive pattern matching, which helps catch missing cases at compile time.

Interview-ready answer

Java 17 and 21 add concise data modeling and safer control flow through records, sealed classes, pattern matching, and switch expressions. Java 21 virtual threads make high-concurrency blocking workloads cheaper, but they do not make CPU work faster or remove database and downstream limits. I evaluate runtime, libraries, observability, and workload characteristics when adopting them.

Java 17 feature details

  • Records: concise nominal data carriers with final components, generated accessors, equality, hash code, and a canonical constructor.
  • Sealed classes: explicitly define permitted subclasses and make domain state transitions easier to review.
  • Pattern matching for instanceof: combines the type test and cast, reducing repeated boilerplate.
  • Text blocks: make multiline JSON, SQL, and templates easier to read.
  • Helpful NullPointerException messages: improve diagnosis by identifying the null expression in many cases.

A record is not deeply immutable. A record component such as List<String> still needs List.copyOf if callers must not mutate it. A compact constructor is useful for validation and normalization.

record Money(String currency, long cents) {
    Money {
        if (cents < 0) throw new IllegalArgumentException("negative amount");
        currency = currency.toUpperCase();
    }
}

Java 21 feature details

  • Pattern matching for switch: switch over types and values with compiler-checked exhaustiveness.
  • Record patterns: destructure record components in conditions and switch cases.
  • Sequenced collections: common first, last, and reversed operations across ordered collections.
  • Virtual threads: lightweight threads scheduled by the JVM and designed for very high numbers of mostly waiting tasks.
  • Scoped values and structured concurrency: important modern concurrency ideas; check the exact JDK release and preview status before production adoption.

Virtual threads are cheap to create, but a request that waits on a database still consumes a database connection. They improve thread scalability around blocking waits; they do not increase CPU cores, database capacity, or external API limits. Avoid pinning virtual threads with long synchronized or native sections, and measure with production-like load.

Virtual-thread example

import java.util.concurrent.Executors;

public class VirtualThreadDemo {
    public static void main(String[] args) throws Exception {
        try (var executor = Executors.newVirtualThreadPerTaskExecutor()) {
            var first = executor.submit(() -> "order-1");
            var second = executor.submit(() -> "order-2");
            System.out.println(first.get() + "," + second.get());
        }
    }
}

Expected output: order-1,order-2. The executor creates a virtual thread per submitted task and closes after all tasks finish. It is still important to bound calls to scarce resources with connection pools, semaphores, or rate limiters.

Migration and compatibility checklist

  1. Compile with the intended --release and run the same major JDK in local, CI, and production environments.
  2. Check Spring Boot, JDBC drivers, agents, serializers, bytecode tools, and monitoring libraries for supported JDK versions.
  3. Test reflection, serialization, native libraries, and module access; newer JDKs may expose illegal assumptions.
  4. Load-test virtual threads with real downstream limits and inspect thread dumps, blocked tasks, heap, and connection pools.
  5. Use preview features only with an explicit rollout decision because syntax or behavior can change before finalization.

Additional follow-up answers

  • Are records immutable? Their components are final, but referenced mutable objects are not automatically copied.
  • Can a record extend another class? No. It implicitly extends Record, but it can implement interfaces.
  • When should virtual threads be avoided? For CPU-bound work where a bounded platform-thread pool is clearer, or when downstream systems cannot handle more concurrent requests.
  • What does exhaustive switch checking provide? The compiler can identify a missing permitted subtype or enum case, reducing runtime default-case surprises.
  • Do newer Java features change garbage collection? They change language and concurrency capabilities; GC selection and tuning remain workload and runtime concerns.
