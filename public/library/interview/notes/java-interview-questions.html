Question: How does HashMap work internally, and what happens during hash collisions, resizing, and concurrent modification?

Short answer

HashMap stores key-value pairs in an array of buckets. It hashes the key, converts the hash into a bucket index, and then searches that bucket using equals. If two keys map to the same bucket, a collision is handled by storing multiple entries in that bucket. In modern Java, a crowded bucket can change from a linked list into a balanced red-black tree. When the map grows past its threshold, it resizes and redistributes entries. Its iterators are fail-fast: structural modification during iteration usually throws ConcurrentModificationException, but this is a best-effort bug detector rather than a thread-safety guarantee.

Start with the basics

What is a map?

A map associates a unique key with a value. For example, an employee ID can identify an employee record:

Map<Integer, String> employees = new HashMap<>();
employees.put(101, "Maya");
employees.put(102, "Luis");

System.out.println(employees.get(101)); // Maya
  • Keys are unique. Adding the same key replaces its old value.
  • Values may repeat.
  • HashMap permits one null key and multiple null values.
  • It does not guarantee insertion order. Use LinkedHashMap for insertion/access order or TreeMap for sorted keys.
  • It is not synchronized and should not be shared for concurrent writes without coordination.

Internal structure

A simplified map looks like this:

table
  [0] - empty
  [1] - Entry(keyA, valueA) -> Entry(keyB, valueB)
  [2] - empty
  [3] - TreeNode(keyC, valueC)
  ...

Each entry contains a key, value, hash, and a link to the next entry when the bucket uses a linked list. The implementation uses internal node classes, but this is the useful mental model:

class Entry<K, V> {
    final int hash;
    final K key;
    V value;
    Entry<K, V> next;
}

Step 1: Hash the key

When you call put(key, value) or get(key), Java obtains the key's hash code and spreads high bits into low bits so more of the hash participates in bucket selection. The conceptual Java 8+ operation is:

int h = key.hashCode();
int spreadHash = h ^ (h >>> 16);

This matters because bucket selection uses the low bits. A key whose hashCode() differs mostly in high bits can still be distributed more evenly after spreading.

Step 2: Calculate the bucket index

For a table length n, HashMap conceptually calculates:

int index = (n - 1) & spreadHash;

The table length is kept as a power of two, such as 16, 32, or 64. That lets a bitwise AND replace a slower remainder operation. This is an implementation detail; application code should never depend on a specific bucket number.

Step 3: Search the bucket

HashMap first compares the stored hash. If the hash matches, it compares keys using identity or equals:

if (storedHash == requestedHash
        && (storedKey == requestedKey
            || requestedKey.equals(storedKey))) {
    return storedValue;
}
  • hashCode narrows the search to a bucket.
  • equals identifies the exact key inside that bucket.

Hash collisions

A collision occurs when different keys select the same bucket. A collision is not automatically an error. HashMap stores both entries in that bucket and uses equals to distinguish them.

Runnable collision example

import java.util.HashMap;
import java.util.Map;

public class HashCollisionDemo {
    static final class Key {
        private final String name;

        Key(String name) {
            this.name = name;
        }

        @Override
        public int hashCode() {
            return 42; // Deliberately force a collision.
        }

        @Override
        public boolean equals(Object other) {
            return other instanceof Key key && name.equals(key.name);
        }

        @Override
        public String toString() {
            return name;
        }
    }

    public static void main(String[] args) {
        Map<Key, Integer> scores = new HashMap<>();
        scores.put(new Key("A"), 10);
        scores.put(new Key("B"), 20);

        System.out.println(scores.get(new Key("A")));
        System.out.println(scores.get(new Key("B")));
        System.out.println(scores.size());
    }
}

Expected output:

10
20
2

All keys return the same hash, but equals still separates A from B. With a small number of collisions, the bucket is commonly a linked list. In Java 8 and later, a sufficiently crowded bucket can be treeified into a red-black tree, improving a long collision search from approximately O(n) to O(log n).

Treeification details

OpenJDK implementations commonly use these thresholds:

  • TREEIFY_THRESHOLD = 8: a bucket may be converted to a tree when it becomes crowded.
  • UNTREEIFY_THRESHOLD = 6: a tree can become a list again after removals.
  • MIN_TREEIFY_CAPACITY = 64: before treeifying, HashMap prefers resizing if the table is still small.

These are implementation details, not API contracts. The practical interview point is that good hash distribution matters, and modern Java has a tree fallback for unusually long collision chains.

Resizing and load factor

HashMap starts with a table capacity and a load factor. The default load factor is 0.75. The resize threshold is approximately:

threshold = capacity * loadFactor

With capacity 16 and load factor 0.75, the map resizes when it grows beyond roughly 12 entries. Resizing normally doubles the table capacity. Entries are redistributed because the new index can change when the table length changes.

Why does resizing cost time?

Adding one entry is usually O(1), but resizing requires visiting existing entries. That individual operation is expensive, so HashMap has amortized O(1) insertion rather than a strict O(1) guarantee for every call. If you know the expected size, choose an appropriate initial capacity:

Map<String, Integer> counts = new HashMap<>(1_000);

Do not blindly use a huge capacity. It consumes memory and can make iteration more expensive. Capacity, load factor, key distribution, and actual workload should guide tuning.

Duplicate keys and nulls

Map<String, String> users = new HashMap<>();
users.put("u1", "old email");
String previous = users.put("u1", "new email");

System.out.println(previous);
System.out.println(users.get("u1"));

Expected output:

old email
new email

The key remains one entry. The new value replaces the old value, and put returns the previous value. A plain HashMap also permits one null key, while ConcurrentHashMap rejects null keys and values.

Concurrent modification

What does fail-fast mean?

HashMap iterators track a modification count. A structural change such as adding or removing a mapping changes that count. The iterator remembers the count from its creation and usually throws ConcurrentModificationException if it detects a mismatch.

import java.util.HashMap;
import java.util.Map;

public class ConcurrentModificationDemo {
    public static void main(String[] args) {
        Map<String, Integer> values = new HashMap<>();
        values.put("keep", 1);
        values.put("remove", 2);

        for (String key : values.keySet()) {
            if (key.equals("remove")) {
                values.remove(key); // Usually throws ConcurrentModificationException.
            }
        }
    }
}

Typical result:

Exception in thread "main" java.util.ConcurrentModificationException

The exception is not a guarantee that every unsafe modification will be detected. It is a best-effort fail-fast check. It does not make HashMap thread-safe.

Safe removal during iteration

values.entrySet().removeIf(entry -> entry.getKey().equals("remove"));

Or use the iterator's own removal operation:

var iterator = values.entrySet().iterator();
while (iterator.hasNext()) {
    if (iterator.next().getKey().equals("remove")) {
        iterator.remove();
    }
}

What if multiple threads access the map?

Concurrent reads are not a substitute for safe publication and coordinated writes. Concurrent writes can race, lose updates, and interact badly with resizing. Use the collection that matches the requirement:

  • ConcurrentHashMap for a general-purpose concurrent map.
  • Collections.synchronizedMap for a synchronized wrapper; iteration still requires external synchronization.
  • An immutable map such as Map.of when data never changes.
  • A database or distributed cache when state must be shared across application instances.

HashMap versus ConcurrentHashMap

import java.util.concurrent.ConcurrentHashMap;

var counts = new ConcurrentHashMap<String, Integer>();
counts.merge("orders", 1, Integer::sum);
counts.merge("orders", 1, Integer::sum);

System.out.println(counts.get("orders"));

Expected output:

2

merge makes the read-update-write operation atomic for that key. ConcurrentHashMap also provides weakly consistent iterators: they do not normally throw ConcurrentModificationException, and they may reflect some updates that happen during iteration.

Key correctness rules

Why must keys be immutable?

If a key changes in a way that affects equals or hashCode after insertion, the map may no longer find the entry in the bucket where it was placed.

import java.util.HashMap;
import java.util.Map;

public class MutableKeyDemo {
    static final class UserKey {
        String id;
        UserKey(String id) { this.id = id; }
        @Override public int hashCode() { return id.hashCode(); }
        @Override public boolean equals(Object o) {
            return o instanceof UserKey k && id.equals(k.id);
        }
    }

    public static void main(String[] args) {
        UserKey key = new UserKey("A");
        Map<UserKey, String> map = new HashMap<>();
        map.put(key, "Alice");
        key.id = "B";

        System.out.println(map.get(key));
        System.out.println(map.containsKey(key));
    }
}

Typical output:

null
false

The entry may still physically exist, but the changed key now hashes to a different location. Prefer immutable key types such as String, enums, records with immutable components, or carefully designed value objects.

equals and hashCode contract

  • If two objects are equal, they must have the same hash code.
  • Unequal objects may share a hash code; that is a collision, not a contract violation.
  • If a key's equality-relevant state changes while it is in the map, lookup behavior becomes unsafe.

Real-world examples

  • Request deduplication: map an idempotency key to a completed response, but use a database uniqueness constraint when multiple application instances can receive the same request.
  • Configuration lookup: map a property name or enum to a typed setting. Make the map immutable after startup if request threads read it.
  • Local cache: map a product ID to a cached value with explicit expiration and a concurrency strategy. A plain HashMap is not a production cache.
  • Counting: use merge in a single-threaded map, or ConcurrentHashMap.merge for concurrent counters.
  • Database identity map: use an entity ID as a stable key, not a mutable field such as a display name.

Common follow-up interview questions and answers

1. Why are HashMap capacities powers of two?

Power-of-two capacity allows the efficient index calculation (n - 1) & hash. Resizing also lets entries stay in the old index or move by the old capacity based on one additional hash bit.

2. What happens if two keys have the same hash code?

They go to the same bucket. HashMap then uses equals to decide whether the key is the same or whether this is a separate entry. Different keys with the same hash are valid.

3. What happens if equals is overridden but hashCode is not?

Equal objects may produce different hashes and land in different buckets. A lookup using an equal object can fail. Always override both consistently.

4. What happens if hashCode is overridden but equals is not?

Different objects can collide more often, and logically equivalent keys may not replace one another. The map may still function, but it will not represent the intended key identity.

5. Is HashMap synchronized?

No. Use ConcurrentHashMap, a synchronized wrapper, external locking, immutable data, or a distributed store depending on scope and consistency requirements.

6. Can HashMap have a null key?

Yes, one null key and multiple null values. ConcurrentHashMap does not allow null keys or values because null would be ambiguous with “no mapping” during concurrent operations.

7. Why does ConcurrentModificationException happen?

An iterator detected a structural modification not performed through that iterator. It is a fail-fast diagnostic, not proof that every concurrent modification was detected.

8. Does changing a value count as structural modification?

Replacing the value for an existing key usually does not change the map's structure. Adding or removing a mapping does. Do not rely on implementation-specific details when designing concurrent code.

9. HashMap versus Hashtable?

Hashtable is a legacy synchronized map that disallows null keys and values. Prefer HashMap for single-threaded use and ConcurrentHashMap for concurrent use.

10. HashMap versus LinkedHashMap versus TreeMap?

HashMap optimizes general lookup without order, LinkedHashMap preserves insertion or access order, and TreeMap keeps keys sorted using natural ordering or a comparator.

11. Why should initial capacity be chosen carefully?

Too little capacity causes repeated resizing; too much wastes memory and can make iteration scan many empty buckets. Estimate expected entries and account for the load factor.

12. Does HashMap protect against malicious collisions?

Modern Java's tree bins reduce the impact of very long collision chains, but application code should still use good key types and avoid attacker-controlled pathological hashing where possible. Hashing is not a substitute for input validation or rate limiting.

Interview-ready answer

HashMap stores entries in an array of buckets. It spreads the key's hash, selects a bucket with a bitwise index calculation, and uses hash plus equals to find the exact key. Different keys can collide in one bucket; the bucket is normally a linked list and can become a red-black tree when it is crowded. HashMap resizes when size exceeds capacity times load factor, usually doubling capacity and redistributing entries, so puts are O(1) amortized rather than guaranteed O(1) individually. HashMap is not thread-safe. Its iterators are fail-fast and may throw ConcurrentModificationException when the map is structurally changed during iteration, but that is only a best-effort diagnostic. For concurrent access I would use ConcurrentHashMap and atomic operations such as merge or compute.

Quick checklist

  • Know the path: hashCode -> spread -> bucket index -> hash/equality check.
  • Know collisions: list first, tree fallback in modern Java.
  • Know resizing: threshold is approximately capacity times load factor.
  • Know the contract: equal keys must have equal hashes; keys should be effectively immutable.
  • Know concurrency: HashMap is unsafe for concurrent writes; fail-fast is not synchronization.
  • Know alternatives: LinkedHashMap, TreeMap, ConcurrentHashMap, synchronizedMap, and immutable maps.

Question: How do equals(), hashCode(), ==, and compareTo() differ, and what happens when they are implemented incorrectly?

Short answer

== compares primitive values or object references. equals compares logical equality when a class overrides it. hashCode supplies a hash used by hash-based collections and must agree with equals. compareTo defines ordering for Comparable. Breaking these contracts causes duplicate set entries, failed map lookups, incorrect sorting, or inconsistent tree-based collections.

How the operations differ

OperationPurposeTypical use
==Primitive value or reference identityCheck whether two references point to the same object
equalsLogical equalityCompare business values such as two account IDs
hashCodeHash bucket selectionHashMap, HashSet, and related collections
compareToRelative ordering: negative, zero, or positiveTreeMap, TreeSet, and sorting

Runnable example

import java.util.*;

record EmployeeId(String value) implements Comparable<EmployeeId> {
    @Override
    public int compareTo(EmployeeId other) {
        return value.compareTo(other.value);
    }
}

public class EqualityDemo {
    public static void main(String[] args) {
        String first = new String("java");
        String second = new String("java");

        System.out.println(first == second);
        System.out.println(first.equals(second));
        System.out.println(first.hashCode() == second.hashCode());
        System.out.println(new EmployeeId("E2").compareTo(new EmployeeId("E10")) > 0);
    }
}

Expected output:

false
true
true
true

The last result is true because lexicographical string ordering compares the first character that differs; it is not numeric ordering. If numeric ordering is needed, compare parsed numbers or use a numeric field.

Internal working

  1. HashMap first uses hashCode to select a bucket.
  2. It then uses equals to identify the exact key inside that bucket.
  3. HashSet uses the same rules because it is backed by a map.
  4. TreeMap and TreeSet use ordering, usually compareTo or a supplied Comparator, instead of hash lookup.

What goes wrong when contracts are broken?

  • Override equals without hashCode: equal objects can enter different hash buckets, so contains or get may fail.
  • Use mutable fields in equality: changing a key after insertion can make the entry unreachable.
  • Make compareTo inconsistent with equality: a TreeSet can treat two unequal objects as duplicates when comparison returns zero.
  • Use subtraction such as this.age - other.age: integer overflow can produce the wrong ordering. Use Integer.compare.

Real-world example

A payment service may identify a request with PaymentId. Its equality should use the stable payment ID, not mutable status or display fields. That makes idempotency maps, database entity lookups, and deduplication predictable.

Follow-up questions

  • Should equal objects always have the same hash code? Yes. The reverse is not required; collisions are allowed.
  • Can compareTo return any negative or positive number? Yes. Only the sign matters, although zero must mean equivalent ordering.
  • Why is BigDecimal a common interview edge case? Its equals considers scale while compareTo does not, so new BigDecimal("1.0") and new BigDecimal("1.00") compare as equal by ordering but not by equals.

Interview-ready answer

== checks primitive values or reference identity, while equals checks logical equality. Hash-based collections use hashCode to find a bucket and equals to find the exact key, so equal objects must have equal hashes. compareTo defines ordering for sorted collections. Breaking these contracts causes failed lookups, duplicate set entries, or incorrect tree ordering.

Question: How do you design an immutable Java class, and why does immutability help with thread safety?

Short answer

An immutable object cannot change after construction. Make the class difficult or impossible to extend, keep fields private and final, initialize them in the constructor, provide no setters, validate inputs, and make defensive copies of mutable objects. Immutability removes shared state changes, so multiple threads can safely read the same object without locks.

Rules for an immutable class

  1. Declare the class final, or carefully control subclassing.
  2. Make state private final.
  3. Set every field during construction.
  4. Do not expose setters or mutable internal state.
  5. Defensively copy mutable input and output such as Date, arrays, and collections.
  6. Validate invariants before publishing the object.

Runnable example

import java.util.*;

public final class UserProfile {
    private final String name;
    private final List<String> roles;

    public UserProfile(String name, List<String> roles) {
        this.name = Objects.requireNonNull(name);
        this.roles = List.copyOf(roles);
    }

    public String name() { return name; }
    public List<String> roles() { return roles; }
}

class ImmutableDemo {
    public static void main(String[] args) {
        List<String> input = new ArrayList<>(List.of("USER"));
        UserProfile profile = new UserProfile("Maya", input);
        input.add("ADMIN");

        System.out.println(profile.name());
        System.out.println(profile.roles());
        try {
            profile.roles().add("ADMIN");
        } catch (UnsupportedOperationException ex) {
            System.out.println("roles cannot be changed");
        }
    }
}

Expected output:

Maya
[USER]
roles cannot be changed

Internal working and thread safety

Threads can safely share an immutable object because its fields never change after construction. A properly constructed object also benefits from the Java Memory Model's final-field guarantees: other threads can reliably observe final fields after safe publication. Immutability does not automatically make referenced objects safe; the whole object graph must be immutable or safely wrapped.

Edge cases

  • Collections.unmodifiableList prevents mutation through that view but does not copy the original list. Changes to the original list may still be visible.
  • A final reference cannot be reassigned, but the referenced object can still be mutable.
  • Returning an internal array directly breaks immutability. Return a copy.
  • Lazy caching inside an immutable object needs safe publication or synchronization.
  • Serialization, reflection, and deserialization can bypass normal constructors, so sensitive classes may need extra protection.

Real-world examples

Value objects such as money, coordinates, configuration snapshots, request objects, cache keys, and Java records are good candidates. Immutable configuration can be shared by request threads without defensive locking.

Follow-up questions

  • Are records always immutable? No. A record's fields are final, but a field may refer to a mutable list or object. Use defensive copies.
  • Why use a builder? A builder helps create complex immutable objects while keeping the final object itself unchangeable.
  • Is immutability faster? It can reduce locking and simplify caching, but defensive copying may add allocation cost.

Interview-ready answer

An immutable class is fully initialized in its constructor and never changes afterward. I use private final fields, no setters, validation, defensive copies, and controlled inheritance. Since threads only read stable state, immutable objects can be shared without locks, are safe as map keys, and are easier to reason about.

Question: How does Java memory management work, including heap, stack, references, pass-by-value, and object allocation?

Short answer

Objects and arrays are normally allocated on the heap and managed by the garbage collector. Each thread has its own stack containing method frames, local variables, and references. A reference is a value that points to an object; it is not the object itself. Java is always pass-by-value: for objects, the value passed is a copy of the reference.

Heap, stack, and references

  • Heap: shared memory for objects, arrays, and most application data.
  • Stack: per-thread call frames containing parameters, locals, and return information.
  • Reference: a variable value used to reach an object; multiple references can point to one object.
  • Metaspace: native memory used for class metadata in modern HotSpot JVMs.

Runnable pass-by-value example

class Box { int value; Box(int value) { this.value = value; } }

public class MemoryDemo {
    static void change(Box box) {
        box.value = 20;
        box = new Box(30);
    }

    static void reassign(int value) {
        value = 99;
    }

    public static void main(String[] args) {
        Box box = new Box(10);
        int number = 1;
        change(box);
        reassign(number);
        System.out.println(box.value);
        System.out.println(number);
    }
}

Expected output:

20
1

The method receives a copy of the reference. It can mutate the shared object through that copy, but assigning the parameter to a new object does not change the caller's reference.

Object allocation and garbage collection

  1. The JVM loads class metadata and checks the requested type.
  2. It allocates space for the object and initializes fields to default values.
  3. The constructor runs and establishes the object's state.
  4. When no GC-root path can reach the object, it becomes eligible for collection.

GC roots include active stack references, static fields, JNI references, and running threads. An object being eligible for collection does not mean it is collected immediately.

Performance details

HotSpot may optimize allocation with thread-local allocation buffers, escape analysis, scalar replacement, and stack allocation-like optimizations. These are implementation optimizations; Java code should not depend on a particular object location.

Edge cases

  • StackOverflowError usually indicates excessive recursion or very large stack frames.
  • OutOfMemoryError: Java heap space can mean too many live objects or a leak.
  • Native buffers, thread stacks, metaspace, and direct memory can exhaust a container even when heap usage looks normal.
  • Calling System.gc() is only a request and is not a reliable memory-management strategy.

Real-world example

In a web service, each request creates temporary DTOs and parsing objects. Those objects become collectible after the request finishes unless a cache, static collection, thread local, listener, or long-lived task retains them.

Follow-up questions

  • Does Java pass objects by reference? No. It passes a copy of the reference by value.
  • When is an object garbage collected? When it is unreachable from GC roots and a collector decides to reclaim it.
  • Can local variables live on the heap? The language does not guarantee physical placement; the JVM may optimize representation.

Interview-ready answer

Java normally stores objects on the shared heap and method frames on each thread's stack. References are values pointing to heap objects, and garbage collection reclaims objects that are unreachable from GC roots. Java is always pass-by-value: an object parameter is a copied reference, so a method can mutate the object but cannot replace the caller's reference.

Question: How do Java generics, type erasure, reflection, and annotations work internally?

Short answer

Generics provide compile-time type safety and are mostly implemented through type erasure, so ordinary generic type arguments are removed from runtime bytecode. The compiler inserts casts where needed. Reflection inspects classes, methods, fields, and annotations at runtime. Annotations are metadata whose retention determines whether they exist only in source, in class files, or at runtime.

Generics and type erasure

import java.util.*;

public class GenericsDemo {
    public static void main(String[] args) {
        List<String> names = new ArrayList<>();
        names.add("Maya");
        String name = names.get(0); // compiler inserts a cast to String
        System.out.println(name);

        System.out.println(names instanceof List<?>);
    }
}

Expected output:

Maya
true

At runtime, the JVM generally sees an ArrayList, not an ArrayList<String>. This is why List<String>.class is illegal and why instanceof List<String> is not allowed.

Reflection and annotations

import java.lang.annotation.*;

@Retention(RetentionPolicy.RUNTIME)
@Target(ElementType.TYPE)
@interface Endpoint { String value(); }

@Endpoint("/orders")
class OrderController { }

public class ReflectionDemo {
    public static void main(String[] args) {
        Class<OrderController> type = OrderController.class;
        Endpoint endpoint = type.getAnnotation(Endpoint.class);
        System.out.println(type.getSimpleName());
        System.out.println(endpoint.value());
    }
}

Expected output:

OrderController
/orders

Frameworks such as Spring use reflection and runtime annotations to discover controllers, services, configuration, validation rules, and dependency injection metadata.

Important limitations and edge cases

  • Generic type arguments are normally unavailable at runtime, although frameworks can preserve them using a type token or subclass metadata.
  • Static fields cannot use a class's type parameter.
  • Primitive types cannot be generic arguments; use wrappers such as Integer.
  • Heap pollution can occur through raw types, unchecked casts, arrays, or unsafe varargs.
  • Reflection can bypass normal access checks and has performance and security implications.
  • SOURCE, CLASS, and RUNTIME retention control annotation visibility.

Real-world examples

Spring's @RestController, Jackson's serialization annotations, JUnit's @Test, and Bean Validation annotations are all examples of metadata-driven behavior. Generic repositories such as Repository<Order, Long> communicate type information to the compiler and sometimes to frameworks through reflection metadata.

Follow-up questions

  • Why can you not create new T()? Erasure removes the runtime type, so the compiler cannot know which constructor to call.
  • What is a bounded type parameter? A declaration such as <T extends Number> restricts accepted types and exposes the bound's operations.
  • What is the difference between reflection and annotation processing? Reflection runs at runtime; annotation processors inspect source during compilation and can generate code.

Interview-ready answer

Generics give compile-time type safety, but Java usually implements them through type erasure and inserts casts into bytecode. Reflection inspects runtime classes and members. Annotations provide metadata, and runtime-retained annotations can be read by frameworks such as Spring. The trade-off is that generic type arguments are usually unavailable at runtime and raw or unchecked operations can create heap pollution.

Question: How would you choose between HashMap, ConcurrentHashMap, Hashtable, CopyOnWriteArrayList, and TreeMap for different real-world applications?

Short answer

Choose based on ordering, concurrency, read/write ratio, null policy, and required operations. Use HashMap for ordinary single-threaded or externally synchronized key-value access, ConcurrentHashMap for concurrent map operations, TreeMap for sorted keys and range queries, and CopyOnWriteArrayList for many reads with very rare writes. Avoid new uses of legacy Hashtable unless compatibility requires it.

HashtableLegacy synchronized API compatibilityCoarse synchronization and legacy design
CopyOnWriteArrayListSmall list with many reads and very rare writesEvery write copies the array; poor for large or write-heavy lists
TreeMapSorted keys, first/last/range queriesO(log n), ordering rules must be consistent

import java.util.*;

public class CollectionChoiceDemo {

        Map<String, Integer> fastLookup = new HashMap<>();
        Map<String, Integer> sharedCounts = new ConcurrentHashMap<>();
        Map<Integer, String> sorted = new TreeMap<>();
        List<String> listeners = new CopyOnWriteArrayList<>();

        fastLookup.put("order-1", 100);
        sharedCounts.merge("success", 1, Integer::sum);
        sorted.put(2, "medium");
        sorted.put(1, "low");
        listeners.add("audit-listener");

        System.out.println(fastLookup.get("order-1"));
        System.out.println(sharedCounts.get("success"));
        System.out.println(sorted.firstKey());
        System.out.println(listeners);
    }
}

Concurrency details

ConcurrentHashMap makes individual operations and methods such as putIfAbsent, compute, and merge safe for concurrent use. A sequence such as “check then put” is not automatically atomic; use one of those compound operations. Its iterators are weakly consistent rather than fail-fast.

Hashtable synchronizes individual methods, but a sequence of calls still needs external coordination. CopyOnWriteArrayList gives readers a stable snapshot-like array and is useful for listener registries, configuration observers, or routing tables with rare changes.

Real-world decision examples

  • Per-request local lookup: HashMap.
  • Application-wide counters or a token registry: ConcurrentHashMap with merge or compute.
  • Time windows, sorted IDs, or range queries: TreeMap.
  • Event listeners read on every request but changed only during startup: CopyOnWriteArrayList.
  • Old library contract requiring a synchronized map: Hashtable, preferably behind a compatibility boundary.

Edge cases and common mistakes

  • Do not use CopyOnWriteArrayList for a high-volume queue or frequently updated collection.
  • Do not assume ConcurrentHashMap makes the values themselves thread-safe.
  • Do not use TreeMap when you only need lookup and do not need ordering.
  • Do not use a synchronized wrapper as a replacement for understanding iteration and compound-operation locking.
  • Do not select a collection only by benchmark numbers; measure the actual workload, memory pressure, and contention.

Follow-up questions

  • Why does ConcurrentHashMap reject null? A null result can clearly mean “no mapping” during concurrent operations, so allowing null would make APIs such as get ambiguous.
  • When is LinkedHashMap a better choice? When insertion or access order matters, such as a simple LRU-style structure.
  • What if I need a thread-safe sorted map? Consider ConcurrentSkipListMap, external synchronization, or a design that avoids shared mutation.

Interview-ready answer

I choose HashMap for ordinary unsynchronized lookup, ConcurrentHashMap for shared concurrent map updates, TreeMap for sorted keys and ranges, and CopyOnWriteArrayList for read-heavy lists with very rare writes. Hashtable is mainly a legacy compatibility choice. I also check whether compound operations need atomic methods such as compute or merge.
